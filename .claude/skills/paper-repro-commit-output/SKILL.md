# paper-repro：成果物の提示とコミット手順、実行結果の検証

## 1. いつ使うか

| 状況 | 適用する節 |
|---|---|
| paper-repro 向けに md やソースを作成・修正した | 第2〜4章 |
| 利用者がコマンドの実行結果を貼って「検証して」と言った | 第5章 |

**ファイルを作って説明だけで終えない。** 提示・手順・URL の3点を必ず出す。

---

## 2. 成果物の提示（必須）

### 2.1 zip と md の両方を提示する

`present_files` を**2回に分けず、1回の呼び出しでまとめて**渡す。渡す順序は次のとおり。

1. **変更した md ファイルを個別に**（最も見てほしいものから）
2. 最後に**配置用の zip**

md を個別に渡すのは、**利用者がチャット内で中身を開いて確認できるようにする**ためである。
zip だけを渡すと、ダウンロードして展開するまで内容が読めない。

```
present_files([
  "/mnt/user-data/outputs/docs/arch-guide/arc-screen-flow.md",
  "/mnt/user-data/outputs/docs/product-design.md",
  "/mnt/user-data/outputs/files_reify_YYYYMMDD_hhmm.zip",
])
```

### 2.2 提示するファイルの選び方

| 変更の種類 | 個別に提示するもの |
|---|---|
| 新規作成した md | **必ず全部** |
| 大きく書き換えた md | 必ず提示する |
| 索引への1行追加など軽微な修正 | 省いてよい。zip には含める |
| ソースコード | 提示しない。zip のみ |

**5ファイルを超えるときは、新規作成分と主要な修正分に絞る。** 全部並べると
どれを見ればよいか分からなくなる。

### 2.3 zip の作り方

- 名前は `files_reify_YYYYMMDD_hhmm.zip`（**JST**）
- **リポジトリのルートからの相対パス**を保つ。展開して `Copy-Item` するだけで配置できる形にする
- 中身は `git status --porcelain` が返した変更ファイルのみ。無関係なファイルを混ぜない
- 前回の zip が `/mnt/user-data/outputs/` に残っていれば削除する。取り違えを防ぐため

## 3. コミットとプッシュの手順

### 3.1 形式

**番号ごとに1つのコピー可能なコマンドブロック**にする。1ブロックに複数行を詰めない。
各ブロックの直前に、何をするかを太字1行で書く。

### 3.2 必ず含める段

| 順 | 段 | 理由 |
|---|---|---|
| 1 | リポジトリのルートへ移動 | 別の場所で実行する事故を防ぐ |
| 2 | `git pull; git status` | 作業ツリーが空であることを確認 |
| 3 | `Expand-Archive` | zip を `$env:TEMP` へ展開 |
| 4 | `Copy-Item` | リポジトリへコピー |
| 5 | **`git status --short`** | **コピーされたことを確認。空なら4をやり直す** |
| 6〜 | 内容の検証 | 変更に応じた確認（第3.3章） |
| — | `git add` | 変更したファイルを明示的に列挙する |
| — | `git status --short` | ステージされたことを確認 |
| — | `git commit` | メッセージは第3.4章 |
| — | `git push` | |
| — | SHA 一致の確認 | `git log --oneline -2; git log --oneline -2 origin/main` |
| — | 一時フォルダの片付け | `Remove-Item ... -Recurse -Force` |

**第5段を `Copy-Item` の直後に置くこと。** 後ろに置くと、コピーを飛ばしたことに
気づくのが遅れる。過去に実際に起きている。

### 3.3 内容の検証の段

変更に応じて入れる。**期待値を必ず書く**（「7 になる」「何も出力されない」など）。

| 変更 | 入れる確認 |
|---|---|
| 文書のみ | `git status --short \| Select-String "backend/\|frontend/"` が**空** |
| Python | `pytest` / `ruff check backend` / `black --check backend` |
| Python の docstring 追加 | AST 比較（`AGENTS.md` §7.1.8）。**`git show` を使い `git stash` は使わない** |
| フロントエンド | `npm --prefix frontend run build` |
| Mermaid を含む md | 図とトグルの数（`^```mermaid$` は**描画用とソース用の両方**を数える） |
| 新規ファイル | ファイル数の確認 |

⚠️ **`--check` だけで終わらせない。** `black` は整形を実行してから確認する。

### 3.4 コミットメッセージ

- **英語**。Conventional Commits（`docs:` `feat:` `fix:` `style:` `build:` `refactor:`）
- 本文は `-m` の2つ目。**2〜3文かつ50語以内**。1文は20語程度
- **差分やコミットした文書に書いてあることを繰り返さない。** なぜそうしたかを書く

## 4. 確認する URL

### 4.1 形式

**1つの URL につき1ブロック。** コピーボタンでそのままブラウザへ貼れるようにする。
直前に何のファイルかを太字の見出しで添える。

### 4.2 並べる順序と件数

1. 新規作成した文書
2. 大きく変更した文書
3. 索引（`docs/README.md`、ルート `README.md`）
4. コミットの差分

**5〜8件に収める。** 多いと開かれない。

### 4.3 URL の作り方

| 対象 | 形 |
|---|---|
| ファイル | `https://github.com/ChestnutForest/paper-repro/blob/main/<path>` |
| フォルダ | `.../tree/main/<path>` |
| 履歴 | `.../commits/main` |
| 特定のコミット | `.../commit/<sha>` |
| **README の見え方** | **`https://github.com/ChestnutForest/paper-repro`**（トップ。実際に描画される形で見える） |

一次資料を根拠にした場合は、**その原典の URL も最後に添える。**

## 5. 実行結果の検証

利用者が VS Code や PowerShell の出力を貼って「検証して」と言ったときの手順。

### 5.1 手順

| 順 | すること |
|---|---|
| 1 | **期待値との照合。** 直前に示した手順の期待値と実際の出力を1つずつ突き合わせ、表で示す |
| 2 | **飛ばされた手順の検出。** コマンドの並びを手順と照合する。飛ばしがあれば、それが後続の結果をどう変えたかまで説明する |
| 3 | **自分の期待値の誤りを疑う。** 食い違ったら、まず自分の数え方や予告が正しいかを確認する |
| 4 | **数値の内訳を説明する。** 件数が違うときは、なぜその数になったかを示す |
| 5 | **削除行の判別。** 置き換えなのか消失なのかを述べる |
| 6 | **コード波及の確認。** 文書のみのはずが backend/ frontend/ に及んでいないか |
| 7 | **次の手順。** 途中なら残りのコマンド、完了なら確認 URL と次の一手 |

### 5.2 守ること

- **利用者の操作ミスと決めつけない。** 自分の期待値が誤っていた場合は、そう明言し、
  正しい確認方法を示す。実際に何度も自分側の誤りだった
- **簡潔にする。** すべて正常なら表1つと数行。問題があるときだけ詳しく書く
- 期待値が誤っていたと分かったら、**正しい確認コマンドをその場で提示する**

### 5.3 よくある食い違いと原因

| 症状 | 多くの場合の原因 |
|---|---|
| `git status --short` が空 | `Copy-Item` を飛ばした |
| `nothing to commit` | 既にコミット済み、または上と同じ |
| Mermaid の数が予告の2倍 | 描画用とソース用の両方を数えている |
| 仕様やファイルの件数が予告と違う | **自分が手で数えた数が古い。** 実データを数え直す |
| `black --check` が失敗したまま commit | `--check` は直さない。整形を先に実行する |

---

## 6. やってはいけないこと

- ファイルを作って**提示しない**。利用者はダウンロードできない
- zip だけを提示し、**md を個別に提示しない**。中身をチャットで確認できない
- 複数のコマンドを1ブロックに詰める。コピーが煩雑になる
- 期待値を書かずに確認コマンドだけ並べる。何を見ればよいか分からない
- **手で数えた件数をそのまま書く。** 必ず実データを数える
- 他のプロジェクト（Processloop など）にこの形式を使う
