## 1. 本書の位置づけ

### 1.1 なぜ USDM で書き直すか

[`requirements.md`](requirements.md) v0.2 の要求文は、**何を作るか**を述べているが、
USDM が要求に担わせる3つの役割を果たしていない。

| 要求の3つの役割（REF-17 2.2.2） | v0.2 の要求文の状態 |
|---|---|
| 求められている**振る舞い**を見せて動きを感じさせる | 「提供するものとする」など、名詞形・静的な表現が多い |
| 求められている**範囲**を示す | どこから始まりどこで終わるかが曖昧 |
| 要求に含まれる**全ての動詞と目的語**を見せる | 動詞が省かれ、仕様を引き出す手がかりが少ない |

USDM は、要求を**振る舞い**として動詞形で書き、その動詞ひとつひとつに仕様を対応させる。
これにより**仕様の漏れに気づきやすくなる**（REF-17 3.1）。

### 1.3 記法の約束

USDM の基本フォーマット（REF-17 4.1）に従い、次の5項目で書く。

| 項目 | 内容 |
|---|---|
| **カテゴリ名** | 要求のグループ名と記号 |
| **要求** | 振る舞いを動詞形で。要求 ID を付ける |
| **理由** | その要求が生じた背景 |
| **説明** | 要求への補足 |
| **仕様** | 仕様グループごとに、具体的な処理内容。仕様 ID を付ける |

**ID の付け方**（REF-17 4.2.5・4.4.4）

- 要求 ID: 既存の `REQ-Cxx` をそのまま使う。**新しい体系を作らない。**
  番号を振り直すと、決定台帳3冊と分析文書19本の追跡が切れるため。
- 下位要求 ID: `REQ-Cxx-Rn`（例: `REQ-C01-R1`）
- 仕様 ID: `REQ-Cxx-Rn.mm`（例: `REQ-C01-R1.10`）。10刻みで振り、間に挿入できるようにする

**避ける表現**（REF-17 4.5.3〜4.5.5）

- 「等」「etc」— 現時点で確定できることは書き切る。未確定なら合意時期を書く
- **否定表現** — 「〜しない」の裏に隠れた条件分岐がある。`else` を必ず書く
- **ペースト作文** — 一部だけ違う仕様をコピーで作らない。差異が読み取れなくなる

## 2. REQ-C01 読解と再現実装の二経路【完全展開】

**フェーズ0で実装中のため、本要求のみ仕様まで展開する。**

### 2.1 上位要求

| カテゴリ | 経路選択（`COURSE`） |
|---|---|
| **要求 `REQ-C01`** | 利用者が**開始時に**読解コースか再現実装コースを**選び**、選んだ経路に応じて工程を**進め**、作業の途中でも経路を**切り替え**、切り替えても既存の成果物を**保持する**。 |
| **理由** | 論文を読み解く力を育てたい利用者と、動くコードを得たい利用者では、必要な工程が違う。片方を主・他方を従にすると、従にした側の利用者が使えない。また、読んでいるうちに実装したくなる（逆もある）ため、途中で乗り換えられないと最初の選択が重荷になる。 |
| **説明** | 経路は `Project.course` として保持する。**NOT NULL・既定値なし**とし、未選択の状態を存在させない。切り替えは何度でも可能。実装単位は `F-15`（画面）と `F-02`（工程表示）。 |

**動詞の数を数える。** 「選ぶ」「進める」「切り替える」「保持する」の4つ。
8個未満なので、**分割しないでよい**（REF-17 4.2.2）。ただし振る舞いの局面が
「開始時」「進行中」「切り替え時」に分かれるため、**時系列分割**（同 4.2.4）で
3つの下位要求へ分ける。局面ごとに仕様の性質が異なるためである。

### 2.2 下位要求 `REQ-C01-R1` 開始時に経路を選ぶ

| 項目 | 内容 |
|---|---|
| **要求** | 利用者が新規作成を**始めた**とき、2つの経路とそれぞれで到達できる成果物を**示し**、どちらか一方を**選ばせ**、選択と論文の URL を受け取って**プロジェクトを作る**。 |
| **理由** | 選ばないまま作れると、利用者は自分がどちらの経路にいるか分からないまま作業を始めてしまう。最初に選ばせることで、以降の画面が何を見せるべきかも決まる。 |
| **説明** | 経路の選択肢は `reading`（読解・学習）と `reproduction`（再現実装）の2つ。3つ目は当面設けない。 |

**＜経路の提示＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R1.10` | 新規作成の画面に、`reading` と `reproduction` の2つを、同時に見える形で並べて表示する。 |
| `REQ-C01-R1.20` | 各経路の下に、その経路で到達できる成果物を1行で表示する。`reading` は「spec と仮定台帳」、`reproduction` は「実行可能なノートブックと照合レポート」とする。 |
| `REQ-C01-R1.30` | 後から切り替えられる旨を、選択肢の近くに表示する。 |
| `REQ-C01-R1.40` | 表示する文言は `next-intl` の翻訳キーで参照し、`ja` `en` `zh-TW` の3ファイルすべてに登録する。 |

**＜経路の選択＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R1.50` | 初期状態ではどちらも選択されていない状態にする。 |
| `REQ-C01-R1.60` | 一方を選ぶと、他方の選択は解除される。両方を同時に選択できない。 |
| `REQ-C01-R1.70` | どちらも選択されていない間は、作成の操作を実行できない状態にする。 |

**＜プロジェクトの作成＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R1.80` | `POST /api/v1/projects` へ、論文の URL と選択した経路の2つを必須の項目として送る。 |
| `REQ-C01-R1.90` | 経路を欠いた要求を受け取った場合、HTTP 422 を返し、プロジェクトを作らない。 |
| `REQ-C01-R1.100` | 経路が `reading` と `reproduction` のいずれでもない値だった場合も、HTTP 422 を返し、プロジェクトを作らない。 |
| `REQ-C01-R1.110` | 作成に成功した場合、`phase` を `created`、`status` を `idle` として保存し、HTTP 201 と作成したプロジェクトを返す。 |

> **`REQ-C01-R1.90` と `.100` を分けて書いた理由。**
> 「経路が正しくなければ 422」と1行で書くと、**欠落と不正値のどちらも指すのか読み取れない。**
> USDM が禁じる曖昧さにあたるため、条件ごとに行を分けた（REF-17 4.5.4）。

### 2.3 下位要求 `REQ-C01-R2` 経路に応じて工程を進める

| 項目 | 内容 |
|---|---|
| **要求** | 承認ゲートで工程を進めるとき、そのプロジェクトの経路を**参照し**、`reproduction` なら実装以降の工程へ**進め**、`reading` なら読解の工程に**留め**、留めた理由を利用者に**示す**。 |
| **理由** | 読解コースの利用者に実装工程を見せても、使わない画面が並ぶだけで迷わせる。ただし「進めない」とだけ表示すると故障と区別がつかないため、経路が理由であることを示す必要がある。 |
| **説明** | 工程の遷移そのものの規則は [`arch-guide/arc-datamodel.md`](arch-guide/arc-datamodel.md) 3.4 に従う。本要求は、そこへ経路による条件を重ねる。 |

**＜経路の参照＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R2.10` | 承認ゲート②（`spec:finalize`）の実行時に、対象プロジェクトの `course` を読み取る。 |
| `REQ-C01-R2.20` | 工程の遷移表には経路の条件を含めない。経路による判定は、ゲートのエンドポイント側で行う。 |

**＜再現実装コースの進行＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R2.30` | `course` が `reproduction` の場合、`phase` を `reading` から `implementing` へ進める。 |

**＜読解コースの滞留＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R2.40` | `course` が `reading` の場合、`phase` を `reading` のまま保つ。 |
| `REQ-C01-R2.50` | 同じ場合に HTTP 400 を返し、応答の本文に「読解コースのため実装工程へ進まない」旨と、現在の経路の値を含める。 |
| `REQ-C01-R2.60` | 画面に、進めなかった理由として経路を表示する。故障や権限の不足と区別できる文言にする。 |

**＜読解コースの終端＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R2.70` | `course` が `reading` の場合でも、成果物（spec と仮定台帳）の出力は実行できる状態にする。 |

### 2.4 下位要求 `REQ-C01-R3` 経路を切り替えても成果物を保持する

| 項目 | 内容 |
|---|---|
| **要求** | 利用者が経路の切り替えを**指示した**とき、新しい経路を**記録し**、切り替えた時刻を**残し**、既存の成果物をすべて**保持したまま**、切り替え後の経路に応じた画面を**表示する**。 |
| **理由** | 切り替えのたびに作業が失われるなら、利用者は切り替えを避ける。避けられる機能は無いのと同じである。保持を保証して初めて、途中で乗り換えられるという価値が成立する。 |
| **説明** | 保持の対象は spec、仮定台帳、注釈、自己説明、承認履歴、コスト記録、サニティ実行結果、照合結果。切り替えは `POST /api/v1/projects/{project_id}/course` で行う。 |

**＜切り替えの記録＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R3.10` | 新しい経路を `Project.course` へ保存する。 |
| `REQ-C01-R3.20` | 切り替えた時刻を `Project.course_changed_at` へ保存する。 |
| `REQ-C01-R3.30` | 切り替えを承認履歴（`Approval`）へ1件記録し、切り替え前と切り替え後の経路の両方を含める。 |
| `REQ-C01-R3.40` | 切り替え前と同じ経路が指定された場合も、要求として受理し、HTTP 200 と現在のプロジェクトを返す。この場合は `course_changed_at` と承認履歴を更新しない。 |

**＜成果物の保持＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R3.50` | 切り替えの前後で、spec、仮定台帳、注釈、自己説明、承認履歴、コスト記録の各件数と内容を同一に保つ。 |
| `REQ-C01-R3.60` | `reproduction` から `reading` へ切り替えた場合、サニティ実行結果と照合結果を削除せず、参照できる状態で残す。 |
| `REQ-C01-R3.70` | `reading` から `reproduction` へ切り替えた場合、既存の spec と仮定台帳をそのまま引き継ぎ、実装工程の入力として使う。 |
| `REQ-C01-R3.80` | 切り替えによって `phase` と `status` を変更しない。 |

**＜切り替え後の表示＞**

| 仕様 ID | 仕様 |
|---|---|
| `REQ-C01-R3.90` | 切り替え後、画面に表示している経路の名称を新しい経路へ更新する。 |
| `REQ-C01-R3.100` | 切り替え後、`reproduction` を選んだ場合は実装工程への導線を表示し、`reading` を選んだ場合はその導線を表示しない。 |

> **`REQ-C01-R3.40` を書いた理由。**
> 「同じ経路が指定されたら」という条件は、要求文にも受入基準にも現れない。
> しかし実装では必ず起き、書かないと**時刻と履歴が無意味に更新される**か、
> **エラーを返して利用者を戸惑わせる**かのどちらかになる。
> USDM の「隠れた IF 文」にあたる（REF-17 4.5.4）。

### 2.5 動詞と仕様の対応（漏れの検査）

上位要求の動詞ひとつひとつに、仕様が対応しているかを確かめる（REF-17 3.1 ①）。

| 上位要求の動詞 | 下位要求 | 対応する仕様グループ | 仕様の数 |
|---|---|---|---|
| 選ぶ | `R1` | 経路の提示（4）、経路の選択（3）、プロジェクトの作成（4） | 11 |
| 進める | `R2` | 経路の参照（2）、再現実装コースの進行（1）、読解コースの滞留（3）、読解コースの終端（1） | 7 |
| 切り替える | `R3` | 切り替えの記録（4）、切り替え後の表示（2） | 6 |
| 保持する | `R3` | 成果物の保持（4） | 4 |
| | | **合計** | **28** |

**28仕様。対応の無い動詞は無い。**

> 「切り替える」と「保持する」は、どちらも `R3` に属する。
> 切り替えという1つの操作に対して、**記録する側面**と**失わせない側面**があり、
> 仕様グループとしては分けたほうが漏れに気づきやすいためである。

**数の検証。** 仕様の定義数は次で数える。表の行頭に限定しないと、
本文中の参照まで数えてしまう（実際 31 件になる）。

```powershell
(Select-String -Path docs\requirements-usdm.md -Pattern "^\| ``REQ-C01-R\d\.\d+``" -AllMatches).Matches.Count
```

## 3. 他の要求【要求と理由まで】

以下は USDM の要求文へ書き直したもの。**仕様は未展開である。**
実装に着手するフェーズで、`REQ-C01` と同じ粒度まで展開する。

### 3.1 学習支援（`LEARN`）

| ID | 要求（振る舞い） | 理由 |
|---|---|---|
| `REQ-C02` | 利用者が理解できない語や数式に**出会った**とき、その語の説明を**示し**、求めに応じて説明を**深め**、説明の根拠となる一次資料の箇所へ**戻す**。 | 前提知識を利用条件にすると、学びたい人ほど使えなくなる。説明を読んで納得した気になるだけでは理解に至らないため、必ず原典へ戻せる必要がある。 |
| `REQ-C04` | 主要な概念ごとに、理論の解説を**示し**、具体例と反例を**構成させ**、確認問題を**出し**、利用者の自己説明を**受け取り**、根拠を添えたフィードバックを**返す**。 | 読んだだけでは理解の程度が分からない。自分の言葉で説明できて初めて理解といえるが、その判定を流暢さで行うと誤る。根拠を示して差を埋める。 |

### 3.2 論文の取り込み（`INTAKE`）

| ID | 要求（振る舞い） | 理由 |
|---|---|---|
| `REQ-C03` | 利用者が論文を**指定した**とき、入手元に応じたアダプタで本文とメタ情報を**取り込み**、版と公開状態を**記録し**、取り込めなかった項目を**そのまま空にして示す**。 | 最初は arXiv だけで足りるが、後から PDF や出版社ページを足すたびに中核を書き換えるのでは持たない。また、不明を推測で埋めると、後の判断が誤った前提の上に載る。 |

### 3.3 再現実装（`REPRO`）

| ID | 要求（振る舞い） | 理由 |
|---|---|---|
| `REQ-C05` | 公式実装を**読み解き**、コードとノートブックを**生成し**、隔離した環境で**実行し**、サニティチェックを**通し**、論文の値と**照合する**。 | 手元で動かなければ再現したとはいえない。ただし第三者のコードをそのまま実行するのは危険なため、隔離を挟む。サニティを通す前の照合は、誤った成功を通してしまう。 |
| `REQ-C06` | 実行を要求されたとき、対象の言語に応じたサンドボックスを**選び**、危険な操作を**検出し**、人間の承認を**求め**、承認を得てから**実行する**。 | 承認を迂回できる経路が1つでもあると、迂回できない保証が崩れる。言語を増やすたびに隔離の条件も変わるため、言語ごとに用意する。 |

### 3.4 批判的検証（`VERIFY`）

| ID | 要求（振る舞い） | 理由 |
|---|---|---|
| `REQ-C07` | 主張ごとに情報源を**集め**、属性と一致状況を**記録し**、食い違いを**そのまま並べて示し**、人間が採用した根拠を**受け取って保存する**。 | 矛盾を自動で解消すると、解消の妥当性を後から検証できない。どちらを採ったかではなく、なぜ採ったかが残らなければ意味がない。 |
| `REQ-C08` | 原文から成果物までの各段階を**記録し**、生成の条件と変換の内容を**添え**、支持と反証の関係を**結び**、どちらの方向からも**辿れるようにする**。 | 成果物だけが残ると、それが論文のどこから来たのか分からなくなる。逆に、論文のある記述が最終的に何へ影響したかも追えなければ、修正の影響範囲が読めない。 |
| `REQ-C10` | 重要な主張を**区分し**、前提と成立範囲を**分け**、支持例と反例を**作らせ**、矛盾を**示し**、人間の最終判断を**受け取る**。 | 論文の主張が正しいかを LLM だけで確定させると、誤りを誤りのまま通す。人間が判断するための材料を揃えることが機能であり、判断そのものを代行しない。 |

### 3.5 蓄積と対話（`ARCHIVE`）

| ID | 要求（振る舞い） | 理由 |
