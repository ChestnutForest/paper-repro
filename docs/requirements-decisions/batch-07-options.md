## 1. 選択方法と前提

1〜5から1つだけ選択する。

- 選択肢1〜4: 採用後の文書構造が異なる具体案
- 選択肢5: LLMによる自動作成
- どの選択肢でも、重要な判断、外部送信、公開およびPhase末では人間の明示的な承認を必要とする
- LLMの出力だけで論文の真偽、回答の正しさ、要求の確定を決定しない

### 1.1 なぜ今決めるのか

[`../requirements-usdm.md`](../requirements-usdm.md) 第4章が4件の未解決を挙げているが、
**そのうち本件だけが展開の作業そのものを止める。**

| 未解決事項 | いつ決めるか |
|---|---|
| 正本をどちらにするか | **展開完了後でよい。** 同書38〜40行が「展開が済んだ時点で判断する」と定めている |
| **サブ要求15件の扱い** | ⚠️ **今決める。** 下記1.2節 |
| 展開の順序 | 本件の決定後、展開に入る直前でよい |
| 非機能要求の書き方 | 展開の後半でよい。手戻りが小さい |

### 1.2 ⚠️ 何が衝突するのか

`REQ-C01` の展開では問題が起きなかった。**`REQ-C01` に既存サブ要求が無かったからである。**

しかし他の要求には既存サブ要求がある。

| メイン要求 | 既存サブ要求 |
|---|---|
| `REQ-C02` | `REQ-C02-S01` |
| `REQ-C03` | `REQ-C03-S01` |
| `REQ-C04` | `REQ-C04-S01`、`REQ-C04-S02` |
| `REQ-C05` | `REQ-C05-S01`、`REQ-C05-S02`、`REQ-C05-S03` |
| `REQ-C07` | `REQ-C07-S01` |
| `REQ-C09` | `REQ-C09-S01`〜`S03` |
| `REQ-C10` | `REQ-C10-S01`〜`S04` |

`REQ-C05` を展開すると、**同じ要求の下に `S01`〜`S03` と `R1`〜`Rn` が並ぶ。**

⚠️ **両者は別の概念である。**

| | 既存サブ要求（`Sxx`） | USDM 下位要求（`Rn`） |
|---|---|---|
| 出所 | 一次資料の分析と5択 | メイン要求を振る舞いへ分解した結果 |
| 粒度 | メイン要求を具体化する要求 | 仕様を導くための中間層 |
| 下位 | 持たない | **仕様（`Rn.10` など）を持つ** |
| 受入基準 | 持つ | 持たない（仕様が代わる） |

**`REQ-C05-S01` は「論文箇所と実装を双方向に対応付ける」という要求である。**
これは `REQ-C05` の下位要求として振る舞いを分解したものではなく、
**独立した要求として5択を経て確定したもの**である。

## 2. サブ要求と下位要求をどう関係づけるか

決めることは、**USDM 展開後の文書構造**である。

| 番号 | 選択肢 | 採用後の構造 | 長所 | 注意点 |
|---:|---|---|---|---|
| 1 | **併存させる**（構造を変えない） | `REQ-C05` の下に `S01`〜`S03` と `R1`〜`Rn` が並ぶ。両者を別の節として書く | 既存のIDを変えない。5択の記録・突合表・トレーサビリティ・マトリクスがそのまま使える | **同じ要求の下に2種類の下位構造が並ぶ。** 読み手が「`S01` と `R1` はどう違うのか」を毎回考えることになる。⚠️ **今日ずっと直してきた二重管理に近い状態** |
| 2 | **サブ要求を下位要求へ昇格させる** | `REQ-C05-S01` を `REQ-C05-R1` として扱い、その下に仕様を展開する。`Sxx` の記法は廃止 | 構造が1種類になる。USDM の階層（要求→下位要求→仕様）に統一される | **既存IDが全て変わる。** 突合表・5択の記録・`arc-datamodel-list.md` の対応要求欄・トレーサビリティ・マトリクスの書き換えが要る。⚠️ **`REQ-C05-S01` は今日時点で `B-02`・`B-03`・`N-06` へ対応づけられている** |
| 3 | **サブ要求を下位要求の1つとして残し、記法は保つ** | `REQ-C05-S01` はIDを保ったまま、USDM 下位要求と同じ階層に置く。仕様は `REQ-C05-S01.10` のように付番する。新規の下位要求だけ `Rn` を使う | 既存IDが変わらない。階層は1種類になる | 同じ階層に `Sxx` と `Rn` の2つの記法が混在する。**由来の違いは残るが、構造上は等価として扱う** |
| 4 | **メイン要求から展開し、サブ要求は受入基準の出所として参照する** | USDM 展開は `REQ-C05` から直接 `R1`〜`Rn` を導く。`Sxx` は展開の入力（何を仕様に落とすかの材料）として参照するが、USDM の階層には現れない | USDM の構造が純粋になる。**`REQ-C01` と同じ形で全要求を展開できる** | `Sxx` が USDM 側に現れないため、**サブ要求が仕様へ落ちたかを検査できない。** 対応づけの表を別に持つ必要がある |
| 5 | LLMによる自動作成 | LLMが構造案、理由、影響範囲を作成する | 選択肢1〜4の枠に収まらない案が出る可能性がある | **本件は全要求展開の前提となる構造決定である。** LLM の案をそのまま採るのは危険が大きい |

### 2.1 選択結果

**選択肢3を採用する**（2026年9月3日）。

既存サブ要求はIDを保ったまま、USDM 下位要求と同じ階層に置く。
仕様は `REQ-C05-S01.10` のように付番し、新規の下位要求だけ `Rn` を使う。

### 判断の経緯

**選択肢1と2は先に落ちた。**

| 選択肢 | 落とした理由 |
|---|---|
| 1 併存 | 同じ要求の下に2種類の下位構造が並ぶ。**二重管理そのものである** |
| 2 昇格 | `REQ-C05-S01` は既に `B-02`・`B-03`・`N-06`、突合表4件、5択記録6件、`arc-datamodel-list.md`、トレーサビリティ・マトリクスから参照されている。**展開に着手する前の作業として大きすぎる** |

**決め手は `REQ-C02-S01` である。**

3.3節のとおり、既存サブ要求15件は性格が一様でない。
特に `REQ-C02-S01`（既読資料の横断保持）は**メイン要求 `REQ-C02` に無い機能を足している。**
`REQ-C02` は「前提知識を段階的に説明し、一次資料へ戻せる」ことを求めるが、
既読資料の横断保持はそこから導けない。

⚠️ **選択肢4を採ると、この要求が USDM の階層から消える。**
`REQ-C02` から下位要求を導いても既読資料の保持は出てこない。
対応表で別途追跡することになるが、**要求仕様書を読んだだけでは機能の存在が分からない。**

選択肢3ならIDを保ったまま同じ階層に置けるため、`REQ-C02-S01.10` のように仕様を展開できる。
**要求仕様書だけで全体が読める。**

### 記法が2つ混在する点について

選択肢3の弱みは `Sxx` と `Rn` が混在することだが、**由来が違うものに違う記号を使うのは情報であって欠陥ではない。**

| 記号 | 由来 |
|---|---|
| `Sxx` | 一次資料の分析と5択を経て確定した要求 |
| `Rn` | メイン要求を振る舞いへ分解した中間層 |

記号が違うことで、その要求がどこから来たかが読み取れる。

### 付随して定めた1点

**仕様の付番規則。** 既存サブ要求は `REQ-Cxx-Sxx.10`、新規下位要求は `REQ-Cxx-Rn.10` とする。
いずれも10刻みとし、後から挿入できるようにする（`REQ-C01-R1` の実績に倣う）。

## 3. 選択にあたっての判断材料

### 3.1 影響を受ける文書

| 文書 | 選択肢1 | 選択肢2 | 選択肢3 | 選択肢4 |
|---|---|---|---|---|
| `requirements.md` 第3章 | 変更なし | **ID全面書き換え** | 変更なし | 変更なし |
| `requirements-usdm.md` | 構造を2種類持つ | 統一 | 統一 | 統一 |
| `traceability-matrix.md` | 変更なし | **書き換え** | 追記 | **対応表を新設** |
| 突合表4件・5択記録6件 | 変更なし | **書き換え** | 変更なし | 変更なし |
| `arc-datamodel-list.md` の対応要求欄 | 変更なし | **書き換え** | 変更なし | 変更なし |

⚠️ **選択肢2の影響は広い。** `REQ-C05-S01` は既に実装単位・エンティティ・突合表から参照されている。

### 3.2 `REQ-C01` の実績が示すこと

`REQ-C01` は下位要求3件・28仕様へ展開できた。**既存サブ要求が無かったため、選択肢4と同じ形で書けた。**

つまり**選択肢4は既に1件の実績がある。** 他の要求で同じ形を採るなら、
`REQ-C01` の展開をやり直す必要が無い。

⚠️ ただし `REQ-C01` にサブ要求が無かったのは偶然である。
**サブ要求を持つ要求で同じ形が成立するかは、まだ確かめていない。**

### 3.3 サブ要求の性格の違い

既存サブ要求15件は、性格が一様ではない。

| 例 | 性格 |
|---|---|
| `REQ-C05-S01`（論文箇所と実装の双方向対応） | **独立した要求に近い。** 受入基準も長大 |
| `REQ-C05-S02`（乱数種・試行回数の記録） | メイン要求の一側面を具体化したもの |
| `REQ-C02-S01`（既読資料の横断保持） | **メイン要求に無い機能を足している** |

**一律の扱いが適切とは限らない。** 選択肢を選んだ後、個別に例外を認めるかの判断が要りうる。

## 4. 選択後に行うこと

1. 選択結果と理由を本書へ記録する。
2. [`../requirements-usdm.md`](../requirements-usdm.md) 第4章の該当項目を解決済みにする。
3. **展開の順序**を決める（第4章の残る未解決）。
4. 展開に着手する。1回の作業単位は**下位要求1件**とする（`REQ-C01-R1` の実測で約35行）。
5. 非機能要求（`N-01`〜`N-10`）の扱いは、展開の後半で決める。

### 4.1 展開の見積り

`REQ-C01` は下位要求3件・28仕様・約155行だった。
残る10要求を同じ粒度で展開すると、**約1,550行・仕様280件**になる見込み。

⚠️ **要求ごとに複雑さが違う。** `REQ-C03`（取り込み）は単純だが、
`REQ-C10`（批判的検証）はサブ要求4件を抱えるため `REQ-C01` より大きくなる。
