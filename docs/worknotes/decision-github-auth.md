# 決定記録：GitHub API の認証を必須とする

- 対象プロダクト: `paper-repro`
- 文書種別: 設計判断の記録
- 決定日: 2026年8月31日
- 契機: [`../arch-guide/arc-interface-list.md`](../arch-guide/arc-interface-list.md) 6章の未決事項
- 影響先: `IF-02`（公式実装の探索）、`BR-13`（未整備）

## 1. 何が問題か

GitHub REST API のレート制限は、認証の有無で**83倍の差**がある。

| 認証 | 制限 | 単位 |
| --- | --- | --- |
| 未認証 | **60 リクエスト/時** | IPアドレス |
| 認証済み | **5,000 リクエスト/時** | アカウント |

`IF-02` は1論文あたり複数回の呼び出しを要する。**未認証では実用に耐えない。**

⚠️ **未認証はIPアドレス単位である。** 同じ回線から複数の利用者が使えば、
60回を共有することになる。個人利用でも枯渇しうる。

## 2. `paper-repro` が必要とする権限

**公開リポジトリの読み取りだけ**である。

| 操作 | 必要性 |
| --- | --- |
| 公開リポジトリの検索・取得 | **必要**（`REQ-C05-S01`） |
| 非公開リポジトリへのアクセス | 不要 |
| 書き込み（Issue、PR、Push） | 不要 |
| 組織情報の取得 | 不要 |

⚠️ **必要な権限が最小である。** 認証方式の選定は、この範囲に絞って行う。

## 3. 検討した選択肢

| 案 | 制限 | 権限の範囲 | 評価 |
| --- | --- | --- | --- |
| A | 未認証のまま | 60/時 | 公開データのみ | 実用に耐えない |
| B | **fine-grained PAT** | **5,000/時** | **公開リポジトリの読み取り** | **採用** |
| C | classic PAT | 5,000/時 | **アカウントの全リポジトリ** | 権限が過剰 |
| D | GitHub App | より高い | 設定による | 個人開発には過剰 |

### 3.1 案Bを採用する理由

**fine-grained PAT は、既定で公開リポジトリの読み取り権限のみを持つ。**
`paper-repro` が必要とする範囲と一致する。

読み取り専用の公開データを扱う用途では、fine-grained PAT が適切であり、
GitHub App より設定が簡単である。

| 観点 | 内容 |
| --- | --- |
| 制限 | 5,000/時。`IF-02` の用途に十分 |
| 権限 | **既定で公開リポジトリの読み取りのみ** |
| 設定 | Settings → Developer settings → Personal access tokens → Fine-grained |
| 有効期限 | 1〜366日。**無期限にできない** |

### 3.2 案Cを採らない理由

**classic PAT の `repo` スコープは、アカウントがアクセスできる全リポジトリに及ぶ。**
非公開リポジトリも含まれる。

`paper-repro` は公開リポジトリの読み取りしかしない。**過剰な権限を持たせる理由がない。**

⚠️ **トークンが漏れた場合の被害範囲が違う。** fine-grained なら公開データの読み取りだけだが、
classic なら非公開リポジトリの内容も読まれうる。

### 3.3 案Dを採らない理由

GitHub App は、ユーザーの代理として動作する場合や、より高い上限が要る場合に適する。

`paper-repro` は**個人開発の単一利用者**であり、いずれも該当しない。設定の複雑さに見合わない。

## 4. 決定

**`IF-02` は fine-grained personal access token による認証を必須とする。**

| 項目 | 内容 |
| --- | --- |
| 認証方式 | fine-grained personal access token |
| 権限 | 公開リポジトリの読み取りのみ（既定） |
| ヘッダ | **`Authorization: Bearer <token>`** |
| 制限 | 5,000 リクエスト/時 |
| 有効期限 | 1〜366日 |

### 4.1 ⚠️ 認証ヘッダの形式に注意

**`Authorization: token <token>` 形式では 403 が返る事例がある。**
fine-grained PAT では **`Bearer`** を使う。

現行のドキュメントと例も `Bearer` を用いている。

### 4.2 ⚠️ トークンの保管

`BR-08`（適用規則）は「シークレット、個人情報、機密情報を成果物へ混入させない」と定める。

| 守ること | 内容 |
| --- | --- |
| 保管先 | 環境変数。`.env` はGit管理外（`.gitignore` 済み） |
| 禁止 | **コード、設定ファイル、成果物、ログへの記載** |
| 公開時 | `REQ-C11` の外部送信でトークンを含めない |

⚠️ **GitHub は公開リポジトリ内のトークンを自動失効させる**（secret scanning）。
ただし非公開リポジトリでは働かない。**混入させないことが前提である。**

### 4.3 ⚠️ 有効期限が切れる

**fine-grained PAT は無期限にできない**（最長366日）。また、12か月未使用で自動削除される。

| 事象 | 挙動 | 対処 |
| --- | --- | --- |
| 期限切れ | 401 が返る | 利用者へ再発行を促す |
| 未設定 | 60/時に落ちる | 動作はするが遅い |

⚠️ **期限切れを「GitHub の障害」と誤って表示しない。** `BR-07`（メッセージ）に従い、
「何が失敗したか」「利用者が次にできること」を含める。

## 5. トークンが無い場合の扱い

**トークンを必須とするが、無くても動作は止めない。**

| 状態 | 挙動 |
| --- | --- |
| トークンあり | 5,000/時で動作 |
| **トークンなし** | **未認証で動作（60/時）。制限が低い旨を表示** |
| トークンが無効 | 401。再発行を促す |

理由は、**初回利用の障壁を下げるため**である。トークンの取得は数分かかる。
まず動かして試し、必要になってから設定する順序を許す。

⚠️ **ただし「必須」の位置づけは変えない。** 実用にはトークンが要る。
未認証は試用のための縮退動作である。
