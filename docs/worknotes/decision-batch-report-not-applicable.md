# 決定記録：バッチ編・帳票編を対象外とする

- 対象プロダクト: `paper-repro`
- 文書種別: 設計判断の記録
- 決定日: 2026年9月1日
- 契機: 外部インタフェース編の完了により、残る2編の扱いを決める必要が生じたこと
- 影響先: [`../arch-guide/arc-artifact-order.md`](../arch-guide/arc-artifact-order.md) 5節、
  ルート [`../../README.md`](../../README.md) の設計工程表

---

## 1. 何を決めたか

**REF-16 のバッチ編と帳票編は、本プロダクトの対象外とする。**

設計工程の表では `⬜`（未着手）ではなく **`—`（非該当）** と表す。
空欄のまま残すと、次に見た人が「これから作るもの」と誤解するためである。

## 2. バッチ編を対象外とする根拠

REF-16 のバッチ編は、**定時・定期に自動起動される一括処理**を扱う。

### 2.1 該当する処理が存在しない

| 確認対象 | 結果 |
| --- | --- |
| [`../requirements.md`](../requirements.md)・[`../requirements-usdm.md`](../requirements-usdm.md) | 定期実行・定時起動・スケジュール実行を求める要求は無い |
| [`../arch-guide/arc-behavior-list.md`](../arch-guide/arc-behavior-list.md) の47業務 | 定期実行・自動起動・夜間処理に該当する業務は0件 |

⚠️ **「1バッチ過学習」は本編のバッチではない。** `requirements.md` 91行・343行・385行に現れる
「バッチ」は、機械学習のミニバッチ（サニティチェックの一段）を指す。
定時実行の一括処理とは無関係である。同様に「スケール」「スケジュール」も学習の進め方を指す。

### 2.2 非同期処理は別の枠組みが扱う

本プロダクトの非同期処理は、**すべて利用者の操作を起点とするジョブ**である。
論文取り込み、実装探索、spec 生成、サンドボックス実行のいずれも、利用者が画面で開始する。

これらの規則は [`../arch-guide/arc-behavior-rules.md`](../arch-guide/arc-behavior-rules.md)
`BR-12`（非同期処理とサンドボックス）が定めている。**バッチ編を追加すると責務が二重になる。**

## 3. 帳票編を対象外とする根拠

REF-16 の帳票編は、**印刷を前提とした出力**の設計を扱う。

### 3.1 印刷帳票が存在しない

本プロダクトの出力は次の2つだけである。

| 出力 | 形式 | 根拠 |
| --- | --- | --- |
| 画面表示 | ブラウザ | 画面編（[`../arch-guide/arc-screen-list.md`](../arch-guide/arc-screen-list.md)）が扱う |
| 成果物のダウンロード | 規約名 zip | `requirements.md` 346行・389行、`product-design.md` 245行 |

要求・設計のいずれにも、**印刷・帳票・レイアウト定義を求める記述が無い。**

### 3.2 「レポート」は帳票ではない

`requirements.md` 363行の「照合・レポート」はフェーズ5の名称であり、
実体は**スコア照合の画面表示と成果物のダウンロード**である。
帳票編が想定する、印刷を前提とした定型出力ではない。

## 4. 見直す条件

次のいずれかが生じたら、本決定を見直す。

| 条件 | 該当する編 |
| --- | --- |
| 定期実行される処理を要求として採用したとき | バッチ編 |
| 印刷を前提とした定型出力を要求として採用したとき | 帳票編 |
| `REQ-C11`（成果物の外部送信）の具体化で、定型フォーマットの生成が必要になったとき | 帳票編 |

⚠️ **`REQ-C11` は初期リリースの対象外である**（[`../arch-guide/arc-interface-list.md`](../arch-guide/arc-interface-list.md) 3.2節）。
具体化の際に本決定を再確認する。

## 5. 仮に設計するとしたら何を書くことになるか

⚠️ **本節は検討の記録である。ここに挙げた内容を設計するという意味ではない。**
次に同じ着想を得た人が、ゼロから検討し直さずに済むように残す。

### 5.1 バッチ編で候補になりうる処理

| 候補 | 内容 | すでに扱っている規則 |
| --- | --- | --- |
| 外部リンクの生存確認 | `IF-02` の GitHub URL や `IF-04` の査読情報は失効・移動しうる。Papers with Code は実際に消滅した（[`decision-pwc-replacement.md`](decision-pwc-replacement.md)） | `BR-13` 失敗時の縮退 |
| 論文の版更新の検知 | arXiv の論文は改訂される。保存済みの版と最新版を比べて利用者へ知らせる | `BR-02` 対象版の記録 |
| サンドボックスの後始末 | 隔離実行の残骸、中間ファイル、失敗ジョブの成果物を片付ける | `BR-11` 保存・削除・共有、`BR-12` |
| LLM コストの集計 | 日次・月次の締めと表示用の積み上げ | `BR-13` コスト |

⚠️ **コストの上限判定はバッチではない。** 呼び出しのたびに行う必要がある（`BR-13`）。
バッチが担えるとすれば集計と表示だけである。

⚠️ **版更新の検知には頻度の制約がある。** arXiv の結果は1日1回しか変わらず、
公式仕様がキャッシュを求めている（[`../arch-guide/interfaces/IF-01.md`](../arch-guide/interfaces/IF-01.md)）。

共通ルールに書くことになるのは、実行時刻の基準（`BR-04`）、多重起動の防止、
失敗時の再実行可否、利用者の操作と競合したときの優先順位である。

### 5.2 帳票編で候補になりうる出力

| 候補 | 内容 | 現在の実現手段 |
| --- | --- | --- |
| 再現レポート | 論文値と再現値の対比、差分、サニティ階段の合否、仮定台帳を1文書に | 画面表示と zip |
| 証拠台帳の出力 | 何をどこから取り、何が取れなかったかの一覧。再現性の主張そのもの | 画面表示（`BR-02`・`BR-10`） |
| 学習経路の記録 | 読解・学習コースの到達点、演習履歴、自己説明（`REQ-C04` 系） | 画面表示 |

共通ルールに書くことになるのは、数式の扱い、長い要旨や著者リストの折り返し、
`unknown` の表記統一、出典表記と arXiv の謝辞の配置である。

### 5.3 それでも作らない理由

**1. 要求が無い。** 5.1・5.2 は「ありそうなもの」を列挙したにすぎず、
[`../requirements.md`](../requirements.md) にも47業務にも根拠が無い。
要求から導かれない設計は、「一覧が先」（[`../arch-guide/arc-artifact-order.md`](../arch-guide/arc-artifact-order.md)）
以前の問題である。

**2. 責務が重複する。** 5.1 の4候補はいずれも `BR-11`・`BR-12`・`BR-13` が既に扱う領域にある。
バッチ編を足すと、**同じ規則が2箇所に分かれる**。
`BR-13` を振舞い編に置いた判断（[`pending-br13-external-api.md`](pending-br13-external-api.md)）と同じ理由で避ける。

**3. zip で足りている。** 再現レポートを PDF にする価値はあるが、それは成果物の一形式であり、
印刷レイアウトの設計を要するほどの要件は現時点で無い。

### 5.4 着手するときの順序

**設計から入らない。要求から入る。**

1. 着想を要求候補として `pending-<要求ID>.md` に起こす
2. 5択を経て `REQ-Cxx` を確定させる
3. 4節の見直す条件に照らし、編そのものが必要かを判断する
4. 必要と決まってから、一覧を最初に作る
