## 1. 設計の前提

### 1.1 確定済みの値

外部IF一覧の作成過程で、公式仕様を調査済みである
（[`../arch-guide/arc-interface-list.md`](../arch-guide/arc-interface-list.md)）。

| IF | 接続先 | レート制限 | 認証 | 課金 |
| --- | --- | --- | --- | --- |
| `IF-01` | arXiv | **1req/3秒**、同時接続1 | 不要 | 無償 |
| `IF-02` | GitHub | **5,000/時**（認証時） | fine-grained PAT | 無償 |
| `IF-03` | Hugging Face | 未確認 | 不要 | 無償 |
| `IF-04` | OpenReview | 1回1,000件 | 任意 | 無償 |
| `IF-05` | LLM プロバイダ | プロバイダ依存 | 必要 | **従量** |

### 1.2 ⚠️ 設計の要点

| 要点 | 内容 |
| --- | --- |
| **従量課金は `IF-05` だけ** | コスト上限の対象を絞れる |
| **`IF-01` が最も厳しい** | 3秒に1回。並列化できない |
| **失敗が検出できない経路がある** | `IF-03`・`IF-04` は空結果とエラーの区別が要る |
| **制限内でも失敗しうる** | arXiv で 429 の報告がある |

## 2. 追記案の本文

以下を `arc-behavior-rules.md` の `BR-12` の後、`13. 個別業務で追加する事項` の前へ挿入する。

```markdown
## BR-13 外部API呼び出し（Paper-repro固有）

### 呼び出しの制御

- 各接続先のレート制限を守る。制限値は`arch-guide/arc-interface-list.md`を正本とする。
- `IF-01`は3秒に1回、同時接続1本を上限とし、並列化しない。
- 制限を守っても`429`が返りうる前提で設計する。制限内の失敗を異常終了として扱わない。
- 認証情報は環境変数から読む。コード、設定ファイル、成果物、ログへ書かない。
- 認証が無い状態でも、制限の低い縮退動作として呼び出しを許す。動作を止めない。

### コスト

- 従量課金は`IF-05`だけである。上限の管理対象をここに限る。
- 上限は利用者が設定し、既定値を持つ。上限に達したら`IF-05`の新規呼び出しを止める。
- 停止しても、実行中のジョブは完了まで進める。中断による成果物の欠落を避けるため。
- 停止中も`IF-01`〜`IF-04`の取得と、利用者の手作業は続けられる。
- 消費量は呼び出しごとに記録し、期間と単位を明示して表示する（`BR-04`）。

### リトライ

- 一時的な失敗（タイムアウト、`429`、`5xx`）だけを再試行の対象とする。
- 入力不正（`4xx`のうち`429`以外）、認証失敗（`401`）、権限不足（`403`）は再試行しない。
- 再試行の間隔は前回より広げる。`IF-01`は3秒の制限を下回らない。
- 再試行の上限回数を定め、超えたら失敗として扱う。無限に繰り返さない。
- `Retry-After`ヘッダがあればその値に従い、独自の間隔より優先する。
- 再試行の回数と理由を記録する。何回目で成功したかを追跡可能にする。

### タイムアウト

- 接続と応答のそれぞれに待ち時間の上限を置く。
- 上限を超えたら打ち切り、一時的な失敗として扱う。
- 上限は接続先ごとに変えてよい。`IF-05`は生成に時間がかかるため長くとる。
- 打ち切りは失敗であり、空の結果ではない。両者を同じ値で表さない。

### 失敗時の縮退

- 外部APIの失敗で`phase`を巻き戻さない。到達済みの工程を保持する。
- 失敗した取得は`unknown`として記録し、推測で補わない（`BR-10`）。
- 代替手段がある場合は利用者へ提示する。`IF-01`と`IF-05`は手作業で代替できる。
- 代替手段が無い`IF-04`の失敗では、その情報を欠いたまま工程を進められるようにする。
- 縮退した状態を利用者へ明示する。欠落に気づかないまま先へ進ませない。

### 空の結果と取得失敗の区別

- 「該当なし」と「取得できなかった」を別の状態として保持する。
- `IF-03`は未索引でも空が返る。「実装が存在しない」と解釈しない。
- `IF-04`は誤ったURLや`invitation`でもエラーにならず空が返る。要求の妥当性を先に確認する。
- 区別できない場合は`unknown`とし、判定を利用者へ委ねる。

### 利用条件

- 各接続先の利用規約に反する自動収集を行わない。
- 謝辞の表示が求められる場合は従う。arXivは製品への表示を要する。
- 取得したデータの保存期間と保存場所は、接続先のライセンスに従う（`BR-08`）。
```

## 3. 設計判断の根拠

### 3.1 コスト上限で「実行中のジョブは完了させる」理由

上限に達した瞬間に全処理を止めると、**中途半端な成果物が残る。**

たとえば spec 草案の生成中に停止すれば、途中までの文章が保存される。
これは `BR-11`（コース切替や失敗で既存成果物を削除しない）の趣旨に反する。

**新規の呼び出しを止め、進行中は完了させる。**

### 3.2 認証が無くても止めない理由

[`decision-github-auth.md`](decision-github-auth.md) で決めた方針を、規則として一般化した。

**トークンの取得には時間がかかる。** まず動かして試せる方が、初回利用の障壁が低い。
ただし制限が低いことを明示する。

### 3.3 `Retry-After` を優先する理由

サーバが待ち時間を指定してきた場合、**こちらの都合で早く再試行すると、さらに制限される。**
指定に従うのが確実である。

### 3.4 「縮退した状態を明示する」理由

`BR-10` は「`unknown` を推測で埋めない」と定めるが、**利用者が気づかなければ意味がない。**

査読情報が取れなかったまま工程が進むと、利用者は「査読情報は無かった」と誤解しうる。
**欠落を見えるようにする。**

### 3.5 空の結果と取得失敗を分ける理由

`IF-03`（Hugging Face）と `IF-04`（OpenReview）は、**失敗しても成功と同じ形で返る。**

| 接続先 | 起きること |
| --- | --- |
| Hugging Face | 未索引の論文でも空が返る |
| OpenReview | 誤ったURLや `invitation` でも空が返る |

**「空 = 該当なし」と解釈すると、設定誤りに気づけない。**

## 4. 定めなかったこと

| 事項 | 理由 |
| --- | --- |
| 具体的なタイムアウト秒数 | 実装時に実測して決める。規則では上限を置くことだけを定める |
| 再試行の上限回数 | 同上 |
| コスト上限の既定値 | 利用者の使い方に依存する。`product-design.md` 側の判断 |
| Hugging Face のレート制限 | 未確認。判明したら一覧へ追記する |

⚠️ **数値を規則へ書き込まない。** 変更のたびに共通ルールを直すことになる。
**規則は方針を定め、値は一覧が持つ。**
