# paper-repro-mvp 設計指針（CCAF適用版）

英語AI論文の読解〜再現実装ツール **paper-repro-mvp** の開発判断に、
Claude Certified Architect – Foundations（CCAR-F）試験ガイドのノウハウを当てるためのスキル。

設計や実装方針で迷ったとき、このスキルの型を参照して「どのフェーズに何を適用するか」を決める。

## 隣接スキルとの境界

| スキル | 役割 |
|---|---|
| **本スキル（paper-repro-arch-guide）** | ツールの**設計判断**にCCAFの型を当てる |
| paper-repro-devlog | その日の開発の**日次ログ**を残す |
| arxiv-paper-repro | 論文そのものを**再現実装する手順** |
| skill-safe-update | スキルを**安全に更新**する規律 |

判断基準：「paper-repro-mvp の設計・実装方針を CCAF のノウハウで決めるのか」＝本スキル。

## 使い方

1. 設計判断が必要になったら、下の「フェーズ別の適用方針」で該当フェーズを見る。
2. 詳細な型の根拠は `references/ccaf-patterns.md`（CCAFのどの領域・タスクに対応するか）を参照する。
3. Claude Code に実装を頼むときは、`references/claude-code-playbook.md` の依頼テンプレートを使う。

## フェーズ別の適用方針（ロードマップ対応）

ロードマップ（docs/roadmap.md）の各フェーズに、CCAFのどのノウハウを当てるか。

### フェーズ0（データ永続化・状態遷移）
- **プランモードの発想**：DB移行のような複数ファイル・アーキテクチャ判断は、まず計画を出させてから実装（実施済み）。
- **状態機械＝プログラム的enforcement**：承認ゲートは「プロンプトでお願い」でなく、状態遷移の検証で強制する（states.pyのcan_transition）。CCAFの「決定論的コンプライアンスが要る場面はhookやゲートで強制」に対応。

### フェーズ1（インテーク：論文取込・タイプ判定・方針選択）
- **構造化出力（tool_use + JSONスキーマ）**：論文のタイプA/B判定、方針5択は、自由文でなくJSONスキーマで受ける。enumに"unclear"を足し、判定不能を許容する。
- **nullableフィールドで幻覚防止**：論文にAbstractが取れない等の欠損は、必須にせずnullを返させる（値の捏造を防ぐ）。
- **エスカレーション基準の明示**：方針選択ゲートは、CCAFの「顧客が人間を求めた／ポリシーが曖昧／進めない」に相当する明示基準を持たせる。few-shot例を添える。

### フェーズ2（非同期ジョブ・WebSocket）
- **エージェントループの終了条件**：長時間ジョブの完了判定は、自然言語の合図でなく明示的な状態（stop_reason的な明確なシグナル）で行う。CCAFの「自然言語で終了判定するアンチパターンを避ける」に対応。
- **構造化エラー**：ジョブ失敗は「失敗した」でなく、失敗種別（transient/validation/permission）・リトライ可否・部分結果を構造化して返す。

### フェーズ3（リーディング：spec草案・仮定台帳）
- **lost in the middle対策**：長い論文PDFは、要点サマリーを先頭に置き、詳細はセクション見出しで構造化する。中盤の見落としを防ぐ。
- **verboseなツール出力のtrim**：リポジトリ読解等で得た大量出力は、関連フィールドだけに絞ってコンテキストに積む。
- **few-shot例**：spec抽出は、多様な論文構造（インライン引用 vs 参考文献欄など）の入出力例を2〜4個添えて一貫させる。
- **claim-sourceマッピング**：仮定台帳は、各仮定に出典（論文の該当箇所）を必ず紐づけ、要約で出典が失われないようにする。

### フェーズ4（検証：サンドボックス・サニティ階段）
- **プランモード必須**：サンドボックスは大規模・アーキテクチャ判断なので、必ず計画を出させてから実装する。
- **検証・リトライループ**：サニティ階段は、失敗内容を次の試行に戻して自己修正させる。ただし「情報が元から無い」失敗はリトライしても無駄、と見分ける。
- **独立レビュー**：生成コードのレビューは、生成したのと同じセッションでなく、独立インスタンスにやらせる（自己レビューの限界を避ける）。

### フェーズ5（照合・レポート）
- **provenance保持**：再現値vs論文値の照合は、どの値がどの出典か（claim-source）を保ったまま突き合わせる。
- **矛盾の注記**：値が食い違うときは、片方を勝手に選ばず両方を出典つきで示す。

### フェーズ6（公開整備）
- **CLAUDE.mdの分割**：肥大化したCLAUDE.mdは .claude/rules/ に分割し、パス別（glob）で該当ファイル編集時だけ読み込む。バックエンド(Python)とフロント(TypeScript)で規約が違うこのプロジェクトに有効。

## Claude Code の使い方（このプロジェクト共通）

- **プランモード vs 直接実行**：複数ファイル・アーキテクチャ判断・複数の妥当な方式があるとき→計画を出させる。単一ファイルの明確な修正→直接実行。
- **カスタムスラッシュコマンド**：繰り返す依頼（レビュー、テスト生成、実装依頼テンプレート）は .claude/commands/ に置いてチーム共有する。
- **パス別ルール**：.claude/rules/ にglob（例: paths: ["backend/**/*.py"], ["frontend/**/*.tsx"]）で規約を条件付き読み込みする。
- **CI連携（将来）**：CIでClaude Codeを使うときは -p（非対話）と --output-format json を使う。

詳細な依頼テンプレートは `references/claude-code-playbook.md` を参照。

## やってはいけないこと

- ❌ CCAFの型を、対応しないフェーズに無理に当てる（例：まだ単一DBのMVPにマルチエージェント設計を持ち込む）
- ❌ このスキルで日次ログを書く（それは paper-repro-devlog の役割）
- ❌ 「確信度スコアで自動判定」など、CCAFがアンチパターンとするものを採用する（自己申告の確信度は当てにならない）
- ❌ 承認ゲートをプロンプトのお願いだけで済ませる（決定論的な強制が要る場面は状態遷移で守る）
