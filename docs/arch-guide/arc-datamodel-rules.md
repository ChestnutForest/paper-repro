# データモデル共通ルールとレビュー基準

- 対象プロダクト: `paper-repro`
- 版: **v0.2**
- 作成日: 2026年8月29日
- 更新日: 2026年8月29日
- 適用先: `arc-datamodel-list.md`、`arc-datamodel-er.md`、
  `arc-datamodel-definitions.md`、`arc-datamodel-crud.md`、`arc-datamodel.md`
- 参照: REF-15／REF-16 データモデル編

## 0. 使い方

`DMR-##`はPaper-repro固有の設計規則、`DMV-##`は本プロジェクトでのレビュー項目である。
ガイドのコツ本文を複製せず、確定要求と既存設計から検査可能な形に組み立てた。

## 1. 共通ルール

### DMR-01 名称とID

- エンティティ名は英語の単数形、文書内の表示はバッククォートで囲む。
- エンティティIDは`DM-E##`で固定し、要求・業務・画面・状態の既存IDを振り直さない。
- 同じ語が別概念を表す場合は、`Course.READING`と`Phase.READING`のように型と説明を分ける。
- 略称、別名、混同しやすい語は用語集または定義の備考で区別する。

### DMR-02 不明値と情報状態

- 取得できない値を空文字、現在日時、LLM推測値で補完しない。
- `unknown`、未報告、推定、外部確認済み、人間承認済みを別状態として扱う。
- DBの`NULL`、空配列、空文字、値`unknown`の意味は物理仕様で列ごとに定義する。
- LLMの分類は候補であり、人間承認済み状態を直接設定しない。

### DMR-03 情報源・版・由来

- 外部から得た値には取得元、対象版、取得日時、取得条件を関連付ける。
- 論文、公式実装、生成物の対応は、版・コミット・位置を伴って双方向に辿れるようにする。
- 原文、抽出、要約、解釈、設計提案、実装、観察結果を同じ種別へ潰さない。
- 訂正で古い由来を消さず、新しい版または訂正履歴を追加する。

### DMR-04 主管と確定権限

- 自動処理が作る値と、利用者だけが最終確定できる値を定義で分ける。
- 承認、採用理由、外部送信、公開、確認付き削除は利用者の明示操作を必要とする。
- 将来の共同利用者、専門家、著者、外部AIは別の回答主体として記録する。

### DMR-05 状態と履歴

- 工程`phase`と実行状態`status`を別属性とし、失敗で工程を失わない。
- 承認、実行、照合、コスト、共有は履歴を追記し、現在値だけへ上書きしない。
- 同じ操作の再実行は新しい実行記録を作り、前の失敗とログを保持する。
- 集計可能な値は元記録を正本とし、派生集計を重複保存する場合は再生成条件を定める。

### DMR-06 保存・削除・復元

- コース切替、実行失敗、方針変更で既存成果物を削除しない。
- プロジェクト削除前に、対象となる子記録、成果物、共有状態、バックアップ状態を表示する。
- 削除は明示確認後に行い、外部共有物を自動的に回収できない場合はその制約を示す。
- 復元・移行用出力は、版、由来、承認、公開範囲を失わない形式にする。
- 保存期間が未決のエンティティは、未決のまま一覧に残し、根拠のない期間を設定しない。

### DMR-07 ドメイン・コード・制約

- 同じ意味の値集合はENUMまたは共有ドメイン候補として一度だけ定義する。
- `course`、`phase`、`status`、`approval_kind`、`paper_type`、`policy`の値は
  [`arc-datamodel.md`](arc-datamodel.md)第3.3節を正本とする。
- 値域、単位、精度、タイムゾーン、大小文字、連番の可否を利用フェーズ直前に確定する。
- `waiting_approval`と`approval_kind`の不変条件のように、DBで表せる制約は物理仕様に明記する。

### DMR-08 外部データ境界

- arXiv、PDF、DOI、出版社、GitHub、LLM API、共有先を外部境界として扱う。
- 入出力の方向、対象データ、変換、欠落、拒否、再試行を外部インタフェース設計と照合する。
- 外部ファイルの項目とエンティティ属性の対応は、取り込みアダプタを追加する時点で定義する。
- 外部サービス内部のIDをPaper-reproの主キーとして無条件に流用しない。

### DMR-09 データ量・容量

- エンティティごとに初期件数、最大件数、増加率、平均サイズ、保存期間、算定根拠を管理する。
- 未計測値を推測で埋めず、計測するフェーズと入力データを決める。
- ログ、PDF、コード、Notebook、zipは、DB行数だけでなく実体容量と保持世代数を測る。
- 容量見積はピークと平均を分け、再実行・版管理・バックアップ分を含める。

### DMR-10 トレーサビリティ

- 各エンティティと主要属性に要求IDを付ける。
- CRUDの各行は`B-xx-xxx`、画面に現れる属性は`S-xx-xx`／`A-xx-xxx`へ関連付ける。
- 物理列、APIスキーマ、ORM、テストへ落とした時点でTMへファイル対応を追加する。
- 由来のない追加属性は「実装上便利」という理由だけで確定要求に格上げしない。

### DMR-11 権利・機密・公開範囲

- 論文、コード、データセット、生成物のライセンス・引用・公開条件を保持する。
- シークレット、個人情報、機密情報を永続化・成果物化する前に除外または保護する。
- 新しい利用者生成物の公開範囲は非公開を既定とする。
- 公開・取消履歴と、外部側で取消不能な範囲を区別する。

### DMR-12 変更と移行

- 論理モデル変更には要求またはレビューギャップの根拠を付ける。
- 変更前後で、エンティティ、属性、多重度、制約、CRUD、移行対象を比較する。
- 捨てられないデータ、複数利用者、一般公開のいずれかが始まる前にマイグレーション方式を確定する。
- 論理名の変更と物理列名の変更を区別し、由来・エクスポート互換性を確認する。
