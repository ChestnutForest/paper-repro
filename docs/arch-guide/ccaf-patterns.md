# CCAF パターン対応表（paper-repro 適用）

CCAR-F 試験ガイドの5ドメインから、paper-repro に効くノウハウだけを抜き出し、
「CCAFのどの領域・タスク」→「このツールのどこに効くか」を対応づけた表。
設計判断の根拠を確認したいときに参照する。

## Domain 1: Agentic Architecture & Orchestration（27%）

| CCAFのノウハウ | このツールへの適用 |
|---|---|
| エージェントループはstop_reasonで制御し、自然言語で終了判定しない | フェーズ2の非同期ジョブ完了判定を、明示的な状態シグナルで行う |
| 決定論的コンプライアンスが要る場面は、プロンプトでなくhook/ゲートで強制 | 承認ゲート（各Phase末）を状態遷移の検証で強制する（states.py） |
| プログラム的な前提条件で下流をブロック（例: 検証前の操作を止める） | 例: spec未確定なら実装フェーズに進ませない |
| タスク分解が狭すぎると網羅漏れ（creative industries→visual artsだけ、の失敗例） | フェーズ1の論文分解・方針決定で、対象範囲を狭めすぎない |

※ マルチエージェント（coordinator-subagent）は初期リリース段階では過剰。フェーズ3以降で論文読解を分割するとき再検討。

## Domain 2: Tool Design & MCP Integration（18%）

| CCAFのノウハウ | このツールへの適用 |
|---|---|
| ツール説明文が選択の主要因。曖昧だと誤選択 | 将来ツール化する機能（取込・照合など）は説明文を明確に差別化 |
| 構造化エラー（errorCategory, isRetryable, 説明） | ジョブ/取込の失敗を構造化して返す（フェーズ2） |
| ツールが多すぎると選択精度が落ちる（18個より4-5個） | 各処理に必要なツールだけに絞る |
| transient/validation/business/permission の区別 | 取込失敗（ネット）と入力不正（URL形式）を区別して扱う |

## Domain 3: Claude Code Configuration & Workflows（20%）

| CCAFのノウハウ | このツールへの適用 |
|---|---|
| CLAUDE.mdの階層（user/project/directory）と@import分割 | 肥大化したらproject-levelを保ちつつ .claude/rules/ に分割 |
| .claude/rules/ にglobでパス別ルール | backend/**/*.py と frontend/**/*.tsx で別規約を条件読み込み |
| .claude/commands/ でチーム共有スラッシュコマンド | 実装依頼テンプレ・レビュー・テスト生成をコマンド化 |
| プランモード vs 直接実行 | 大規模/アーキ判断→計画、単一ファイル明確→直接 |
| test-driven iteration、interview pattern | 不慣れな領域はClaudeに質問させてから実装 |
| CI連携は -p と --output-format json | フェーズ6でCIレビューを入れるときに使う |

## Domain 4: Prompt Engineering & Structured Output（20%）

| CCAFのノウハウ | このツールへの適用 |
|---|---|
| tool_use + JSONスキーマで構造化出力を保証 | タイプ判定・方針5択・spec・仮定台帳をスキーマで受ける |
| nullableフィールドで幻覚防止 | 論文の欠損項目はnull可にし、値の捏造を防ぐ |
| enumに"unclear"/"other"+detail | 判定不能・分類外を明示的に許容 |
| few-shot例で一貫性向上（2-4個） | spec抽出で多様な論文構造の入出力例を添える |
| 明示的な基準で誤検知を減らす | 「〜のときだけフラグ」と具体化する |
| 検証・リトライループ（エラーを戻して自己修正） | サニティ階段の失敗を次試行に戻す（フェーズ4） |
| リトライが無駄な場合（情報が元から無い）を見分ける | 論文に無い数値は、リトライでなく「取得不能」と扱う |
| バッチAPI（50%コスト減、24hまで、SLAなし） | 大量論文の非同期処理を将来検討（ブロッキング処理には使わない） |

## Domain 5: Context Management & Reliability（15%）

| CCAFのノウハウ | このツールへの適用 |
|---|---|
| lost in the middle（長い入力の中盤が抜ける） | 長い論文PDFは要点を先頭に、詳細を見出しで構造化 |
| verboseなツール出力を関連フィールドだけtrim | リポジトリ読解等の大量出力を絞ってコンテキストに積む |
| case facts/scratchpadで重要事実を保持 | 仮定台帳・spec を永続レイヤーに持つ |
| エスカレーション基準（人間要求/ポリシー曖昧/進めない） | 方針選択ゲートの承認基準に対応。few-shot例を添える |
| 確信度の自己申告は当てにならない | 「確信度スコアで自動判定」を採用しない |
| claim-sourceマッピングを要約後も保持 | 仮定・照合結果に出典を紐づけ、要約で失わない |
| 矛盾する値は片方を選ばず出典つきで両方示す | 再現値vs論文値の食い違いを注記する |
| 出版/収集日を構造化出力に含める | 論文の版・日付を保持し、時系列の誤解を防ぐ |

## 初期リリースでは当面採用しないもの（過剰なため）

- マルチエージェント（coordinator-subagent）の本格導入 → フェーズ3以降で論文読解分割時に再検討
- Message Batches API → 大量論文処理が必要になったら
- 本格的なMCPサーバ自作 → 標準統合は既存を使い、team固有処理だけ自作
