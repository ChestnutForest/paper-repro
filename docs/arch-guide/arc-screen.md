## 1. 本書の位置づけ

### 1.1 本書で決めること・決めないこと

**本書は枠組みだけを定める。** どの文書を作り、何をどのIDで識別し、
どこまで書けば完了とするか、を決める。

| 決めること | 決めないこと |
|---|---|
| 作成する工程成果物の種類と、その担当文書 | 個々の画面のレイアウト |
| 画面・画面項目・アクションのID体系 | 画面に置く部品の配置 |
| 完了の判定（合意成熟度の読み替え） | 配色・フォントの具体値 |
| USDM の仕様・TM との連結方法 | 画面遷移の具体的な線の引き方 |

**具体的な設計は本書の枠組みが固まってから着手する。** 枠組みが無いまま
レイアウトを描くと、後から識別子や粒度を揃え直すことになる。

## 2. ⚠️ 合意形成の前提の読み替え

**REF-16 は「発注者と開発者が齟齬なく合意する」ことを目的としている。**
`paper-repro` は**個人開発であり、発注者と開発者が同一人物である。**
前提が成り立たないため、そのまま適用できない。

この点を隠して「ガイドに準拠した」と書くと、後から読む人が誤解する。

### 2.1 誰と誰の合意に読み替えるか

| ガイドの役割 | `paper-repro` での読み替え |
|---|---|
| 発注者（何が欲しいかを言い切る側） | **要求を出す立場の自分。** `REQ-Cxx` を選択・承認する人 |
| 開発者（仕様を書き、聞き切る側） | **実装する立場の自分と、AIエージェント**（Claude Code / Codex） |

**合意の相手が実在する。** AIエージェントは要求を推測で補いうるため、
齟齬を防ぐ必要は個人開発でも消えない。実際、フェーズ0-1では
`can_transition` の役割を私が取り違え、承認ゲートを通り抜ける実装が生まれた
（[`../devlog/devlog-2026-08-25.md`](../devlog/devlog-2026-08-25.md)）。

もう1つの相手は**半年後の自分**である。書かなかったことは思い出せない。

### 2.2 この読み替えで失われるもの

ガイドが想定する「**発注者が業務を知っており、開発者が知らない**」という
知識の非対称は、個人開発では生じない。したがって業務知識を伝えるための
コツは効きにくい。**効くのは、書き方と抜けもれの検出に関するコツである。**

## 3. 作成する工程成果物

REF-16 は画面について**6つの工程成果物**を定義している。
`paper-repro` での採否と担当文書を次のとおり定める。

| # | 工程成果物 | 採否 | 担当文書 | 作成の時期 |
|---|---|---|---|---|
| 1 | **画面一覧** | 採用 | [`arc-screen-list.md`](arc-screen-list.md) | ✅ v0.1 作成済 |
| 2 | **画面遷移** | 採用 | `arc-screen-flow.md` | ⬜ 未作成 |
| 3 | **画面レイアウト** | 採用 | [`screens/`](screens/) の7ファイル | ✅ v0.1 作成済 |
| 4 | **画面入出力項目一覧** | 採用 | 同上（同じファイル内 2節） | ⬜ 枠のみ。実装フェーズで |
| 5 | **画面アクション明細** | 採用 | 同上（同じファイル内 3節） | ⬜ 枠のみ。実装フェーズで |
| 6 | **画面遷移・レイアウト共通ルール** | 採用 | [`arc-screen-rules.md`](arc-screen-rules.md) | ✅ v0.1 作成済 |

### 3.1 3〜5を1つのファイルにまとめる理由

ガイドは3つを別の成果物として定義するが、**同じ画面について書くもの**である。
別ファイルにすると、画面を1つ直すたびに3ファイルを開くことになり、
どれか1つの更新を忘れる。**1画面1ファイルとし、その中を3節に分ける。**

ガイド自身も、設計書の単位を工程成果物と一致させるかはプロジェクトの判断としている。

### 3.2 共通ルールを先に作る理由

共通ルール（#6）を後回しにすると、個別の画面ごとに配色や配置を決めることになり、
**後から揃え直せなくなる。** 画面一覧と同時に着手する。

## 4. ID体系

**画面まわりのIDをここで確定する。** 文書をまたいで同じものを指すため、
先に決めないと突き合わせができない。

| 対象 | 記法 | 例 | 規則 |
|---|---|---|---|
| 画面 | `S-nn-mm` | `S-01-01` | `nn` は画面グループ、`mm` はグループ内の連番 |
| 画面グループ | `nn` | `01` | 利用者から見た機能のまとまり。10刻みにしない |
| 画面項目 | 画面内の連番 | `1` `2` `3` | 画面IDと組で一意（`S-01-01` の `3`） |
| アクション | `A-nn-mmm` | `A-01-001` | `nn` は画面グループ、`mmm` は連番 |
| 画面遷移 | `T-nn` | `T-01` | ひとまとまりの遷移図に1つ |
| 共通ルール | `CR-nn` | `CR-01` | ルールの節ごと |

**要求ID（`REQ-Cxx`）と実装単位（`F-xx`）は既存のものを使う。** 新設しない。

### 4.1 IDを揃える約束

- 画面レイアウト・画面入出力項目一覧・画面アクション明細の**3節で、同じ画面項目には同じ番号**を使う。
- 画面遷移のイベント名と、画面アクション明細のイベント名を**一致させる**。
- 画面一覧に無い画面を、先に画面レイアウトから起こさない。**一覧が先である。**

## 5. 完了の判定：合意成熟度の読み替え

REF-16 は合意成熟度を**仕掛・充実・完成**の3レベルで表す。
`paper-repro` では、これを [`../traceability-matrix.md`](../traceability-matrix.md) の工程へ次のように対応づける。

| 成熟度 | 本プロジェクトでの意味 | TM の工程 |
|---|---|---|
| **仕掛** | 画面の存在と役割が決まった。画面一覧に行がある | 要求 ✅ |
| **充実** | 遷移・レイアウト・入出力項目・アクションが書かれ、抜けを検査した | 設計 ✅ |
| **完成** | 実装され、テストが通り、**画面で操作して確認した** | 画面 ✅ |

> **「完成」に画面での確認を含めた。** ガイドは外部設計工程までを対象とし、
> 実装は範囲外としている。しかし `paper-repro` は
> [`../roadmap.md`](../roadmap.md) の開発方針で「画面で確認できない項目は完了にしない」と
> 定めており、そちらを優先する。**ガイドからの意図的な逸脱である。**

## 6. 4つの作業の適用

REF-16 は合意形成を**言い切る／聞き切る・図表に書く・もれ／矛盾をチェックする・
一緒にレビューする**の4つの作業で説明している。個人開発での扱いを定める。

| 作業 | `paper-repro` での扱い |
|---|---|
| 言い切る／聞き切る | **USDM が担う。** 要求・理由・仕様を書き切ることが「言い切る」にあたる |
| 図表に書く | 本書の枠組みに沿って各工程成果物を書く |
| もれ／矛盾をチェックする | **機械的な検査を優先する。** 画面一覧とレイアウトの件数照合、IDの一致、遷移とアクションのイベント名照合をスクリプトで検査する |
| 一緒にレビューする | **対面の相手がいない。** 代わりに、AIエージェントへ設計を読ませて指摘を求め、その指摘を記録する |

**3番目を機械検査に寄せたのは、1人では見落としに気づけないためである。**
目視のチェックリストは、書いた本人が読むと通ってしまう。

## 7. 文書の枠組み

新規に作る3文書の章立てを、ここで確定する。

### 7.1 `arc-screen-list.md`（画面一覧）

| 章 | 内容 |
|---|---|
| メタ情報 | 版・作成日・準拠する標準 |
| 一覧表 | 1行＝1画面。列は下記 |
| ツリー図 | 画面の階層構造を Mermaid で |
| 画面グループの定義 | `nn` の割り当てと、その根拠 |

**一覧表の列**: `No.` / 画面ID / 画面名 / 分類 / 階層 / 説明 / 対応要求（`REQ-Cxx`）/
実装単位（`F-xx`）/ 想定利用者 / 備考

**「対応要求」列を独自に追加した。** ガイドの構成要素は機能名・機能IDだが、
`paper-repro` は USDM で要求を管理しているため、そちらへ繋ぐ。

### 7.2 `arc-screen-flow.md`（画面遷移）

| 章 | 内容 |
|---|---|
| メタ情報 | 同上 |
| 遷移図 | Mermaid。**1図＝1つの完結した利用の流れ** |
| 正常系と異常系 | 線種で区別する |
| イベント一覧 | 遷移を起こすイベントと、対応するアクションID |
| 経路による分岐 | `course=reading` / `reproduction` の違い（`REQ-C01`） |

### 7.3 `arc-screen-rules.md`（画面遷移・レイアウト共通ルール）

REF-16 が挙げる構成要素8種に沿って章を立てる。

| 章 | 決めること |
|---|---|
| ページの構成要素 | 画面をどのエリアに分けるか、各エリアの用途 |
| 配色 | キーカラー、アクセントカラー、フォントカラー |
| 文字フォント・サイズ | 書体、サイズ、行間 |
| 全体構造とナビゲーション | 階層構造、ナビゲーションの表示 |
| 画面遷移パターン | エリアごとの遷移の型 |
| エラー表示方法・エラーメッセージ | 分類、表示位置、書式 |
| ユーザの定義 | 利用者の分類 |
| 制約事項 | 画面サイズ、ブラウザ、性能 |

**`paper-repro` 固有として次を追加する。**

| 追加する章 | 理由 |
|---|---|
| **多言語の扱い** | `ja` `en` `zh-TW` の3言語。文言はすべて翻訳キーで参照する（`AGENTS.md` 5章） |
| **承認ゲートの表示** | 遷移型①②③と事象駆動型④⑤⑥で見せ方が異なる（`../product-design.md` 1.3） |
| **長時間処理の表示** | 進捗のストリーム表示。画面を閉じても処理は続く |

### 7.4 `screens/S-xx-xx.md`（画面ごと）

| 節 | 内容 |
|---|---|
| 書誌情報 | 画面ID・画面名・概要・対応要求 |

| 2. 画面入出力項目一覧 | 表。項目ごとの型・制約・初期表示 |
| 3. 画面アクション明細 | アクションごとの処理概要・詳細・遷移先 |

## 8. USDM・TM との連結

**画面は仕様から導く。** 思いついた画面を並べるのではない。

```
REQ-Cxx（要求）
  └─ REQ-Cxx-Rn.mm（仕様）
       └─ S-nn-mm（画面）
            ├─ 画面項目（入出力項目一覧）
            └─ A-nn-mmm（アクション）
```

`arc-screen-list.md` の「対応要求」列と、
[`../traceability-matrix.md`](../traceability-matrix.md) 第5章の交差表で、
**双方向に辿れるようにする。**

### 8.1 対応が付かないものの扱い

| 状況 | 扱い |
|---|---|
| 仕様に対応する画面が無い | **仕様の実現手段が未定。** 画面一覧の「未確定の画面」へ記録する |
| 画面に対応する仕様が無い | **要求の裏づけが無い画面。** USDM へ仕様を足すか、画面を削る |

**後者を放置しない。** 根拠のない画面は、作った本人しか理由を説明できなくなる。

## 9. 6編の作成順序

REF-16 は6つの技術領域を扱う。`paper-repro` での作成順序を定める。

| 順 | 編 | 担当文書 | 状態 | 理由 |
|---|---|---|---|---|
| 1 | **画面** | 本書 ＋ 3文書 | 🔨 枠組み作成中 | 利用者が最初に触れる。フェーズ0の確認画面に直結 |
| 2 | システム振舞い | `arc-behavior.md` | ⬜ | 画面の背後の処理。承認ゲートと状態遷移 |
| 3 | データモデル | [`arc-datamodel.md`](arc-datamodel.md) | ✅ **v1.0 済** | 既に作成済み。**ただし REF-16 データモデル編には準拠していない**（後述） |
| 4 | 外部インタフェース | `arc-interface.md` | ⬜ | arXiv・GitHub・Claude API との接続 |
| 5 | バッチ | `arc-batch.md` | ⬜ | Celery のジョブ。フェーズ2以降 |
| 6 | 帳票 | `arc-report.md` | ⬜ | 照合レポートと zip 出力。フェーズ5以降 |

### 9.1 ⚠️ 既存の `arc-datamodel.md` との差

`arc-datamodel.md` v1.0 は **REF-16 のデータモデル編に準拠して作ったものではない。**
DDL と状態遷移表を先に確定させる目的で、独自の構成で書いた。

**このまま「データモデル編に相当する」とは言えない。** 6編を揃える段階で、
データモデル編の工程成果物（ER図、エンティティ一覧、CRUD図など）と突き合わせ、
不足があれば補う。それまでは**準拠していないことを明記して扱う。**
