## 1. 本書の位置づけ

### 1.1 本書で決めること・決めないこと

**本書は枠組みだけを定める。** どの文書を作り、何をどのIDで識別し、
どこまで書けば完了とするか、を決める。

| 決めること | 決めないこと |
| --- | --- |
| 作成する工程成果物の種類と、その担当文書 | 個々の画面のレイアウト |
| 画面・画面項目・アクションのID体系 | 画面に置く部品の配置 |
| 完了の判定（合意成熟度の読み替え） | 配色・フォントの具体値 |
| USDM の仕様・TM との連結方法 | 画面遷移の具体的な線の引き方 |
| **成果物をまたぐ整合の取り方** | **個々の項目の入力制約の値** |

**具体的な設計は本書の枠組みが固まってから着手する。** 枠組みが無いまま
レイアウトを描くと、後から識別子や粒度を揃え直すことになる。

## 2. ⚠️ 合意形成の前提の読み替え

**REF-16 は「発注者と開発者が齟齬なく合意する」ことを目的としている。**
`paper-repro` は**個人開発であり、発注者と開発者が同一人物である。**
前提が成り立たないため、そのまま適用できない。

この点を隠して「ガイドに準拠した」と書くと、後から読む人が誤解する。

### 2.1 誰と誰の合意に読み替えるか

| ガイドの役割 | `paper-repro` での読み替え |
| --- | --- |
| 発注者（何が欲しいかを言い切る側） | **要求を出す立場の自分。** `REQ-Cxx` を選択・承認する人 |
| 開発者（仕様を書き、聞き切る側） | **実装する立場の自分と、AIエージェント**（Claude Code / Codex） |

**合意の相手が実在する。** AIエージェントは要求を推測で補いうるため、
齟齬を防ぐ必要は個人開発でも消えない。実際、フェーズ0-1では
`can_transition` の役割を私が取り違え、承認ゲートを通り抜ける実装が生まれた
（[`../devlog/devlog-2026-08-25.md`](../devlog/devlog-2026-08-25.md)）。

もう1つの相手は**半年後の自分**である。書かなかったことは思い出せない。

### 2.2 ⚠️ ガイドが想定する役割との差

REF-16 は発注者・開発者を**6種類の役割**に分けて図示し、本編では
**業務システム設計担当者とシステム開発者の間**を中心にコツをまとめている。

`paper-repro` にはこの分業が存在しない。したがって、役割間の伝達を扱うコツは効きにくい。
**効くのは、書き方と抜けもれの検出に関するコツである。**

### 2.3 この読み替えで失われるもの

ガイドが想定する「**発注者が業務を知っており、開発者が知らない**」という
知識の非対称は、個人開発では生じない。

## 3. 作成する工程成果物

REF-16 は画面について**6つの工程成果物**を定義している。
`paper-repro` での採否と担当文書を次のとおり定める。

| # | 工程成果物 | 採否 | 担当文書 | 作成の時期 |
| --- | --- | --- | --- | --- |
| 1 | **画面一覧** | 採用 | [`arc-screen-list.md`](arc-screen-list.md) | ✅ v0.1 作成済 |
| 2 | **画面遷移** | 採用 | [`arc-screen-flow.md`](arc-screen-flow.md) | ✅ v0.1 作成済 |
| 3 | **画面レイアウト** | 採用 | [`screens/`](screens) の7ファイル | ✅ v0.1 作成済 |
| 4 | **画面入出力項目一覧** | 採用 | 同上（同じファイル内 2節） | ⬜ 枠のみ。実装フェーズで |
| 5 | **画面アクション明細** | 採用 | 同上（同じファイル内 3節） | ⬜ 枠のみ。実装フェーズで |
| 6 | **画面遷移・レイアウト共通ルール** | 採用 | [`arc-screen-rules.md`](arc-screen-rules.md) | ✅ v0.1 作成済 |

### 3.1 3〜5を1つのファイルにまとめる理由

ガイドは3つを別の成果物として定義するが、**同じ画面について書くもの**である。
別ファイルにすると、画面を1つ直すたびに3ファイルを開くことになり、
どれか1つの更新を忘れる。**1画面1ファイルとし、その中を3節に分ける。**

ガイド自身も、設計書の単位を工程成果物と一致させるかはプロジェクトの判断としている。

### 3.2 共通ルールを先に作る理由

共通ルール（#6）を後回しにすると、個別の画面ごとに配色や配置を決めることになり、
**後から揃え直せなくなる。** 画面一覧と同時に着手する。

### 3.3 ⚠️ 共通情報・書誌情報の枠（v0.2で追加）

**REF-16 は6つの成果物すべてに、共通の枠を定めている。**

| 分類 | 内容 |
| --- | --- |
| **0. 共通情報** | プロジェクト名、システム名、工程名、ドキュメントID、ドキュメント名、作成者、作成日付、バージョン、更新者、更新日付 |
| **1. 書誌情報** | その成果物のID、名称、概要 |

v0.1 はこの枠を扱っていなかった。`paper-repro` での扱いを次のとおり定める。

| ガイドの項目 | `paper-repro` での扱い |
| --- | --- |
| プロジェクト名 | 各文書のメタ情報に「対象プロダクト: `paper-repro`」として記載済み |
| システム名 | プロジェクト名と同一のため**省略** |
| 工程名 | [`../traceability-matrix.md`](../traceability-matrix.md) の工程で管理。文書には書かない |
| ドキュメントID | **ファイル名で代替する。** `arc-screen-list.md` 等が一意 |
| ドキュメント名 | 各文書の見出し（H1） |
| 作成者 | **省略。** 個人開発であり、Git の履歴が担う |
| 作成日付・更新日付 | メタ情報に記載 |
| バージョン | メタ情報の「版」 |
| 更新者 | **省略。** 同上 |
| 成果物のID・名称・概要 | 各文書のメタ情報と冒頭の説明 |

**省略した項目は、Git とファイル名が同じ役割を果たすためである。**
複数人が別々に文書を編集する状況では必要になるが、個人開発では冗長になる。

⚠️ **将来、共同開発へ移行する場合は省略を見直すこと。**

### 3.4 ⚠️ 画面一覧の2つの使い方（v0.2で追加）

REF-16 は、画面一覧に**用途に応じた2つの書き方**があるとしている。

| 用途 | 記述内容 |
| --- | --- |
| 画面設計を進める | 構成要素をすべて記載する |
| 設計の進捗管理表として使う | No.、画面ID、画面名称のみでよい |

`paper-repro` は**前者を採る。** 進捗管理は
[`../traceability-matrix.md`](../traceability-matrix.md) が担うため、
画面一覧を進捗表として二重に使わない。

### 3.5 ⚠️ 記述範囲の境界（v0.2で追加）

REF-16 は、画面入出力項目一覧と画面アクション明細の**記述範囲を明確に分けている**。
この境界を守らないと、同じことを2箇所に書くか、どちらにも書かないことになる。

| 成果物 | 書くこと | **書かないこと** |
| --- | --- | --- |
| 画面入出力項目一覧 | **単一項目**の外部仕様（型、桁数、入力制約、初期表示） | データ構造との関連。ユーザ操作の観点以外の内容 |
| 画面アクション明細 | イベントに対して発生する動作 | **単一項目の外部仕様**（入出力項目一覧が担う） |

**両者は補完関係にある。** 項目1つの制約は入出力項目一覧、
複数項目にまたがる処理や画面全体の動作はアクション明細が扱う。

⚠️ **「データ構造との関連」は [`arc-datamodel.md`](arc-datamodel.md) が扱う。**
入出力項目一覧に DB のカラム名を書かない。

## 4. ID体系

**画面まわりのIDをここで確定する。** 文書をまたいで同じものを指すため、
先に決めないと突き合わせができない。

| 対象 | 記法 | 例 | 規則 |
| --- | --- | --- | --- |
| 画面 | `S-nn-mm` | `S-01-01` | `nn` は画面グループ、`mm` はグループ内の連番 |
| 画面グループ | `nn` | `01` | 利用者から見た機能のまとまり。10刻みにしない |
| 画面項目 | 画面内の連番 | `1` `2` `3` | 画面IDと組で一意（`S-01-01` の `3`） |
| アクション | `A-nn-mmm` | `A-01-001` | `nn` は画面グループ、`mmm` は連番 |
| 画面遷移 | `T-nn` | `T-01` | ひとまとまりの遷移図に1つ |
| 共通ルール | `CR-nn` | `CR-01` | ルールの節ごと |

**要求ID（`REQ-Cxx`）と実装単位（`F-xx`）は既存のものを使う。** 新設しない。

### 4.1 IDを揃える約束

- 画面レイアウト・画面入出力項目一覧・画面アクション明細の**3節で、同じ画面項目には同じ番号**を使う。
- 画面遷移のイベント名と、画面アクション明細のイベント名を**一致させる**。
- 画面一覧に無い画面を、先に画面レイアウトから起こさない。**一覧が先である。**
- **アクションID `A-nn-mmm` は、[`arc-behavior.md`](arc-behavior.md) の処理ID `P-nn-mmm` と
  `nn`・`mmm` を揃える。** 揃えないと画面と処理の突き合わせができない。

## 5. 完了の判定：合意成熟度の読み替え

REF-16 は合意成熟度を**仕掛・充実・完成**の3レベルで表す。
`paper-repro` では、これを [`../traceability-matrix.md`](../traceability-matrix.md) の
工程へ次のように対応づける。

| 成熟度 | 本プロジェクトでの意味 | TM の工程 |
| --- | --- | --- |
| **仕掛** | 画面の存在と役割が決まった。画面一覧に行がある | 要求 ✅ |
| **充実** | 遷移・レイアウト・入出力項目・アクションが書かれ、抜けを検査した | 設計 ✅ |
| **完成** | 実装され、テストが通り、**画面で操作して確認した** | 画面 ✅ |

> **「完成」に画面での確認を含めた。** ガイドは外部設計工程までを対象とし、
> 実装は範囲外としている。しかし `paper-repro` は
> [`../roadmap.md`](../roadmap.md) の開発方針で「画面で確認できない項目は完了にしない」と
> 定めており、そちらを優先する。**ガイドからの意図的な逸脱である。**

## 6. 4つの作業の適用

REF-16 は合意形成を**言い切る／聞き切る・図表に書く・もれ／矛盾をチェックする・
一緒にレビューする**の4つの作業で説明している。個人開発での扱いを定める。

| 作業 | `paper-repro` での扱い |
| --- | --- |
| 言い切る／聞き切る | **USDM が担う。** 要求・理由・仕様を書き切ることが「言い切る」にあたる |
| 図表に書く | 本書の枠組みに沿って各工程成果物を書く |
| もれ／矛盾をチェックする | **機械的な検査を優先する**（6.1節） |
| 一緒にレビューする | **対面の相手がいない。** 代わりに、AIエージェントへ設計を読ませて指摘を求め、その指摘を記録する |

**3番目を機械検査に寄せたのは、1人では見落としに気づけないためである。**
目視のチェックリストは、書いた本人が読むと通ってしまう。

### 6.1 機械検査の項目

| 検査 | 内容 |
| --- | --- |
| 件数の照合 | 画面一覧の行数と、`screens/` のファイル数が一致するか |
| IDの一致 | 画面一覧の `S-nn-mm` と、`screens/` のファイル名が一致するか |
| イベント名の一致 | 画面遷移のイベント名と、アクション明細のイベント名が一致するか |
| 項目番号の一致 | レイアウト・入出力項目一覧・アクション明細の3節で、同じ項目に同じ番号か |
| 対応の網羅 | 画面一覧の全画面が、いずれかの仕様（`REQ-Cxx`）に対応するか |
| **成果物間の整合** | **第8章の観点**（v0.2で追加） |

## 7. 文書の枠組み

新規に作る3文書の章立てを、ここで確定する。

### 7.1 `arc-screen-list.md`（画面一覧）

| 章 | 内容 |
| --- | --- |
| メタ情報 | 版・作成日・準拠する標準（3.3節の共通情報を兼ねる） |
| 一覧表 | 1行＝1画面。列は下記 |
| ツリー図 | 画面の階層構造を Mermaid で |
| 画面グループの定義 | `nn` の割り当てと、その根拠 |
| 未確定の画面 | 存在は決まったが役割が固まっていないもの |

**一覧表の列**: `No.` / 画面ID / 画面名 / 分類 / 階層 / 説明 / 対応要求（`REQ-Cxx`）/
実装単位（`F-xx`）/ 想定利用者 / 備考

**「対応要求」列を独自に追加した。** ガイドの構成要素は機能名・機能IDだが、
`paper-repro` は USDM で要求を管理しているため、そちらへ繋ぐ。

### 7.2 `arc-screen-flow.md`（画面遷移）

| 章 | 内容 |
| --- | --- |
| メタ情報 | 同上 |
| 遷移図 | Mermaid。**1図＝1つの完結した利用の流れ** |
| 正常系と異常系 | 線種で区別する |
| イベント一覧 | 遷移を起こすイベントと、対応するアクションID |
| **条件分岐** | **分岐の条件と、条件に対応する遷移先**（v0.2で明示） |
| 経路による分岐 | `course=reading` / `reproduction` の違い（`REQ-C01`） |

⚠️ **REF-16 は画面遷移の記述内容として、条件分岐がある場合はその条件と
分岐遷移を書くことを求めている。** `paper-repro` は承認ゲートで分岐するため、
この観点が特に重要である。

### 7.3 `arc-screen-rules.md`（画面遷移・レイアウト共通ルール）

REF-16 が挙げる構成要素8種に沿って章を立てる。

| 章 | 決めること |
| --- | --- |
| ページの構成要素 | 画面をどのエリアに分けるか、各エリアの用途 |
| 配色 | キーカラー、アクセントカラー、フォントカラー |
| 文字フォント・サイズ | 書体、サイズ、行間 |
| 全体構造とナビゲーション | 階層構造、ナビゲーションの表示 |
| 画面遷移パターン | エリアごとの遷移の型 |
| エラー表示方法・エラーメッセージ | 分類、表示位置、書式 |
| ユーザの定義 | 利用者の分類 |
| 制約事項 | 画面サイズ、ブラウザ、性能 |

**`paper-repro` 固有として次を追加する。**

| 追加する章 | 理由 |
| --- | --- |

## 8. ⚠️ 工程成果物間の整合（v0.2で追加）

**前身 REF-15 は「第7章 工程成果物間」を独立章として設けていた。**
後継 REF-16 では章として現れないが、観点そのものは失われていない。

**個人開発ではこの観点が最も抜けやすい。** 1人で全成果物を書くため、
書いた本人の頭の中では整合しているつもりになり、文書間の食い違いに気づけない。

### 8.1 揃えるべき対応関係

```
画面一覧（S-nn-mm）
  ├─→ 画面遷移（T-nn）        … 一覧の全画面が遷移図に現れるか
  ├─→ 画面レイアウト           … 一覧の全画面にファイルがあるか
  │     ├─→ 画面入出力項目一覧  … レイアウトの全項目が表にあるか
  │     └─→ 画面アクション明細  … レイアウトの全ボタンにアクションがあるか
  └─→ 共通ルール（CR-nn）      … 個別画面がルールに違反していないか
```

### 8.2 検査すべき食い違い

| 食い違い | 兆候 | 対処 |
| --- | --- | --- |
| 一覧にあるが遷移図に無い | どこからも到達できない画面 | 遷移を足すか、画面を削る |
| 遷移図にあるが一覧に無い | 一覧の更新漏れ | 一覧へ追加する |
| レイアウトの項目が入出力項目一覧に無い | 仕様が未定義の項目 | 一覧へ追加する |
| ボタンがあるがアクション明細に無い | 押しても何も起きないボタン | 明細を書くか、ボタンを削る |
| アクション明細のイベント名が遷移図と違う | 表記ゆれ | 名称を統一する |
| 共通ルールに反する個別画面 | 配色や配置の不統一 | ルールへ合わせるか、例外として記録する |

**6.1節の機械検査へ、これらを組み込む。**

### 8.3 振舞い編との整合

画面編の成果物は、[`arc-behavior.md`](arc-behavior.md) の成果物とも対応する。

| 画面編 | 振舞い編 | 対応 |
| --- | --- | --- |
| アクション（`A-nn-mmm`） | 処理（`P-nn-mmm`） | **`nn`・`mmm` を揃える**（4.1節） |
| 画面遷移（`T-nn`） | 状態遷移（`TR-nn`） | **別物。混同しない**（8.4節） |

### 8.4 ⚠️ 画面遷移と状態遷移は別物

| | 画面遷移（画面編） | 状態遷移（振舞い編） |
| --- | --- | --- |
| 何が変わるか | 表示される画面 | プロジェクトの状態（DB上の値） |
| 契機 | 利用者の操作 | 処理の完了、承認、外部イベント |
| 対応 | **1対1ではない** | 同上 |

**画面が変わっても状態は変わらないことがあり、その逆もある。**
1つの図に混ぜて描かない。

## 9. USDM・TM との連結

**画面は仕様から導く。** 思いついた画面を並べるのではない。

```
REQ-Cxx（要求）
  └─ REQ-Cxx-Rn.mm（仕様）
       └─ S-nn-mm（画面）
            ├─ 画面項目（入出力項目一覧）
            └─ A-nn-mmm（アクション）
                 └─ P-nn-mmm（処理。振舞い編）
```

`arc-screen-list.md` の「対応要求」列と、
[`../traceability-matrix.md`](../traceability-matrix.md) 第5章の交差表で、
**双方向に辿れるようにする。**

### 9.1 対応が付かないものの扱い

| 状況 | 扱い |
| --- | --- |
| 仕様に対応する画面が無い | **仕様の実現手段が未定。** 画面一覧の「未確定の画面」へ記録する |
| 画面に対応する仕様が無い | **要求の裏づけが無い画面。** USDM へ仕様を足すか、画面を削る |

**後者を放置しない。** 根拠のない画面は、作った本人しか理由を説明できなくなる。

REF-16 は6つの技術領域を扱う。`paper-repro` での作成順序を定める。

| 順 | 編 | 担当文書 | 状態 | 理由 |

| 5 | バッチ | `arc-batch.md` | ⬜ | Celery のジョブ。フェーズ2以降 |
| 6 | 帳票 | `arc-report.md` | ⬜ | 照合レポートと zip 出力。フェーズ5以降 |

### 10.1 ⚠️ 既存の `arc-datamodel.md` との差

`arc-datamodel.md` v1.0 は **REF-16 のデータモデル編に準拠して作ったものではない。**
DDL と状態遷移表を先に確定させる目的で、独自の構成で書いた。

**このまま「データモデル編に相当する」とは言えない。** 6編を揃える段階で、
データモデル編の工程成果物と突き合わせ、不足があれば補う。
それまでは**準拠していないことを明記して扱う。**
