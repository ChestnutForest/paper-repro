## 1. ⚠️ 対象領域の読み替え（本書で最も重要）

### 1.1 ガイドが想定する対象

REF-16 は外部インタフェースを次のように定義している。

> 開発対象となる**業務システム**とそれ以外の**業務システム**（同一企業内／企業外を問わず）
> との間で発生する**データのやりとり**

**企業の業務システム間の連携を想定している。** 受注データを基幹系へ送る、といった場面である。

### 1.2 `paper-repro` の外部連携との差

`paper-repro` が連携する相手は、業務システムではない。

| 連携先 | 種別 | ガイドの想定との差 |
| --- | --- | --- |
| arXiv | 公開Webサービス | 相手は不特定多数向け。**交渉相手が存在しない** |
| GitHub | 公開Webサービス | 同上 |
| Claude API | 商用API | 同上。加えて**従量課金** |

**ガイドが前提とする「相手システムの担当者と仕様を合意する」という構図が成り立たない。**
仕様は先方が一方的に定め、こちらは従うだけである。

### 1.3 読み替えの方針

| ガイドの区分 | `paper-repro` での読み替え |
| --- | --- |
| 同一企業内で同一システム | **該当なし** |
| 同一企業内の外部システム | **該当なし** |
| 社外の外部システム | **すべてここに該当する** |
| 新規のインタフェース | 該当なし（先方の仕様に合わせる） |
| 既存でインタフェースの変更が必要 | 該当なし |
| 既存でインタフェースの変更は不要 | **すべてここに該当する** |

**この区分は `paper-repro` では意味を持たない。** 全連携が「社外・既存・変更不可」に
分類されるため、区分によって扱いが変わらない。

### 1.4 ⚠️ 代わりに区別すべきこと

ガイドの区分が効かない代わりに、`paper-repro` 固有の区別が必要である。

| 区別 | 内容 | なぜ重要か |
| --- | --- | --- |
| **課金の有無** | 無償（arXiv、GitHub）／従量課金（Claude API） | コスト上限の管理対象が変わる |
| **利用規約の制約** | レート制限、自動取得の可否、再配布の可否 | 違反すると遮断される |
| **失敗時の影響** | 取り込み不能／読解不能／実行不能 | どこまで縮退できるかが変わる |
| **代替の可否** | 代替手段があるか | 障害時の設計が変わる |

**これらは工程成果物の一覧に列を足して扱う**（4.1節）。

**外部API呼び出しに関する規則は未整備であった。**

| 規則 | 状況 |
| --- | --- |
| 外部サービスの識別（arXiv、GitHub、LLM API） | ✅ `BR-02` にある |
| 取得値に取得元・取得日時・対象版を伴わせる | ✅ `BR-02` にある |
| APIエラーの表示（安定コードと人向けメッセージの分離） | ✅ `BR-07` にある |
| 著作権・ライセンスの保存 | ✅ `BR-08` にある |
| **レート制限** | ❌ **無い** |
| **コスト上限と、達したときの停止** | ❌ **無い** |
| **リトライ・タイムアウト** | ❌ **無い** |
| **呼び出し失敗時の縮退** | ❌ **無い** |

⚠️ **`BR-12`「非同期処理とサンドボックス」は外部API呼び出しの規則ではない。**
同ルールは「ネットワークは原則遮断」と定めており、**隔離実行環境の話**である。
外部APIを呼ぶ文脈とは逆である。

**したがって、上の表の「振舞い編」欄は、現時点では担い手が不在である。**
外部IF一覧の作成時に、`arc-behavior-rules.md` へ `BR-13` として追記する必要がある
（9章の未解決事項）。本書側で定義すると、責務が二重になる。

## 3. 作成する工程成果物

REF-16 は外部インタフェースについて**4つの工程成果物**を定義している。

| # | 工程成果物 | 略称 | 担当文書 | 時期 |
| --- | --- | --- | --- | --- |
| 1 | **外部インタフェース一覧** | 外部IF一覧 | [`arc-interface-list.md`](arc-interface-list.md) | ⬜ **最初に着手** |
| 2 | **外部システム関連図** | — | [`arc-interface-map.md`](arc-interface-map.md) | ⬜ 一覧と同時 |
| 3 | **外部インタフェース項目説明** | 外部IF項目説明 | [`interfaces/`](interfaces) のIFごと | ⬜ 枠のみ |
| 4 | **外部インタフェース処理説明** | 外部IF処理説明 | 同上（同じファイル内） | ⬜ 枠のみ |

### 3.1 一覧を最初に作る理由

[`arc-artifact-order.md`](arc-artifact-order.md) の原則に従う。
**一覧に載ったインタフェースについて、関連図・項目説明・処理説明を書く。**

⚠️ **本編には「共通ルール」に相当する成果物が無い。** 画面編・振舞い編と異なる点である。
外部API呼び出しの共通規則は、**振舞い編の共通ルールが扱うと定めた**（2.3節）。
⚠️ **ただし当該規則は未整備である。** 同節の注記を参照。

### 3.2 3と4を1つのファイルにまとめる理由

**同じインタフェースについて書くもの**である。項目説明（何を送受信するか）と
処理説明（どう送受信するか）を別ファイルにすると、片方の更新を忘れる。

**1インタフェース1ファイルとし、その中を2節に分ける。**

### 3.3 ⚠️ 記述範囲外

原文は次を範囲外と定めている。

> インタフェースに用いられる**データの作成ロジック**、および
> **システム内に保持されるデータとの関係**

`paper-repro` での扱いを次のとおり定める。

| 範囲外の事項 | 担当 |
| --- | --- |
| 取り込んだデータをどう加工するか | 振舞い編（業務説明） |
| 取り込んだデータをどのテーブルに保存するか | [`arc-datamodel-definitions.md`](arc-datamodel-definitions.md) |

**本書には DB のカラム名を書かない。** 外部システムとやりとりする形式だけを扱う。

## 4. ID体系

| 対象 | 記法 | 例 | 規則 |
| --- | --- | --- | --- |
| 外部インタフェース | `IF-nn` | `IF-01` | 連番。系統でグループ分けしない |
| 外部システム | `EX-nn` | `EX-01` | 連番 |
| データ項目 | IF内の連番 | `1` `2` `3` | インタフェースIDと組で一意 |

**`nn` を系統で分けない理由**：外部システムは3〜5個程度で、増えても十数個である。
グループ分けする規模ではない。**振舞い編の `B-nn-mmm` とは方針が異なる。**

### 4.1 振舞い編とのID対応

```
B-02-002（論文のメタ情報を取得する）  ← 振舞い編
  └─ IF-01（arXiv 論文取得）          ← 本書
       └─ EX-01（arXiv）              ← 本書
```

**外部連携を伴う業務は、対応する `IF-nn` を持つ。**
[`arc-behavior-list.md`](arc-behavior-list.md) の該当業務に、IF-ID の列を足す必要がある。

## 5. 完了の判定：合意成熟度の読み替え

基本は [`arc-screen.md`](arc-screen.md) 第5章と同一とし、外部IF固有の判定基準を定める。

| 成熟度 | 本プロジェクトでの意味 | TM の工程 |
| --- | --- | --- |
| **仕掛** | 連携先と目的が決まった。一覧に行がある | 要求 ✅ |
| **充実** | 項目説明・処理説明が書かれ、**先方の公式仕様と突き合わせた** | 設計 ✅ |
| **完成** | 実装され、**実際に接続して応答を確認した** | 実装 ✅ |

### 5.1 ⚠️ 外部IF固有の判定基準

**「先方の公式仕様と突き合わせた」を充実の条件とした。**
外部インタフェースの仕様は**こちらが決められない**。推測で書いた仕様書は、
実装時に必ず食い違う。

| 条件 | 確認方法 |
| --- | --- |
| 項目定義が正しい | **先方の公式ドキュメントのURLと参照日を記録** |
| 実際に接続できる | 実接続のテストが通る |
| **失敗時に業務が止まらない** | **接続失敗時のテストが通る** |
| レート制限を守る | 制限値を記録し、超えない設計になっている |

**3番目を必須とした。** 外部システムは**こちらの都合と無関係に落ちる**。
正常系だけのテストでは、障害時の挙動が検証できない。

## 6. 文書の枠組み

### 6.1 `arc-interface-list.md`（外部インタフェース一覧）

REF-16 の構成要素に沿いつつ、1.4節の区別を列として足す。

| 章 | 内容 |
| --- | --- |
| メタ情報 | 版・作成日・準拠する標準 |
| 一覧表 | 1行＝1インタフェース。列は下記 |
| 外部システムの一覧 | `EX-nn` の定義。公式ドキュメントのURLと参照日 |
| 未確定のインタフェース | 存在は決まったが仕様が固まっていないもの |

**一覧表の列**（★は `paper-repro` 独自）:

`No.` / 外部IF-ID（`IF-nn`）/ 外部IF名称 / 接続先システム（`EX-nn`）/ **出力・入力の識別** /
**既存・新規の識別** / ★課金 / ★レート制限 / ★失敗時の影響 / ★代替の可否 /
対応業務（`B-nn-mmm`）/ 対応要求（`REQ-Cxx`）

⚠️ **「既存・新規の識別」は原文の構成要素だが、`paper-repro` では全て「既存」になる**
（1.3節）。列は残すが、全行同じ値になることを注記する。

### 6.2 `arc-interface-map.md`（外部システム関連図）

| 章 | 内容 |
| --- | --- |
| メタ情報 | 同上 |
| 関連図 | Mermaid。本システムと外部システムの関係 |
| 方向の表記 | 出力（送り出し）と入力（受け取り）を線種で区別 |
| ★依存の強さ | 落ちたときの影響度を色または注記で示す |

**構成要素**（原文）: 本システムの名称 / 外部システムの名称 /
外部IF名称・ID / 方向

### 6.3 `interfaces/IF-nn.md`（項目説明＋処理説明）

| 節 | 内容 |
| --- | --- |
| 書誌情報 | IF-ID・名称・接続先・対応業務・**公式ドキュメントのURLと参照日** |
| 1. 項目説明 | 送受信するデータ項目の定義 |
| 2. 処理説明 | 呼び出しの手順、事前条件、本処理、終了条件 |

**項目説明の構成要素**（原文）: 外部IF-ID / 名称 / 全体レコード長 / 階層レベル /
繰り返し数 / 項目名 / 型 / 桁数・サイズ / 可変長・固定長 / 設定元データ / 項目説明

⚠️ **「全体レコード長」「可変長・固定長」は固定長ファイルを想定した項目である。**
`paper-repro` は JSON でやりとりするため、**該当しない項目は「—」とする。**
代わりに **JSON のネスト構造**を階層レベルで表す。

**処理説明の構成要素**（原文）: 接続先相手システム名 / 接続先プラットフォーム /
送・受信の識別 / データ量 / 全体レコード長 / 保存期間 / 保存場所 /
処理説明（事前条件）/ 処理説明（本処理）/ 処理説明（終了条件）

⚠️ **「保存期間」「保存場所」は、取得したデータをどこにどれだけ置くかである。**
`paper-repro` では**著作権とライセンスに関わる**ため、特に重要になる。
論文本文をどれだけ保持してよいかは、arXiv のライセンスによって決まる。
