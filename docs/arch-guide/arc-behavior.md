## 2. ⚠️ 合意形成の前提の読み替え

読み替えの基本は [`arc-screen.md`](arc-screen.md) 第2章と同一とし、
本書では**システム振舞い固有の差**を記す。

### 2.1 振舞いに固有の齟齬

画面は目に見えるため、齟齬があれば気づきやすい。**振舞いは目に見えない。**

実際、フェーズ0-1では `can_transition` の役割を取り違え、**承認ゲートを
通り抜ける実装が生まれた**（[`../devlog/devlog-2026-08-25.md`](../devlog/devlog-2026-08-25.md)）。

### 2.2 AIエージェントとの合意

実装を担う AIエージェントは、処理の意図を推測で補いうる。特に次が危うい。

| 危うい箇所 | 起こりうる誤り |
| --- | --- |
| 承認ゲート | 承認済みの判定を緩め、人手を介さず次工程へ進める |
| 状態遷移 | 定義にない遷移を許す |
| エラー処理 | 失敗を握りつぶして正常終了として扱う |
| 非同期ジョブ | 完了判定を自然言語の応答で行う |

### 2.3 画面編との責務の分担

| 対象 | 担当 |
| --- | --- |
| 画面に何を表示するか | 画面編 |
| どのボタンで何が起きるか（アクション名） | 画面編（`A-nn-mmm`） |
| **その業務の処理内容** | **本書**（`B-nn-mmm`） |
| **業務がどの状態からどの状態へ遷移させるか** | **本書**（`ST-nn`） |
| 失敗をどう画面に見せるか | 画面編 |
| **画面を伴わない処理**（バッチ、定期実行） | **本書** |

### 2.4 ⚠️ 「システム利用作業」と「機能」の区別（v0.2で追加）

**REF-16 は、システム化業務を2種類に分けている。** この区別が本書の要である。

| 種別 | 定義 | `paper-repro` の例 |
| --- | --- | --- |
| **システム利用作業** | 人とシステムのやり取りに関わる処理 | 論文URLの入力、方針の承認、自己説明の記入 |
| **機能** | システムによって自動化される処理 | 論文の取り込み、spec草案の生成、サンドボックス実行 |

**この区別は `paper-repro` の human-in-the-loop 設計と直結する。**
承認ゲートは**システム利用作業**であり、自動化してはならない。
2.2節で挙げた「承認を緩める実装」は、システム利用作業を機能として扱った誤りである。

**システム化業務一覧では、両者を列で区別する**（7.1節）。

| 2 | **システム化業務フロー** | 業務全体の中で**システム化する部分を識別**したもの | [`arc-behavior-flow.md`](arc-behavior-flow.md) | ⬜ 一覧の次 |

### 3.1 ⚠️ v0.1 からの変更点

v0.1 は6成果物としていたが、**原文は4つである。** 対応は次のとおり。

| v0.1 | v0.2 での扱い |
| --- | --- |
| 業務フロー ＋ システム化業務フロー | **1つに統合。** 原文の「システム化業務フロー」が両方を含む |
| 機能一覧 | **システム化業務一覧**へ改称 |
| 機能処理内容 | **システム化業務説明**へ改称 |
| 状態遷移 | **ガイドの成果物ではない。** 3.4節で扱う |
| 処理・機能共通ルール | **システム振舞い共通ルール**へ改称 |

⚠️ **v0.1 が「業務フローとシステム化業務フローを統合する」と書いたのは、
結果的に正しかった。** 原文の「システム化業務フロー」は、業務全体を俯瞰する
流れ図の中でシステム化部分を識別したものであり、初めから両方を含んでいる。

### 3.2 システム化業務一覧を最初に作る理由

**原文は、この成果物の役割を「目次」と定義している。**
他の3つは、一覧に載った業務について詳しく書くものである。
一覧が無ければ、何を書くべきかが決まらない。

v0.1 は状態遷移を最優先としたが、**それはガイドの成果物ではない。**
順序をガイドに合わせる。

⚠️ **順序の根拠と、逆にした場合に何が起きるかは
[`arc-artifact-order.md`](arc-artifact-order.md) にまとめた。**
6編に共通する原則であるため、各編に同じ説明を書かない。

### 3.3 記述粒度と範囲（v0.2で追加）

原文は、システム化業務一覧の記述粒度と範囲を次のように定めている。

| 項目 | 内容 |
| --- | --- |
| 記述粒度 | **「場所」「時間」「作業者」で区分される業務の単位** |
| 範囲外 | 開発対象外である**外部システムのシステム化業務** |

`paper-repro` での読み替えを次のとおり定める。

| ガイドの区分 | `paper-repro` での意味 |
| --- | --- |
| 場所 | **画面**（`S-nn-mm`）。同じ画面で行う作業はまとめる |
| 時間 | **フェーズ**（Phase 0〜6）。段階が変われば別の業務 |
| 作業者 | **利用者／システム／外部サービス** |

⚠️ **arXiv、GitHub、Claude API 側の処理は範囲外である。**
本書が扱うのは、それらを呼び出す `paper-repro` 側の業務までとする。

### 3.4 ⚠️ 状態遷移の扱い（v0.1 からの重要な変更）

**状態遷移は REF-16 の工程成果物ではない。** しかし `paper-repro` には
`states.py` に実装があり、承認ゲートの中核でもある。

**扱いを次のとおり定める。**

| 観点 | 決定 |
| --- | --- |
| ガイドの成果物か | **いいえ。** `paper-repro` 独自の追加である |
| どこに書くか | **[`arc-behavior-state.md`](arc-behavior-state.md) として独立させる** |
| 位置づけ | 4成果物の**補助資料**。ガイド準拠の枠外であることを明記する |
| 理由 | 実装が先行しており、設計文書が無い状態が危うい |

⚠️ **「ガイドに準拠した成果物」と「独自の追加」を混ぜない。**
混ぜると、後から読む人がどこまでがガイド由来か判断できなくなる。

### 3.5 ⚠️ 既存実装との突き合わせ

`arc-behavior-state.md` は、**新規に設計するのではなく、既存実装を文書化して
検証する**ことから始める。

| 手順 | 内容 |
| --- | --- |
| 1 | `states.py` の `ProjectState` と `ALLOWED_TRANSITIONS` を表に起こす |
| 2 | [`arc-datamodel.md`](arc-datamodel.md) の状態遷移表と突き合わせる |
| 3 | USDM の `REQ-C06`（承認ゲート）が要求する遷移と照合する |
| 4 | 差分を「実装の誤り」「設計の欠落」「意図的な差」に分類する |

## 5. 完了の判定：合意成熟度の読み替え

基本は [`arc-screen.md`](arc-screen.md) 第5章と同一とし、振舞い固有の判定基準を定める。

| 成熟度 | 本プロジェクトでの意味 | TM の工程 |
| --- | --- | --- |
| **仕掛** | 業務の存在と役割が決まった。一覧に行がある | 要求 ✅ |
| **充実** | フロー・業務説明が書かれ、**実装と突き合わせて差分を解消した** | 設計 ✅ |
| **完成** | 実装され、**異常系を含めて動作を確認した** | 実装 ✅ |

### 5.1 ⚠️ 振舞い固有の判定基準

画面編は「画面で操作して確認」を完成の条件とした。**振舞いは目に見えない。**

| 条件 | 確認方法 |
| --- | --- |
| 正常系が動く | テストが通る |
| **定義にない遷移が拒否される** | **状態遷移の異常系テストが通る** |
| **承認なしに次工程へ進めない** | **承認ゲートの迂回を試みるテストが通る** |
| 失敗が握りつぶされない | エラー時に状態が正しく設定されるテストが通る |

**2番目と3番目を必須とした。** 2.2節の誤りは、正常系のテストでは検出できない。

## 6. 4つの作業の適用

基本は [`arc-screen.md`](arc-screen.md) 第6章と同一である。

| 作業 | `paper-repro` での扱い |
| --- | --- |
| 言い切る／聞き切る | **USDM が担う。** 特に `REQ-C06`（承認ゲート）を書き切る |
| 図表に書く | フロー図・状態遷移図を Mermaid で書く |
| もれ／矛盾をチェックする | **機械的な検査を優先する**（6.1節） |
| 一緒にレビューする | AIエージェントへ設計を読ませて指摘を求め、記録する |

### 6.1 機械検査の項目

| 検査 | 内容 |
| --- | --- |
| 件数の照合 | 一覧の行数と、`behaviors/` に書かれた業務数が一致するか |
| 種別の網羅 | 全業務が**システム利用作業／機能のいずれかに分類**されているか |
| **承認ゲートの分類** | **承認を伴う業務が、機能でなくシステム利用作業になっているか** |
| 状態の一致 | `ST-nn` と `states.py` の `ProjectState` が一致するか |
| 遷移の一致 | `TR-nn` と `ALLOWED_TRANSITIONS` が一致するか |
| 孤立状態の検出 | 入る遷移／出る遷移が無い状態が無いか |
| 対応の網羅 | 全業務がいずれかの仕様（`REQ-Cxx`）に対応するか |

⚠️ **「承認ゲートの分類」を追加した。** 2.4節の区別が守られているかを機械的に検査する。

| 入出力のデータ | 業務間で受け渡すデータ |
| 承認ゲートの明示 | **利用者のレーンに置く**（2.4節） |
| 経路による分岐 | `course=reading` / `reproduction` の違い |
| 異常系の流れ | 失敗したときの戻り先 |

⚠️ **原文は「業務全体において、システム化する範囲を明示的に表す」ことを
この成果物の役割としている。** システム化しない部分も描き、その中で
システム化部分を識別する。

### 7.3 `behaviors/B-xx.md`（システム化業務説明）

**業務グループごとに1ファイル**とし、その中に業務を並べる。

| 節 | 内容 |
| --- | --- |

⚠️ **原文は「利用者とシステムの間の相互作用に関する仕様書」と定義している。**
内部の実装詳細ではなく、**使い方**を書く。

### 7.4 `arc-behavior-rules.md`（システム振舞い共通ルール）

**原文が挙げる記述内容**に沿って章を立てる。

| 章 | 原文の項目 | `paper-repro` での内容 |
| --- | --- | --- |
| 利用者の定義 | 利用者の定義 | 論文を読む人。役割の区分 |
| 拠点 | 拠点 | **該当なし**（単一環境） |
| フローの構成要素 | システム化業務フローの構成要素 | 記号、レーン、線種の約束 |

| 準拠すべき規則 | 準拠すべき規則 | ライセンス、著作権、コスト上限 |

| **長時間処理の進捗通知** | 画面を閉じても処理は続く |

## 8. ⚠️ 工程成果物間の関連（v0.2で追加）

**前身 REF-15 は「第5章 工程成果物間の関連」を独立章として設けていた。**
画面編（REF-15 第7章）と同じ構成である。

### 8.1 揃えるべき対応関係

```
システム化業務一覧（B-nn-mmm）
  ├─→ システム化業務フロー（BF-nn）  … 一覧の全業務がフローに現れるか
  ├─→ システム化業務説明             … 一覧の全業務に説明があるか
  └─→ 共通ルール（BR-nn）            … 個別の業務がルールに違反していないか
```

### 8.2 検査すべき食い違い

| 食い違い | 兆候 | 対処 |
| --- | --- | --- |
| 一覧にあるがフローに無い | どの流れにも現れない業務 | フローに足すか、業務を削る |
| フローにあるが一覧に無い | 一覧の更新漏れ | 一覧へ追加する |
| 一覧にあるが説明が無い | 内容が未定義の業務 | 説明を書く |
| **種別が未分類** | **システム利用作業か機能か決まっていない** | **2.4節の基準で分類する** |
| 共通ルールに反する業務 | 表記の不統一 | ルールへ合わせるか、例外として記録する |

### 8.3 画面編との整合

| 画面編 | 本書 | 対応 |
| --- | --- | --- |
| アクション（`A-nn-mmm`） | システム化業務（`B-nn-mmm`） | **`nn` を揃える** |
| 画面遷移（`T-nn`） | 状態遷移（`TR-nn`） | **別物。混同しない** |

### 8.4 ⚠️ 画面遷移と状態遷移は別物

| | 画面遷移（画面編） | 状態遷移（本書・独自） |
| --- | --- | --- |
| 何が変わるか | 表示される画面 | プロジェクトの状態（DB上の値） |
| 契機 | 利用者の操作 | 業務の完了、承認、外部イベント |

**画面が変わっても状態は変わらないことがあり、逆もある。**

## 9. USDM・TM との連結

```
REQ-Cxx（要求）
  └─ REQ-Cxx-Rn.mm（仕様）
       └─ B-nn-mmm（システム化業務）
            ├─ A-nn-mmm（画面アクション。画面を伴う場合）
```

### 9.1 対応が付かないものの扱い

| 状況 | 扱い |
| --- | --- |
