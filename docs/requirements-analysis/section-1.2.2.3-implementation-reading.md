## 4. 新しいメイン要求を追加しない理由

- `REQ-C05:4`は、公式実装読解からコード生成、隔離実行、サニティチェック、論文値照合までを
  支援範囲として選択済みである。
- 上位の「1.2.2」分析で、論文記述と公式実装の対応、差異、省略および確認不能箇所を扱う
  `REQ-C05-S01`が既に定義されている。
- 実装の入手可能性と検査可能性は、独立した利用者目標ではなく、`REQ-C05-S01`の対応状態として
  表現できる。
- 論文と実装の不一致時の扱いは、`REQ-C07:4`の証拠比較、`REQ-C08:4`のプロヴェナンス、
  `REQ-C10-S04`の主張区分を組み合わせて扱える。

したがって、メイン要求の選択をやり直さず、既存サブ要求1件を詳細化して変更案の根拠を強化する。

## 5. サブ要求の詳細化

### 5.1 REQ-C05-S01：論文記述と版付き公式実装の対応・差異・検査可能性

#### 要求文案

システムは、論文の節、主張、数式、図表または擬似コードを、公式実装のリポジトリ、版、コミット、
タグ、ファイル、シンボル、行範囲、Notebookセル、設定および配布物へ双方向に対応付けるものとする。
対応関係は、一致、実装詳細、論文での省略、版差、意図的変更、バグ候補、原因不明、入手不能または
検査不能として記録し、論文と実装の双方を保持する。どちらを判断の根拠に採用するかは、対象実験との
版整合、証拠および利用者の承認理由とともに保存し、一方を自動的に常時優先しないものとする。

#### 最小受入基準

- 論文箇所から対応コードへ、コードから論文箇所へ移動できる。
- 実装のURL、リポジトリ所有者、コミット、タグ、ハッシュ、取得日時およびライセンスを保存できる。
- ファイル、シンボル、行範囲、Notebookセル、設定ファイル、モデル配布物を対応対象として区別できる。
- 論文で報告された実験と参照実装の版が一致するかを、一致、候補、未確認、不一致として記録できる。
- 不一致を、一致、実装詳細、論文での省略、版差、意図的変更、バグ候補、原因不明として保留できる。
- 公開状態を、ソース検査可能、Notebook検査可能、バイナリ・モデルのみ、APIのみ、非公開、取得不能、
  版不明として区別できる。
- 情報不足または検査不能を推測で埋めず、確認不能箇所と追加調査項目を保持できる。
- 論文と実装の両方を証拠として残し、利用者の採用理由、訂正、レビューおよび承認履歴を保存できる。
- 実装を実行する場合は、既存のサンドボックス、承認、ネットワーク制限、資源上限を迂回しない。

## 6. 補強する既存要求

### 6.1 REQ-C07:4：情報源の不一致と採用根拠

論文と実装を異なる証拠種別として併記し、不一致を隠さず、版整合、対象実験との関係、確認可能性、
採用理由を人間が承認する。公式であることだけを正しさの保証にはしない。

### 6.2 REQ-C08:4：実装対応のプロヴェナンス

論文箇所からコード、Notebook、設定、配布物、実行結果、利用者訂正までを、版と生成・変換条件を
含めて双方向追跡する。対応関係の追加・変更・取消も履歴として保持する。

### 6.3 REQ-C10-S04：不足情報・著者評価・宣伝的表現の区分

情報の非公開または不足という観察事実と、秘匿理由、宣伝性、意図に関する解釈を分離する。
不足情報から研究の真偽、不正、商業上の意図をLLMだけで確定しない。

## 7. 要求として固定しない記述

| 記述 | 判定理由 | 取り扱い |
|---|---|---|
| 論文と実装が違う場合は常に実装を信じる | 版差、設定差、意図、バグ、公開後の修正があり得る | 双方を保持し、対象実験との版整合と証拠から人間が判断する |
| GPT-2の正規表現を製品処理へ固定する | 対象小節で具体例として紹介された実装詳細である | 対応付け機能のテストデータまたは教材例に留める |
| annotated-transformerまたはJupyterを必須サービスにする | 有用な資料・媒体の例であり、代替形式が存在する | Notebookを対応対象の一種として扱い、特定サービスへ固定しない |
| GitHubスター数を正しさや採用条件にする | 人気と正しさ、対象版、利用者の目的は一致しない | 取得時点付き参考情報としてのみ扱う |
| GPTシリーズの情報量低下を全モデルへ一般化する | 著者の観察例であり、版や公開方針によって変化する | 対象資料ごとの公開・検査状態として記録する |
| 配布モデルが利用できれば構造も理解できるとみなす | 実行可能性とソース・構造の検査可能性は異なる | 公開、実行、検査、版特定を別々の状態にする |
| 情報不足を研究不正または意図的秘匿と自動判定する | 根拠が不足し、著者の意図を推定する危険がある | 観察事実、解釈、未確認を分離し、人間が判断する |

## 8. 既存方針との整合性

- `REQ-C05:4`の公式実装読解を、版付き双方向対応、差異分類、検査可能性の表示へ具体化する。
- `REQ-C07:4`に従い、論文と実装の不一致を隠さず、利用者が採用根拠を承認する。
- `REQ-C08:4`に従い、論文、コード、Notebook、設定、配布物、実行結果、訂正の由来を追跡する。
- `REQ-C10-S04`に従い、不足情報という事実と、秘匿・宣伝性に関する解釈を区別する。
- Python、Jupyter、GitHub、Kaggle等は例示として扱い、特定言語、媒体、ホスティングへ固定しない。
- 信頼できないコードのホスト直接実行禁止、サンドボックス、シークレット分離、コスト上限を維持する。
- 初期リリースのタイプB・Python中心の縦切り範囲は、この分析だけでは変更しない。

## 10. 結論と次の処理

「1.2.2.3 実装を読み解いて理解を深める」から、新しい独立メイン要求は見つからなかった。
一方、選択済みの`REQ-C05:4`を支える`REQ-C05-S01`について、対象小節に限定した要求文、
受入基準、禁止する自動優先・自動推定および影響範囲を詳細化できた。また、`REQ-C07:4`の
証拠比較、`REQ-C08:4`のプロヴェナンス、`REQ-C10-S04`の事実と解釈の区分が補強された。

次の処理は、本分析を上位分析と[`requirements-change-proposal.md`](../requirements-change-proposal.md)の
根拠参照へ追加し、続く「1.2.2.4」以降を同じ方法で限定分析することである。変更案の承認前は
`requirements.md`、製品設計、ロードマップ、製品コードを変更しない。
