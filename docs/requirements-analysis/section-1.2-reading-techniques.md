## 4. メイン要求候補

### 4.1 REQ-C10：批判的読解・成立条件検討支援

#### 要求文案

システムは、論文の重要な主張ごとに、前提条件、成立範囲、主張区分、実験条件、
不確実性、支持・反証情報および検討状態を構造化し、利用者が手計算、具体例、反例、
実装との突合によって妥当性を検討できるようにする。最終判断は人間が承認するものとする。

#### サブ要求候補

| ID | 要求内容 |
|---|---|
| `REQ-C10-S01` | 主張から前提条件、帰結、適用範囲、議論を追う深さを分離して記録する |
| `REQ-C10-S02` | データ、乱数、パラメータ、試行回数、エラーバー、比較条件などの実験設定を確認する |
| `REQ-C10-S03` | 手計算、具体例、反例、境界条件を作成・実行し、対象主張へ関連付ける |
| `REQ-C10-S04` | 事実、実験結果、推論、仮説、宣伝的表現を区別し、バイアスと不確実性を表示する |

#### 最小受入基準

- 重要主張ごとに、前提条件、成立範囲、証拠、不確実性、検討状態を表示できる。
- 情報不足を誤りと断定せず、未確認として保持できる。
- 利用者の計算、具体例、反例、再現結果を根拠へ関連付けられる。
- LLMの判断だけで検討済みまたは確定済みに変更できない。
- 論文の学術的真偽をシステムが最終判定しない。

#### 独立要求とする理由

`REQ-C04`は学習活動、`REQ-C07`は情報源の比較を中心としている。
本候補は理論、実験、実装を横断して主張の成立範囲を検討する独立した利用者価値を持ち、
リーディング画面、仮定・証拠台帳、承認ゲートへ影響するため、メイン要求候補とする。

### 4.2 REQ-C11：質問・対話・共同読解支援

#### 要求文案

システムは、論文や公式実装だけでは解決できない疑問を質問として管理し、少人数での議論、
著者への問い合わせ、ウェブ上の議論、生成AIとの対話から得られた回答を、情報源と由来を
明示して記録できるようにする。外部への送信または公開は、利用者の明示的な操作を必須とする。

#### サブ要求候補

| ID | 要求内容 |
|---|---|
| `REQ-C11-S01` | 未解決点から質問候補を作成し、対象箇所、質問理由、期待する回答を記録する |
| `REQ-C11-S02` | 勉強会、著者回答、ウェブ上の議論などの回答を、主体と媒体を区別して保存する |
| `REQ-C11-S03` | 生成AIを壁打ち相手として利用し、その回答を非確定情報として検証対象にする |
| `REQ-C11-S04` | 外部送信・公開前に、機密情報、著作権、公開範囲、相手への配慮を確認する |

#### 最小受入基準

- 質問を論文のページ、節、数式、図表、コード、未解決主張へ関連付けられる。
- 回答者、媒体、日時、公開範囲、原文、要約を記録できる。
- 著者回答、専門家意見、一般利用者の意見、AI回答を区別できる。
- AI回答は正しさが保証されないことを表示し、利用者の確認前に確定要求へ昇格させない。
- メール送信やウェブ公開を自動実行せず、利用者の明示的確認を要求する。

#### 独立要求とする理由

質問管理と外部対話は、情報源を受動的に比較する`REQ-C07`だけでは表現できない。
外部通信、共同作業、公開範囲、プライバシー、対話履歴という独立した状態と承認境界が必要になるため、
メイン要求候補とする。

## 6. 要求として固定しない記述

| 記述 | 判定理由 | 取り扱い |
|---|---|---|
| Google Drive、Notability、X、Reddit、alphaXivなどのサービス | 著者の利用例であり、製品を特定ベンダーへ固定する | 保存先・対話先アダプタの参考例に留める |
| 著者へ質問した場合の返信率 | 個人の経験値で、一般的なサービス水準ではない | 受入基準やKPIに使用しない |
| 論文と実装が違う場合は常に実装を優先する規則 | 不一致の原因は意図、版差、バグなど複数あり得る | `REQ-C07`に従い併記し、人間が採用理由を承認する |

## 7. 既存方針との整合性

- `REQ-C10`は学術的真偽を自動判定せず、成立条件と検討状態を整理する支援に限定する。
- `REQ-C11`は外部送信や公開を自動化せず、human-in-the-loopを維持する。
- AIとの対話は証拠そのものではなく、質問、推論、検証候補として扱う。
- 論文、実装、著者回答、専門家意見、ウェブ上の意見、AI回答は出典種別を分離する。
- 特定の保存サービス、SNS、LLMプロバイダへ固定しない。
- 信頼できないコードの隔離実行とシークレット分離に関する既存方針は変更しない。

## 9. 次の意思決定

1. `REQ-C10`と`REQ-C11`について、それぞれ5つの選択肢を作成する。
2. 各5択では、選択肢1〜4を具体案、選択肢5だけをLLMによる自動作成とする。
3. 利用者の選択理由、影響範囲、受入基準を決定台帳へ記録する。
4. 既存10件のサブ要求候補を、採用、修正、保留へ分類する。
5. 全ての選択後に要件定義変更案を更新する。
6. 更新した変更案が承認されるまで、確定要件、設計、ロードマップ、製品コードを変更しない。
