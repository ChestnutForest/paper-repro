### 1.1 検証で分かった限定

- Karpathy の記事は2016年で、**大規模言語モデル以前**である。執筆と発表の助言は現在も通用するが、実験の進め方に関する記述は前提が古い。
- Marek Rei の記事は2022年で、項目5に**事前学習済み大規模モデルでは early stopping の重要性が下がっている**という追記がある。著者自身が前提の変化を認めている。
- LiveResearchBench は**ウェブ検索にもとづく報告書生成**の評価であり、`paper-repro` が扱う**論文の再現実装**とは対象が異なる。

### 1.2 ⚠️ 確認できなかった記述

きっかけとなった資料は、LiveResearchBench から次の趣旨の一文を引いていた。

> 大半のシステムは深く探索するだけで、深く研究してはいない。

**この文はアブストラクトに存在しない。** 論文本文中の記述と思われるが、本書の作成時点では所在を特定できていない。

したがって**本書はこの一文を根拠として用いない。** 代わりに、アブストラクトで確認できた次の事実だけを用いる。

- 評価対象は17件の最先端システム（単一エージェントのウェブ検索、単一エージェントの深層調査、複数エージェント）である。
- 分析は、現在の強みと**繰り返し現れる失敗の型**を明らかにしたとしている。

⚠️ **5択の前に、当該記述の所在を確認すること。** 確認できなければ `AS-M-04` の根拠は弱いままである。

## 2. メイン要求候補

### `AS-M-01` 再現の判定に実行間のばらつきを含める

**根拠。** Marek Rei 項目10。乱数の種を固定しても GPU の並列演算では丸め誤差が生じ、同じ実験を繰り返すと結果が異なりうる。同氏は各実験を10回程度実行して平均を報告し、標準偏差または信頼区間も併せて示すことを勧めている。**単一の結果だけを報告する慣行は、後から再現しにくい高い値を示してしまうことがある**と指摘している。

**現行との関係。** [`../requirements.md`](../requirements.md) の `REQ-C05` は照合を定めるが、**複数回実行とばらつきの扱いは見当たらない**（未突合）。1回の実行値と論文値を比べるだけでは、一致・不一致の判定が偶然に左右される。

**製品への意味。** 「再現できた」の定義に関わる。第0章の「再現」の水準の定義と衝突しないかを確認する必要がある。

⚠️ **本候補は新規ではない。** [`academic-research-skills-frameworks.md`](academic-research-skills-frameworks.md) が
ML再現性チェックリストを根拠に「実行回数と分散の記録」を新規候補として既に挙げている。
**本書は独立した第2の出典として、その候補の根拠を補強する位置づけである。** 5択では重複させず、1件として扱う。

### `AS-M-02` 評価コード自体を検証の対象にする

**根拠。** Marek Rei 項目8。モデルにバグがあれば性能が出ないので捨てられるが、**評価にバグがあると、動作していないモデルが高い値を出す**。同氏はこれを、公表後に結果が虚構と判明する事態として警告している。

**現行との関係。** サニティ階段（`REQ-C05`）はモデルの側を検査する。評価コードの側を検査する段は現行に見当たらない（未突合）。

**製品への意味。** タイプBの「オラクル満点」の段が近い。正解を与えたときに満点が出ることを確かめる操作は、評価コードの検証そのものである。**既存の段の目的を明示し直せば足りる可能性がある。**

⚠️ **`ARF-M-05` と混同しないこと。** [`academic-research-skills-frameworks.md`](academic-research-skills-frameworks.md) の
`ARF-M-05` は**論文から評価指標を抽出する**要求であり、読解の工程に属する。
本候補は**自分の評価コードにバグがないか検査する**要求であり、検証の工程に属する。**向きが逆であり、別の要求である。**

### `AS-M-03` データ分割の由来を記録する

**根拠。** Marek Rei 項目9・項目11。訓練・開発・テストの分割を分け、**先行研究がすでに分割している場合は同じ分割を使う**。強い理由なく新しい分割を作らない。同項目11は、まず先行研究の設定で同じデータを使い、その結果を再現できるか確かめることを勧めている。

**現行との関係。** `BR-02`（取得値に取得元・取得日時・対象版を伴わせる）と同じ発想だが、**データ分割は現行の記録対象に含まれていない**（未突合）。

**製品への意味。** 分割が違えば数値は当然ずれる。照合が不一致だったとき、**手法の差なのか分割の差なのかを区別できる**必要がある。

⚠️ **3候補のうち、本候補だけが新規の見込みである。** ML再現性チェックリストが求める記載項目
（[`academic-research-skills-frameworks.md`](academic-research-skills-frameworks.md) 108行）はデータセットを含むが、
**先行研究の分割を踏襲することまでは求めていない。** 5択で確認する。

### `AS-M-04` 縮退した調査結果を人間が主導して補う

**根拠（弱い）。** LiveResearchBench が「繰り返し現れる失敗の型」を明らかにしたとする記述、および同ベンチマークが引用の正確さと分析の深さを評価軸に含めていること。

⚠️ **1.2節のとおり、きっかけとなった資料が引いていた一文は未確認である。** 本候補は根拠が弱く、**5択に載せる前に所在を確認すべきである。**

**現行との関係。** `REQ-C01` の human-in-the-loop 方針および `BR-13` の縮退規則と重なる。**新規要求ではなく既存方針の補強にとどまる可能性が高い。**

## 3. 対象外と判断した領域

再調査を避けるため、判断と根拠を残す。

### 3.1 研究生活の管理は製品の範囲外

きっかけとなった資料と Karpathy の記事は、次を大きく扱っていた。いずれも `paper-repro` の対象外である。

| 領域 | 対象外とする理由 |
|---|---|
| 研究テーマの選定、6か月の日程 | 製品は**1本の論文**を読解し再現実装する。研究計画の管理は担わない |
| 指導教員・研究室の選び方 | 人間関係であり、製品が扱う対象ではない |
| 共同研究者のネットワーク構築 | 同上 |
| 発表・ポスター・質疑応答 | 製品の出力は画面と zip である（[`../worknotes/decision-batch-report-not-applicable.md`](../worknotes/decision-batch-report-not-applicable.md) 3節） |
| リバッタル、査読者としての役割 | 投稿工程は製品の範囲外 |
| キャリアパス、メンタル | 同上 |

⚠️ **Karpathy の記事のうち、コード公開と将来の自分に向けた文書化の節だけは製品に関係する。** ただし `REQ-C09`（成果物）と `BR-11`（保存）が既に扱っており、**新規要求は生じない。**

### 3.2 チーム規模と引用影響は製品の対象外

Journal of Informetrics の論文は、著者チームの規模が引用影響への構造的経路であることを構造方程式モデリングで示している。分野・資金・オープンアクセス経路によって引用の傾向が体系的に異なるとも報告している。

**しかし `paper-repro` は共著者数も引用数も扱わない。** 製品の対象は1本の論文の読解と再現実装であり、書誌計量ではない。**要求は生じない。**

⚠️ 同論文は**変換の選び方によって、実在する関連を検出できるかどうかが決まる**とも述べている。統計処理の選択が結論を左右するという指摘自体は、`REQ-C05` の照合にも通じる。ただしこれは `AS-M-01` に含まれる論点であり、別の要求にはしない。

### 3.3 実装の助言のうち、要求にならないもの

Marek Rei の助言には有用だが**要求にならない**ものが多い。開発の作法であって、製品が利用者へ提供する機能ではないためである。

| 助言 | 扱い |
|---|---|
| 項目1〜3（テンソルの形を確認する、assert を置く、出力を目視する） | 実装の作法。`AGENTS.md` の領域 |
| 項目6（バージョン管理と外部バックアップ） | 同上 |
| 項目7（ハイパーパラメータの調整） | 同上 |
| 項目16（まず最も単純な版を早く実装する） | ロードマップの縦切り方針と同趣旨。既に採用済み |
| 項目20（計算資源の割り当てを計画的に使う） | `BR-13` のコスト規則が扱う |
| 項目25〜37（執筆と投稿） | 3.1節のとおり対象外 |
| 項目38〜44（指導教員との関わり） | 同上 |

⚠️ **項目4（診断テスト）は要求にならないが、根拠にはなる。** 小さな訓練集合を暗記できるかを確かめる手法は、現行のサニティ階段の「1バッチ過学習」（[`../requirements.md`](../requirements.md) 91行・343行・385行）と同じ発想である。**現行設計が公開された助言と一致していることの裏づけになる。**
