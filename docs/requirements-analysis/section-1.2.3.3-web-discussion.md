## 5. 新規サブ要求候補：REQ-C07-S03

### 5.1 「1.2.3.2」との違いが要求を分ける理由

「1.2.3.2」の分析で確定した`REQ-C07-S02`は、照会由来の情報を扱う。しかし本小節が扱う
公開議論由来の情報は、次の点で性質が根本的に異なる。

| 観点 | 照会（1.2.3.2） | 公開議論（1.2.3.3） |
| --- | --- | --- |
| 発言者 | 論文の著者本人 | 不特定多数（著者を含む場合がある） |
| 内容の質 | 効果的な回答が期待できる | 的外れなコメントを含む |
| 取得の確実性 | 6〜7割は返信がある | 運の要素が大きい |
| 文脈の共有 | 個別に前提を説明できる | 短文で前提や意図の共有が難しい |
| 公開性 | 当事者に閉じる | 広く共有される |

両者を同じ「補完源」として同一に扱うと、**著者本人の回答と匿名の的外れなコメントを
区別できなくなる**。したがって、公開議論由来の情報について、発言者の属性、文脈の欠落、
質のばらつきを明示的に扱う要求を分けて定義する。

### 5.2 要求文案

システムは、公開の場（SNS、掲示板、論文に紐づく議論サービスなど）で得られた情報を
補完源として記録する場合、発言者の属性が確認済みであるか未確認であるかを区別して保持する
ものとする。発言が論文の特定箇所に対するものである場合、その対応関係を保持できるものとする。
公開議論由来の情報は、内容の妥当性が検証されていない候補として扱い、利用者が採否と理由を
記録するまで検証済みの結論へ昇格させないものとする。賛同数、閲覧数その他の反応量を、
内容の正しさの根拠として扱わないものとする。

### 5.3 最小受入基準

- 公開議論由来の情報を、出所、取得日時、対象の論文箇所または疑問へ関連付けて保存できる。
- 発言者の属性を、著者として確認済み、確認できない、その他として区別できる。
- **発言者が著者本人であることが確認できない場合、確認済みとして表示しない。**
- 論文の特定箇所に紐づく議論を、その箇所へ関連付けて保持できる。
- 公開議論由来の情報を、一次資料由来および照会由来の情報と区別して表示できる。
- 公開議論由来の情報を、利用者の採否判断なしに検証済みの結論へ昇格させない。
- 賛同数、閲覧数、返信数などの反応量を、内容の正しさの指標として提示しない。
- 内容が対象の疑問と無関係である場合、利用者が「該当しない」として記録できる。
- 短文により前提が不明な情報について、前提が不明である旨を保持できる。
- 特定の外部サービスが利用不能になった場合でも、取得済みの記録を参照できる。
- 外部サービスの利用規約または取得条件に反する自動収集を行わない。

## 6. 補強する既存要求

### 6.1 REQ-C07-S02：補完源としての公開議論

「1.2.3.2」で確定した`REQ-C07-S02`の「補完源」に、公開議論由来の情報を含める。
ただし、その扱いは`REQ-C07-S03`が定める区分に従う。公開議論の場で著者本人が回答した場合、
その回答は照会由来に準じて扱えるが、**発言者が著者本人であることの確認が前提**である。

### 6.2 REQ-C09-S03：公開の場での発信

本小節は、情報を発信することでコメントを得るという流れを述べている。これは学習成果を
外部へ出す行為であり、`REQ-C09-S03`が定める公開範囲の選択、公開前検査、秘匿情報の判断が
そのまま適用される。「積極的にコメントを書くとよい」という推奨も、既定の非公開と
明示的操作の原則を変えない。

### 6.3 REQ-C07-S01：情報源の種類と時点

公開議論由来の情報についても、種類（公開議論）、出所（サービス名、URL）、
取得時点を区別して表示する。

### 6.4 REQ-C09-S05：公開の場での著者とのやり取り（暫定）

公開の場で著者が回答した場合も、応答者に義務が生じない前提と、返礼の記録という
`REQ-C09-S05`の考え方が適用される。

### 6.5 REQ-C08:4：公開議論由来の情報のプロヴェナンス

情報の取得、発言者属性の判定、採否の判断、該当しないとした記録までを、
時点、出所、判断理由とともに追跡する。

## 7. 要求として固定しない記述

| 記述 | 判定理由 | 取り扱い |
| --- | --- | --- |
| 特定のサービス（X、Reddit、alphaXiv）と連携する機能を必須にする | 本文はalphaXivを試験的な取り組みとし、将来広く使われるかは非自明と明記している | 特定サービスへ依存しない記録の枠組みを扱う |
| システムが公開議論を自動収集する | 利用規約、取得条件、著作権に抵触しうる | 利用者の操作による記録を基本とする |
| 賛同数や反応量の多い意見を優先的に採用する | 反応量は内容の正しさを意味しない | 反応量を正しさの指標として扱わない |
| 公開議論での発言を著者の見解として扱う | 発言者が著者本人である確認が必要である | 属性が確認できない場合は確認済みとしない |
| 的外れなコメントをシステムが自動判定して除外する | 的外れかどうかは利用者の疑問との関係で決まる | 利用者が「該当しない」と記録できるようにする |
| 公開議論から得られる情報量や有用性を保証する | 本文は運の要素が大きいと明記している | 取得の確実性を約束しない |
| 短文の発言から前提をLLMが推定して補う | 前提の推定は`REQ-C10-S02`が禁じる推測補完に当たる | 前提が不明である旨を保持する |
| コメントの投稿を製品機能として提供する | 本文は外部サービスの利用を述べており、製品化の示唆はない | 投稿は外部サービス上で利用者が行う |

## 8. 既存方針との整合性

- `REQ-C07:4`に従い、公開議論由来の情報と一次資料の矛盾を消さず、人間が採用理由を決める。
- `REQ-C07-S02`との整合：補完源の枠組みに含めつつ、信頼性の扱いを`REQ-C07-S03`で分ける。
- `REQ-C09-S03`に従い、公開の場での発信も既定を非公開とし、明示的操作を必要とする。
- `REQ-C10-S02`に従い、短文で不明な前提を推測で補わない。
- `REQ-C08:4`に従い、取得と判断の由来を追跡する。
- human-in-the-loopの原則により、公開議論由来の情報の採否は利用者が判断する。
- 外部サービスの利用規約と取得条件を遵守し、自動収集を行わない。
- 初期リリースのタイプB・Python中心の縦切り範囲は、この分析だけでは変更しない。

## 10. 結論と次の処理

「1.2.3.3 ウェブ上で議論する」から、新しいメイン要求は見つからなかった。
本小節は、選択済みの`REQ-C07:4`・`REQ-C09:4`の範囲内で、公開の場での議論という
補完手段を扱っている。

一方、新規サブ要求候補`REQ-C07-S03`（公開議論由来の情報の扱い）を提案する。
これは「1.2.3.2」で確定した`REQ-C07-S02`だけでは扱えない性質——発言者が不特定多数であること、
的外れなコメントを含むこと、取得が運に左右されること、短文で前提の共有が難しいこと——を
明示的に扱うためである。

**両者を同一の「補完源」として扱うと、著者本人の回答と匿名の的外れなコメントを
区別できなくなる。** この区別は、`REQ-C07:4`が定める「矛盾を消さず、人間が採用理由を決める」
という原則を実装可能にするために必要である。

また、図1.8が示す「論文の特定箇所に紐づく議論」という形態は、`REQ-C09-S01`（電子的読解と
注釈）が扱う注釈と構造が近い。将来、外部の議論を自分の注釈と並べて参照する設計が
考えられるが、本分析では記録の枠組みまでに留める。

次の処理は、「1.2.3」配下の次の小節を同じ方法で限定分析し、その結果を踏まえて
`REQ-C07-S03`および`REQ-C09-S05`を確定するか統合するかを判断することである。
変更案の承認前は`requirements.md`、製品設計、ロードマップ、製品コードを変更しない。
