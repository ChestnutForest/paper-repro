## 4. 新しいメイン要求を追加しない理由

- 本小節は冒頭で「内容の理解そのものの技術ではない」と明記されており、独立した製品目的ではなく
  理解を深める手段として位置づけられている。
- 自分の言葉による説明と未理解点の記録は、上位の「1.2.2」分析で`REQ-C04-S02`として既に定義済みである。
- 公開範囲の選択と秘匿情報の扱いは、同分析で`REQ-C09-S03`として既に定義済みである。
- 公開による議論という副次効果は、外部との協働を扱う「1.2.3」の主題であり、本小節の根拠だけで
  独立したメイン要求へ昇格させると、後続小節の分析と重複する。
- 新しいメインIDを追加すると、同じ利用者価値を`REQ-C04`・`REQ-C09`と二重管理することになる。

したがって、メイン要求の選択をやり直さず、既存サブ要求2件を詳細化して変更案の根拠を強化する。

## 5. サブ要求の詳細化

### 5.1 REQ-C04-S02：自己説明による理解の輪郭化と未理解点の保持

#### 要求文案

システムは、利用者が理解したと考える内容を自分の言葉で記述できる自己説明の場を提供し、
説明できた部分、明快に言語化できなかった部分、未解決の疑問および次に深掘りする項目を
区別して保持するものとする。言語化できなかった箇所は欠落として扱わず、対象の論文箇所、
概念、数式または実装へ関連付けた未理解点として保存し、深掘り候補へ引き継げるものとする。
文章の流暢さ、分量または生成の完了をもって理解済みと自動判定せず、理解状態の確定は
利用者の操作によるものとする。

#### 最小受入基準

- 自己説明を、論文の節、数式、図表、実装箇所または概念へ関連付けて保存できる。
- 一つの自己説明の中で、説明できた部分と言語化できなかった部分を区別して記録できる。
- 未理解点を、対象、疑問の内容、気づいた時点、現在の状態とともに保存できる。
- 理解状態として、理解済み、部分理解、未理解、要再確認を区別できる。
- 未理解点を深掘り対象の候補として`REQ-C09-S02`のキューへ送り、対応状況を追跡できる。
- 自己説明の改訂履歴を保持し、以前の版と現在の版を比較できる。
- LLMが生成した補足説明と、利用者自身が書いた説明を区別して表示できる。
- 流暢さ、文字数または生成完了だけを根拠に、理解済みへ自動遷移しない。
- 利用者が自己説明を作成しないまま読解工程を進めることを妨げない。

### 5.2 REQ-C09-S03：学習成果の公開範囲と秘匿情報の判断

#### 要求文案

システムは、自己説明、注釈、読解メモ、計算結果および学習成果ごとに、非公開、限定共有、公開の
範囲を選択できるようにし、既定値を非公開とするものとする。外部送信または公開の前に、機密情報、
個人情報、認証情報、未公開の論文・実装・データ、著作権のある本文の転載、引用元およびライセンスを
確認し、利用者が対象範囲と内容をプレビューしたうえで明示的に操作した場合にのみ実行するものとする。
公開後に第三者から得られた指摘、質問または議論を、学習成果へ関連付けて記録できるものとする。

#### 最小受入基準

- 成果物ごとに非公開、限定共有、公開を選択でき、新規作成時の既定値は非公開である。
- 公開前に、公開先、公開範囲、公開内容および添付物をプレビューできる。
- 公開前検査で、機密情報、個人情報、認証情報、未公開資料、著作権上の懸念を警告できる。
- 検査結果を無視して公開する場合、利用者の明示的な確認と理由を記録できる。
- 利用者の明示的な最終操作なしに、外部送信または公開を実行しない。
- 秘匿対象と判断した成果物を、公開対象から恒久的に除外する設定を保持できる。
- 公開範囲の変更履歴、公開日時、公開先および取消操作を保存できる。
- 外部サービス側で取消が完了しない場合、その制約と残存する可能性を表示する。
- 公開した成果物への外部からの指摘、質問または議論を、対象成果物へ関連付けて記録できる。
- 外部からの指摘を、検証済みの結論と区別し、利用者が採否と理由を記録できる。
- 引用元、ライセンス、出典の表示が必要な素材を、表示なしで公開対象に含めない。

## 6. 補強する既存要求

### 6.1 REQ-C09-S02：未理解点から深掘り対象への接続

自己説明で明らかになった未理解点を、重要文献、データセット、関連実装の深掘りキューへ
候補として送れる。優先順位と理由は利用者が決定し、未理解であること自体は自動的な
優先度上昇の根拠としない。

### 6.2 REQ-C10-S01：理解の輪郭と読解深度の対応

自己説明で言語化できなかった箇所を、主張の前提、帰結または省略された推論のどこに
対応するかへ関連付けられる。読解深度の変更は利用者の操作によるものとし、自己説明の
存在だけで「導出を追跡」以上へ自動遷移しない。

### 6.3 REQ-C08:4：自己説明と公開過程のプロヴェナンス

自己説明の作成、改訂、理解状態の変更、公開範囲の変更、公開前検査の結果、外部からの
指摘の取り込みまでを、時点、操作者、判断理由およびレビュー履歴とともに追跡する。

## 7. 要求として固定しない記述

| 記述 | 判定理由 | 取り扱い |
| --- | --- | --- |
| すべての論文について自己説明を必須にする | 本文もアウトプット対象は読んだ論文のごく一部としている | 利用者が対象を選ぶ任意の工程とする |
| 自己説明を書かなければ次工程へ進めない | 本文はこの過程を経ずとも理解できる人の存在を認めている | 推奨として提示し、必須の関門にしない |
| 学習成果を常にウェブ公開する | 秘匿情報、著作権、個人情報、利用目的に反する場合がある | 非公開を既定とし、利用者が範囲を決める |
| 公開すれば理解が深まると保証する | 本文が示すのは副次効果であり、成立は文脈に依存する | 効果を約束せず、公開の選択肢と履歴だけを扱う |
| LLMが自己説明を代筆して理解済みにする | 理解の主体は利用者であり、代筆は理解の輪郭化にならない | 補助説明はLLM生成と明示し、理解状態は利用者が確定する |
| 説明の流暢さから理解度を採点する | 流暢さと理解は一致せず、本文も言語化の詰まりを手掛かりとしている | 詰まった箇所を未理解点として保持する |
| GitHubへの公開を前提の運用にする | 著者の実践例であり、利用者の環境や制約は異なる | 公開先を特定サービスへ固定しない |
| 外部からの指摘を正しい訂正として自動採用する | 指摘者の前提や目的も検証対象である | 指摘を候補として保持し、利用者が採否を決める |
| 未理解点の件数で理解度を数値評価する | 記録の粒度や対象選択に依存し、比較可能な指標にならない | 状態と対応履歴を表示し、単一スコア化しない |

## 8. 既存方針との整合性

- `REQ-C04:3`の学習支援を、自己説明と未理解点の保持という検証可能な単位へ具体化する。
- `REQ-C09:4`の論文ポートフォリオを、公開範囲管理と外部指摘の取り込みへ接続する。
- `REQ-C08:4`に従い、自己説明の改訂、理解状態の変更、公開操作の由来と判断履歴を追跡する。
- `REQ-C09-S02`に従い、未理解点を深掘りキューの候補として扱い、優先順位は利用者が決める。
- `REQ-C10-S01`に従い、理解状態と読解深度をLLMだけで確定しない原則を維持する。
- human-in-the-loopの原則により、外部送信と公開は利用者の明示的操作を必要とする。
- GitHub、ウェブ公開は著者の実践例として扱い、特定サービスへ固定しない。
- 初期リリースのタイプB・Python中心の縦切り範囲は、この分析だけでは変更しない。

## 10. 結論と次の処理

「1.2.2.5 アウトプットすることで理解を深める」から、新しい独立メイン要求は見つからなかった。
本小節は冒頭で内容理解そのものの技術ではないと位置づけられており、選択済みの`REQ-C04:3`と
`REQ-C09:4`の範囲内で表現できる。

一方、`REQ-C04-S02`について自己説明による理解の輪郭化と未理解点の保持を、`REQ-C09-S03`について
公開範囲の選択、秘匿情報の判断および外部からの指摘の取り込みを、対象小節に限定した要求文、
受入基準および禁止する自動判定まで詳細化できた。また、`REQ-C09-S02`の深掘りキューへの接続、
`REQ-C10-S01`の読解深度、`REQ-C08:4`のプロヴェナンスが補強された。

これにより、「1.2.2」の上位分析で挙げた既存サブ要求候補8件のうち、小節別の詳細検証が
すべて完了した。次の処理は、本分析を上位分析と[`requirements-change-proposal.md`](../requirements-change-proposal.md)の
根拠参照へ追加し、続く「1.2.3 自分以外の力も借りて論文を読み解くための技術」を同じ方法で
限定分析することである。変更案の承認前は`requirements.md`、製品設計、ロードマップ、
製品コードを変更しない。
