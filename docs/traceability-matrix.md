## 1. 本書の役割

**仕様ひとつひとつが、どの工程まで進んでいるかを1か所で見る。**

USDM は要求から仕様を漏れなく引き出す（[`requirements-usdm.md`](requirements-usdm.md)）。
しかし仕様が**実装され、テストされ、画面で確認され、リリースされたか**は、USDM だけでは追えない。
その対応づけを担うのが TM である。

| 文書 | 担うこと |
|---|---|
| [`requirements-usdm.md`](requirements-usdm.md) | 何を作るか（要求と仕様） |
| [`arch-guide/arc-datamodel.md`](arch-guide/arc-datamodel.md) | どう作るか（DDL・状態遷移） |
| [`arch-guide/arc-behavior-list.md`](arch-guide/arc-behavior-list.md) | どう振る舞うか（業務・フロー・入出力・例外・状態遷移） |
| **本書** | **どこまで進んだか、どのコードが対応するか** |
| [`roadmap.md`](roadmap.md) | いつ作るか（フェーズと確認画面） |
| [`arch-guide/arc-screen-list.md`](arch-guide/arc-screen-list.md) | どの画面で実現するか（仕様 → 画面IDの対応） |

## 2. ⚠️ XDDP 本来の TM との違い

**本書は XDDP の TM をそのまま使っていない。用途を広げている。**
その差を隠さず記録する。後から読む人が、XDDP の教科書と本書を見比べて混乱しないためである。

| 観点 | XDDP 本来の TM | 本書の TM |
|---|---|---|
| **目的** | **Where** — 変更がどこに影響するかを特定する | 同左に加え、**工程の進捗を追う** |
| **縦軸** | 変更仕様 | 仕様（変更に限らない） |
| **横軸** | 母体の**全モジュール**（関数・ファイル） | **工程**（要件定義〜リリース）と**実装単位** |
| **セルの意味** | 変更内容（`×→○` のように Before / After を書く） | 工程の状態、または対応するファイル |
| **前提** | 既存の母体がある（派生開発） | **母体が無い（新規開発）** |

### なぜ用途を広げたか

`paper-repro` は現時点で**新規開発**であり、XDDP が前提とする母体が無い。
変更箇所を特定する必要がまだ生じていない一方、**仕様が実装まで届いたかを追う必要は今ある。**

XDDP の適用事例にも、トヨタ自動車が従来の設計書を変更設計書として使ったように、
**組織の実情に合わせたテーラリングの前例がある**（[`references-usdm-ipa.md`](references-usdm-ipa.md) 1.5節）。

### 母体ができたら本来の形へ戻す

フェーズ1以降、既存のコードへ変更を加える場面が増える。そのとき、
**変更仕様 × ファイル・関数**の交差表（第5章）を、XDDP 本来の使い方で運用する。
本書は両方の表を持ち、局面に応じて使い分ける。

## 3. 工程と状態の記号

### 工程

| 工程 | 完了の条件 |
|---|---|
| **要求** | USDM で仕様として書き出されている |
| **設計** | DDL・API・画面・システム振舞いのいずれかで、実装できる粒度まで決まっている |
| **実装** | コードが存在する |
| **テスト** | 自動テストが存在し、通っている |
| **画面** | ブラウザで操作して結果が見える（[`roadmap.md`](roadmap.md) の確認画面） |
| **リリース** | 利用者が使える状態で公開されている |

### 状態

| 記号 | 意味 |
|---|---|
| ✅ | 完了 |
| 🔨 | 進行中 |
| ⬜ | 未着手 |
| — | 対象外（その仕様にその工程が無い） |

> **画面工程を独立させた理由。** 実装とテストが済んでも、利用者が操作できなければ
> この製品では未完成である（[`roadmap.md`](roadmap.md) の開発方針）。
> 実装に含めてしまうと、この判定ができなくなる。

### 4.2 集計

| 工程 | ✅ | 🔨 | ⬜ | 進捗 |
|---|---|---|---|---|
| 要求 | 28 | 0 | 0 | **100%** |
| 設計 | 28 | 0 | 0 | **100%** |

| **画面** | **0** | 0 | 28 | **0%** |
| リリース | 0 | 0 | 28 | 0% |

**この集計は手で数えない。** 次のコマンドで数え直す。手で書くと、
行を足したときに直し忘れて実態とずれる。

```powershell
$text = Get-Content -Raw -Encoding UTF8 'docs/traceability-matrix.md'
$start = $text.IndexOf('### 4.1')
$end = $text.IndexOf('### 4.2')
$rows = ($text.Substring($start, $end - $start) -split "`n") |
    Where-Object { $_ -match '^\| `R\d+\.\d+` \|' }
$names = @('要求', '設計', '実装', 'テスト', '画面', 'リリース')
for ($i = 0; $i -lt $names.Count; $i++) {
    $values = $rows | ForEach-Object { ($_ -split '\|')[$i + 3].Trim() }
    $counts = $values | Group-Object | ForEach-Object { "$($_.Name)=$($_.Count)" }
    "$($names[$i]): $($counts -join ', ')"
}
```

> **画面工程が0%であることが、いま最も重要な事実である。**
> 実装が29%進んでいるのに、**利用者が触って確かめた仕様は1つも無い。**
> [`roadmap.md`](roadmap.md) の開発方針に照らせば、`REQ-C01` はまだ1つも完了していない。

## 6. 更新の規約

### いつ更新するか

**仕様の状態が変わったときに、同じ変更の中で更新する。**
後でまとめて直すと、必ず実態とずれる。

| きっかけ | 更新する箇所 |
|---|---|
| USDM へ仕様を展開した | 第4章に行を追加し、要求工程を ✅ |
| 設計文書に落とした | 設計工程を ✅ |
| コードを書いた | 実装工程を ✅、第5章にファイルを記入 |
| テストを追加した | テスト工程を ✅ |
| **ブラウザで確認した** | **画面工程を ✅** |
| フェーズを完了した | リリース工程を ✅ |

### 何を正本とするか

| 項目 | 正本 |
|---|---|
| 仕様の内容 | [`requirements-usdm.md`](requirements-usdm.md) |
| フェーズの進捗 | [`roadmap.md`](roadmap.md) |
| **仕様ごとの工程の状態** | **本書** |

**本書は仕様の内容を書かない。** 要点欄は識別のための短い覚え書きであり、
内容が知りたければ `requirements-usdm.md` を見る。両方に書くと必ず食い違う。

### 集計の求め方

第4.2章の数は手で数えている。**仕様が増えたら数え直す。**
数が合わないと漏れの検出に使えないため、行を足したら必ず集計も直す。

## 7. 未解決の確認事項

- **画面工程の判定を誰が行うか。** 自動テストでは判定できない。
  確認した日付と確認者を記録する欄が要るかどうか。
- **`REQ-C06` のテスト先行をどう解消するか。** 要求を USDM へ展開したとき、
  既存テストが要求と食い違ったらどちらを直すか。
- **リリース工程の単位。** 仕様ごとか、フェーズごとか。現在はフェーズ単位を想定している。
- **第5章を全モジュールへ広げる時期。** XDDP 本来の使い方では、影響しないモジュールも
  横に並べる。現在は実装済みのファイルだけを載せている。
- **変更設計書を導入するか。** 母体が育ち、既存コードへの変更が増えた時点で判断する。
