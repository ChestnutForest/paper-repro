## 開発方針：画面で確認できない項目は完了にしない

**各開発項目には、それを画面で確かめる手段を必ず対にする。**
バックエンドだけを作って「テストが通ったので完了」とはしない。

### なぜこの方針にするか

フェーズ0-1で `course` を必須にしたとき、バックエンドの契約だけを変えてフロントエンドを
次回送りにした。結果、リポジトリが「バックエンドは正しいがアプリとしては型が通らない」
状態で一時的に止まった（[`devlog/devlog-2026-08-25.md`](devlog/devlog-2026-08-25.md) の教訓）。

**動くものを常に見えている状態に保てば、この種のずれがその場で分かる。**
また、要件 v0.2 の設計方針は human-in-the-loop であり、**人間が見て判断する画面**が
機能そのものである。画面が無い機能は、この製品では未完成に等しい。

### 完了の条件（3つすべてを満たす）

| # | 条件 | 確かめ方 |
|---|---|---|
| 1 | バックエンドが動く | `pytest` が通る |
| 2 | **画面から操作できる** | ブラウザで実際に触れる |
| 3 | **画面で結果が見える** | 変化が目で確認できる |

条件2・3を満たせない項目は、**画面側の作業を同じフェーズに含める。**
別フェーズへ送らない。送ると、上に書いたずれが起きる。

### 確認の手順

毎回、次の3つを起動したうえで、対応する画面を開いて確かめる。

```powershell
docker compose up -d
```

```powershell
backend\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --app-dir backend
```

```powershell
npm --prefix frontend run dev
```

投入する論文は [`test-papers.md`](test-papers.md) の**基準論文**を使う。
毎回同じ論文を使うことで、前回との違いが画面の差として現れる。

### 例外

**フェーズ2（非同期ジョブの背骨）だけは、単独では画面を持たない。**
Celery と Redis は他の機能を下から支える部品であり、それ自体に操作対象が無いためである。
代わりに、**フェーズ1の論文取り込みを非同期化して進捗バーで見せる**ことを確認手段とする。
「見えないから確認しない」ではなく、**見える機能に載せて確認する。**

## フェーズ0：土台の仕上げ（最優先）

土台に残る穴を塞ぐ。ここを固めてから機能を積む。

- **0-0. データモデル仕様を確定する** ✅ 完了（2026-08-25）
  [`docs/arch-guide/arc-datamodel.md`](arch-guide/arc-datamodel.md) **v1.0（確定）**。
  既存記述との矛盾9件の解消方針と、未決事項3件の決定を記録済み。
- **0-1. `projects` / `papers` を作り、PostgreSQL に永続化する** ← 次の一手
  現状は uvicorn 再起動でプロジェクトが消える。Docker で起動済みの PostgreSQL に保存する。
  **DDL・ENUM の値は `arc-datamodel.md` 3章に従う。**
  `course` は `NOT NULL`・既定値なしのため、`POST /projects` の変更を伴う（同 5.1）。
- **0-2. 状態遷移を動かす**
  `state` 1列を **`phase` × `status` の2列**へ分ける（同 2.1）。
  遷移表は同 3.4・3.5 に従い、`POST /projects/{id}/state` は**廃止する**（同 5.2）。

### フェーズ0の確認画面

| 開発項目 | 対にする画面 | 目で見る内容 |
|---|---|---|
| 0-1. 永続化 | ダッシュボード（`/`） | 基準論文で作成 → **uvicorn を再起動 → 一覧に残っている**。再起動前後の画面を見比べる |
| 0-1. `course` 必須 | 作成フォーム | コース未選択のまま作成しようとすると**進めない**。選ぶと作成できる |
| 0-2. 状態の2列化 | プロジェクトカード | `phase` と `status` が**別々のバッジ**で出る。1つのバッジではない |
| 0-2. 失敗からの復帰 | プロジェクトカード | 失敗させると `status` だけが `failed` になり、**`phase` は元の工程のまま**残る |
| 0-2. ゲートの迂回不可 | プロジェクトカード | 工程を飛ばす操作が画面に**存在しない**。`/policy` 以外の道が無い |

**0-2 の3行目と4行目が、この方針の効き所である。** 2列に分けた効果は、
テストでは「同じ」と「違う」しか分からないが、画面では**バッジが2つ並ぶ**ことで一目で分かる。

## 順序の設計理由

- **フェーズ0を最優先**：データが消える土台の上に機能を積んでも崩れるため。
- **フェーズ2（非同期）をフェーズ4より前**：重い処理の前に背骨を通す。逆順だと作り直し。
- **フェーズ4（サンドボックス）を後ろ**：最も難しくリスクが高いので、周辺が固まってから臨む。

## 技術選定メモ

### データベース：当面 PostgreSQL

- 現在の設計・雛形はすべて PostgreSQL 前提（docker-compose.yml, requirements.txt の psycopg, DATABASE_URL, 各設計文書）。
- 初期リリースの規模（プロジェクト数件〜）には PostgreSQL で十分。枯れていてトラブル時の情報も豊富。
- **DBアクセスは SQLAlchemy（ORM）経由で抽象化し、特定DB依存の機能を避ける。** → 将来のDB差し替えを容易にする保険。

### 将来のDB候補：TiDB（フェーズ6以降で再検討）

- **TiDB** は MySQL 互換の分散型DB。永久無料枠（5GBストレージ）あり。強みは「数十億行の大規模・分散処理」と「リアルタイム分析（HTAP）」、および「ネイティブなベクトル検索・フルテキスト検索」。
- **今は採用しない理由**：
  - 初期リリースの規模に対して過剰で、分散の強みが活きない。
  - 既存の雛形・設計がPostgreSQL前提で、切り替えると全面書き換えになる（フェーズ0の目的＝永続化とは無関係な作業）。
  - ローカル開発が複雑化する（今は `docker compose up -d` で完結）。
  - MySQL互換だが100%同一ではなく、挙動が異なる箇所のテストが必要。
- **再検討する条件**：
  - 多数ユーザーの同時利用など、大規模化してスケールが必要になったとき。
  - 論文の類似検索など、**ベクトル検索**が欲しくなったとき（TiDBのnative vector capabilitiesが効く可能性）。
  - フェーズ6以降の本格公開で負荷が上がったとき。
- SQLAlchemy 経由で抽象化しておけば、この時点での移行が容易になる。
