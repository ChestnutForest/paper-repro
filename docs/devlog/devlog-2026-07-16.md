## Q&A 知識カード

### Q. 論文再現ツールを「全自動」にできない理由は何か？
A. 手順の本質が、各Phaseの終わりに人間が方針を決めるゲート（human-in-the-loop、人間を処理の輪に入れる方式）にあるためである。方針の5択（フル再現／縮小版／読解＋改造／部分採用／見送り）、論文タイプの判定、オラクル満点の確認などを人間が承認する。これを飛ばすと精度が崩れる。よって製品像は伴走型パイプラインになる。
（出典: 本日の作業から）

### Q. このツールの最大の技術的リスクは何か？
A. サンドボックス実行である。論文の公式コードや生成コード（＝信頼できない第三者コード）を実行してサニティチェックする必要があり、これがツールの心臓部であると同時に最大のセキュリティリスクになる。ネットワーク原則遮断・リソース制限・使い捨てコンテナが必須要件となる。もう1つのリスクはAPIコストの暴走である。
（出典: 本日の作業から）

### Q. MVP（最小実行可能製品）をタイプB・公式実装ありに絞ると何が良いか？
A. GPUもレンダリング環境もLLM-as-a-Judge（別のLLMを審査員に使う採点）も不要になり、最大リスクであるサンドボックスを「CPUのみ・ネットワーク遮断」で済ませられる。これはStructEval-Tの実作業で「API課金ゼロ・システム依存ゼロで完結する」ことが実証済みである。
（出典: 本日の作業から）

### Q. バックエンドをPython（FastAPI）に寄せる理由は何か？
A. サニティチェック・スコア照合・ノートブック生成がすべてPython資産であり、会話中に作ったt_scorer.py（StructEval-T採点コード）がそのまま流用できるためである。フロントをTypeScript、バックをPythonに分けても、重い処理をPythonで一貫させるのが最も無駄がない。
（出典: 本日の作業から）

### Q. 設計における「非同期ジョブ＋WebSocket進捗」とは何を指すか？
A. 論文取り込み・リポジトリ読解・LLM推論・サンドボックス実行はどれも数十秒〜数十分かかるため、同期REST（リクエストを待たせる方式）では破綻する。代わりに「ジョブを投げてジョブIDを受け取り、進捗はWebSocket（双方向通信）でストリーム受信する」形を全エンドポイントの基本にする設計である。
（出典: 本日の作業から）

### Q. Claude Code の VS Code拡張を使うための前提バージョンは何か？
A. VS Code 1.98.0以上、Node.js 18以上が必要で、Anthropicの有料プラン（Pro／Max／Team／Enterprise、またはAPIキーの従量課金）が要る。拡張機能はCLI（コマンドラインツール）を内蔵しているため、チャットパネルを使うだけなら別途CLIを入れる必要はない。
（出典: Claude Code の VS Code 拡張の公式ドキュメント）
