# 動作確認に使うテスト論文

開発中に **画面で動作を確かめるために投入する論文**の一覧。

- 対象プロダクト: `paper-repro`
- 作成日: 2026年8月26日
- 関連: [`roadmap.md`](roadmap.md) の「開発方針：画面で確認できない項目は完了にしない」

## 使い方

各フェーズの開発項目を確認するとき、**基準論文を投入する。**
毎回同じ論文を使うことで、前回との違いが画面の差として現れる。
論文を変えると、変化が実装の差なのか論文の差なのか分からなくなる。

> **本ファイルは開発用の入力を管理するものであり、参考文献ではない。**
> 設計や規約の根拠として引用した文献は [`references.md`](references.md) が正本である。
> 本ファイルの論文は「読むための資料」ではなく「**動作確認のための入力データ**」として扱う。

### 概要

LLM が構造化された出力を生成する能力を測るベンチマーク。
JSON・YAML・CSV のような**描画を伴わない形式**と、HTML・React・SVG のような
**描画を伴う形式**の両方を扱う。18形式・44種類のタスクからなり、
自然言語から構造化出力を作る「生成」と、形式間で変換する「変換」の2系統で評価する。

### なぜこの論文を基準にするか

| 理由 | 内容 |
|---|---|
| **タイプB である** | 学習を伴わない。初期リリースの対象そのもの（要件 第8章） |
| **GPU が要らない** | サンドボックスの GPU 対応を待たずに、フェーズ4まで通せる |
| **公式実装がある** | フェーズ1の実装探索、フェーズ3のリポジトリ読解を実際に試せる |
| **照合できる数値がある** | o1-mini の平均 75.58 など、フェーズ5の ±5 判定を試せる具体値を持つ |
| **既に手を動かした実績がある** | 会話で作った `t_scorer.py` などの資産があり、比較の土台がある |
| **再利用が許される** | CC BY 4.0。出典を示せば利用できる |
| **改訂履歴が3版ある** | `REQ-C03-S01` が求める「版の履歴」の動作を実データで確認できる |

**最後の行は見落としやすいが重要である。** v1・v2・v3 があるため、
版を保持する仕組みが本当に動くかを、作り物のデータではなく実物で確かめられる。

### 期待する動作（フェーズごと）

| フェーズ | 投入したときに画面で見えるべきこと |
|---|---|
| 0 | 作成 → 再起動 → 一覧に残る |
| 1 | タイトルと Abstract が出る。**タイプ B と判定される** |
| 3 | spec 草案に18形式・44タスクの構造が反映される |
| 4 | サニティ階段でオラクル満点の段を通過する |
| 5 | 論文値との差が ±5 の判定で色分けされる |

## 追加の候補（未採用）

**当面は基準論文1本だけで進める。** 増やすのは、基準論文で確認できない挙動が
出てきたときに限る。数を増やすこと自体は目的ではない。

追加を検討する状況と、そのとき満たすべき条件を先に決めておく。

| 追加する状況 | 論文に求める条件 |
|---|---|
| 公式実装が無い場合の画面を確かめたい | 公式実装が存在しないタイプB論文 |
| タイプ A の判定を確かめたい（フェーズ2以降） | 学習を伴う論文。**GPU が必要になるため、実行はしない** |
| 取り込みの失敗系を確かめたい | 存在しない arXiv ID、または PDF のみで HTML が無い論文 |
| 多言語の論文を確かめたい | 英語以外の本文を含む論文 |

**追加するときは本ファイルへ、基準論文と同じ項目（URL・書誌・ライセンス・確認日・
採用理由）を揃えて記録する。** ライセンスの確認を省かない。

## 注意

- **論文の本文・図表をリポジトリへ置かない。** 記録するのは URL と書誌だけにする。
  CC BY 4.0 は再配布を許すが、リポジトリの目的は道具の開発であり、論文の配布ではない。
- 取り込みの動作確認で arXiv へ繰り返しアクセスする場合は、**間隔を空ける。**
  短時間に集中して叩かない。
- 画面の見た目を記録として残す場合（フェーズ6の README 用スクリーンショットなど）は、
  **論文の本文が大きく写り込まない構図**にする。
