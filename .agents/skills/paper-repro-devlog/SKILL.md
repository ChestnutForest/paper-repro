# 論文再現ツール開発ログの資産化（paper-repro-devlog）

## 利用元の前提

作業前に`paper-repro-skill-source-policy`で、このファイルがGitHub登録済みの
`.agents/skills/paper-repro-devlog/SKILL.md`であることを確認する。
個人領域、プラグインキャッシュ、他リポジトリの同名スキルは使用しない。

英語AI論文の読解〜再現実装ツール **paper-repro** の開発で、その日に得た学び・決定・つまずきを、
**1日1ファイルの構造化Markdown**に変換し、**NotebookLM のソース**として投入するためのスキル。

RAG（NotebookLM の検索）で後から引けることが最重要。**切り出された断片が単独で意味を持つように書く。**

このファイルは `paper-repro` リポジトリにおける本スキルの正本であり、Claude Code、Codex、
Antigravity IDEのいずれから利用しても同じ内容を基準にする。

## このスキルの位置づけと、隣接スキルとの境界

| スキル | 役割 | いつ使うか |
|---|---|---|
| **本スキル（paper-repro-devlog）** | 論文再現ツール自体の開発の日次ログ | 「今日の分を資産化して」— このツール開発の作業を残す |
| **research-log** | 企業との共同研究の日次ログ | 共同研究プロジェクトの学びを残す |
| **learning-asset** | CCAF・TOEIC等の資格学習の日次ログ | 資格勉強の学びを残す |
| **arxiv-paper-repro** | 論文の再現実装そのものの手順 | 論文を実装・再現するのが目的のとき |
| **english-parsing** | 英文解釈フォーマット | 英文を1本読んで解釈するのが目的のとき |

**発火の判断基準:** 「論文再現ツール（paper-repro）の開発作業で得た学びを、日次ファイルに残すのか」——ならば本スキル。
日々の開発（コードを書く、Git操作、設計を決める、つまずきを解決する）を1日の終わりに残す用途に限る。

## 出力手順

1. **その日の会話を読み返す。** 実際にやったこと・決めたこと・つまずいたこと・解決したことを拾う。
   **その日にユーザーがアップロードした画面キャプチャ（スクリーンショット）も、アップロードされた順にすべて拾い、「画面キャプチャ記録」章に1行ずつ書く。** 画像ファイル自体は埋め込めない（NotebookLMはテキスト検索のため）ので、「何の画面か＋結果」をテキストで記録する。
2. **JST の日付をシステムから取得する**（推測しない）。利用中の環境でJSTを取得し、Windows PowerShellなら`Get-Date -Format yyyy-MM-dd`を使う。
3. **前日までの累積を確認する。** 前日の `devlog-*.md` が会話中に貼られていれば、その累積頻度に本日分を足す。
   **無ければ捏造しない**（下の「正確性の制約」を厳守）。
4. **`docs/devlog/devlog-YYYY-MM-DD.md`を生成する**（下のテンプレートに沿う）。既存ファイルがある場合は、重複作成せず内容を統合する。
5. `docs/devlog/README.md`と必要な索引を同期し、リポジトリ内のファイルリンクを提示する。zipはユーザーが明示的に求めた場合だけ作る。

## ファイルテンプレート（devlog-YYYY-MM-DD.md）

RAG 出力先なので、**各セクション・各カードが単独で読めるように**書く（RAG制約は後述）。

```markdown
# 開発ログ: paper-repro — YYYY-MM-DD（JST）

## メタ情報
- 日付（JST）: YYYY-MM-DD
- 本日の作業範囲: <例: GitHubへの初回push / CLAUDE.mdへのi18n方針追記>
- 参照したソース URL:
  - <この日に見た公式ドキュメント・記事のURL。無ければ「本日は該当なし」>

## Q&A 知識カード
その日に理解したことを、問いと答えの形で残す。**各カードは単独で読めるように書く。**

### Q. <この日に理解したことを問いの形で。例: git push -u origin main の -u は何をするか？>
A. <答え。略語は展開し、照応表現を使わない。>
（出典: <URL または「本日の作業から」>）

### Q. <2つ目の問い>
A. <答え>
（出典: ...）

## 開発の型の出現記録
このプロジェクトの開発ならではの「型」を記録し、累積頻度を数える。
**前日ファイルが会話にある場合のみ累積を更新。無ければ本日分のみを書く。**

### 決定ログ（なぜその技術・設計を選んだか）
| 決定した事項 | 選んだ理由 | 却下した代替案 | 本日/累積 |
|---|---|---|---|
| <例: バックエンドをPythonに寄せる> | <評価資産がPythonにある> | <Node統一→二重実装> | 本日1 / 累積N |

### つまずき→解決の記録
| つまずき | 原因 | 解決方法 | 本日/累積 |
|---|---|---|---|
| <例: git addでLF/CRLF警告> | <改行コードの差> | <無視でよい/autocrlf true> | 本日1 / 累積N |

### Git・環境操作の記録
| 操作 | コマンド/手順 | 効果 | 本日/累積 |
|---|---|---|---|
| <例: 初回push> | <git push -u origin main> | <mainを追跡設定> | 本日1 / 累積N |

## 語彙・用語リスト（プロジェクト固有）
このプロジェクトで出た固有用語を、**毎回定義ごと**書く（RAGで単独で引けるように）。
| 用語 | 定義 |
|---|---|
| <例: タイプB（論文）> | <学習なしの論文。既製LLM＋プロンプト＋評価コードで構成> |
| <例: オラクル満点> | <正解相当の入力を評価器に入れ、満点が出るかで評価器の正しさを確かめる検証> |
| <例: i18n> | <internationalization。画面文言をt("キー")方式にして日英を切り替える仕組み> |

## 未解決の疑問と翌日の開発計画
- 未解決の疑問:
  - <例: サンドボックスをgVisorで組むときのネットワーク遮断の具体設定>
- 翌日の計画:
  - <例: CLAUDE.mdのStep 1に沿って、projects.pyのインメモリ保存をPostgreSQLに置き換える>

## 画面キャプチャ記録
その日にユーザーがアップロードした画面キャプチャ（スクリーンショット）を、**アップロードされた順に**、
実行ログ風に1行で記録する。画像ファイル自体は埋め込まず、**何の画面か＋結果**をテキストで書く（NotebookLMで検索できるように）。
画像が1枚も無かった日は「本日は画面キャプチャの共有なし」と書く。

| # | 何の画面か | 結果・状態 |
|---|---|---|
| 1 | <例: VS Codeでpaper-reproを開いた直後> | <ルートが正しく開けている。エクスプローラーに主要フォルダが見える> |
| 2 | <例: Swagger UIのGET /health実行後> | <Code 200、{"status":"ok"}が返り疎通確認成功> |
| 3 | <例: フロント画面 localhost:3000> | <プロジェクト一覧に2件表示、フロント↔バック連携成功> |
```

## 最重要の制約：RAG（NotebookLM）向けの書き方

出力先は NotebookLM で、**チャンク分割して検索**される。切り出された断片が単独で意味を持つように、次を必ず守る。

- **照応表現を禁止する。**「上記の通り」「前述の」「これ」を使わない。毎回、主語と対象を明示する。
- **略語を毎回展開する。**「CRLF」ではなく「CRLF（Windowsの改行コード、キャリッジリターン＋ラインフィード）」。
  「i18n」ではなく「i18n（internationalization、画面文言の多言語切り替え）」。
- **見出しを問いの形にする。**「pushの仕組み」ではなく「Q. git push -u origin main の -u は何をするか？」。
- **各 Q&A カードに出典を付ける**（URL、または「本日の作業から」）。

## 正確性の制約（捏造しない）

- **累積頻度など過去履歴が要るデータは、前日までのファイルが会話中に無ければ捏造しない。**
  無い場合は「**本日分のみ。累積更新には前日の devlog を貼ってください**」と明記する。
- **その日に実際にやったこと・分かったことだけを書く。** 網羅のために、やっていない一般論で埋めない。
  空欄は「**本日は該当なし**」と正直に書く。
- **原典の長い引用をしない。** 要点は自分の言葉で書き直す。

## 運用

- **JST の日付はシステムから取得する**。Windows PowerShellでは`Get-Date -Format yyyy-MM-dd`を使い、推測しない。
- 生成後は`docs/devlog/`の索引を同期し、利用中のAI開発環境が対応するリポジトリ内ファイルリンクを示す。
- NotebookLMへ追加する場合は、生成したMarkdownを「ソースを追加」からアップロードするよう案内する。

## やってはいけないこと

- ❌ 前日ファイルが無いのに、累積頻度の数字をそれらしく捏造する
- ❌ その日に触れていない設計・技術について、一般論で章を埋める
- ❌ 照応表現（「前述の」「これ」）を使い、RAG で断片が読めなくなる書き方をする
- ❌ research-log（共同研究）や learning-asset（資格学習）の領域の内容を、このファイルに混ぜる
