# 上流工程の独立

作業前に `paper-repro-skill-source-policy` で、このファイルが GitHub 登録済みの
`.agents/skills/paper-repro-upstream-isolation/SKILL.md` であることを確認する。
個人領域、プラグインキャッシュ、他リポジトリの同名スキルは使用しない。

## 1. 規律

⚠️ **上流工程の途中で、既存の実装とテストの状態を判断材料にしない。**

上流工程とは次を指す。

| 工程 | 成果物 |
|---|---|
| 要件定義 | `docs/requirements.md`、`docs/requirements-usdm.md`、`docs/requirements-decisions/` |
| 画面編の設計 | `docs/arch-guide/arc-screen-*.md`、`screens/` |
| システム振る舞い編の設計 | `docs/arch-guide/arc-behavior-*.md`、`behaviors/` |
| データモデル編の設計 | `docs/arch-guide/arc-datamodel-*.md` |
| 外部インタフェース編の設計 | `docs/arch-guide/arc-interface-*.md`、`interfaces/` |

### 1.1 始めてはいけないこと

上流工程の途中で、次を**自分から提案しない。着手しない。**

- 開発環境の起動（`scripts/start-dev.ps1`、Docker、uvicorn、Next.js）
- Swagger UI やブラウザでの動作確認
- データベースのテーブルとスキーマの確認
- テストの実行
- ロードマップ・設計文書と実装の突き合わせ調査
- 「実装はどうなっているか」を確かめるためのコード読解

### 1.2 やってよいこと

**コードを根拠として引用することは禁じない。** 禁じるのは、上流の判断のために
**実装の現状を調べに行く**ことである。

| 行為 | 可否 |
|---|---|
| 要求文の根拠として既存コードの docstring を引く | ✅ 可 |
| 実装単位（`F-xx`・`B-xx`）との対応を文書上で確かめる | ✅ 可 |
| 動作を確かめるために環境を起動する | ❌ 不可 |
| 「どこまで実装済みか」を調べて上流の順序を変える | ❌ 不可 |

## 2. 例外

次の場合は本スキルを適用しない。

| 場合 | 従う規約 |
|---|---|
| 実装工程・テスト工程に入っている | [`AGENTS.md`](../../../AGENTS.md) 第9章、[`roadmap.md`](../../../docs/roadmap.md) の確認画面 |
| 利用者が実装の確認を明示的に求めた | 利用者の指示 |
| 上流の作業そのものが動かせない（環境が壊れて文書を編集できない等） | 復旧を優先する |

⚠️ **`AGENTS.md` 第9章「機能を追加・変更したときは画面で確かめる」は実装工程の規律である。**
上流工程では機能を追加・変更しないため、この条項は掛からない。

## 3. ずれに気づいたときの扱い

上流工程の途中で、実装や下流文書とのずれに気づくことがある。
**調査へ移らず、記録に留めて上流の作業を続ける。**

### 3.1 記録する場所

| 気づいた内容 | 記録先 |
|---|---|
| ロードマップの記述が実装と合わない | `docs/worknotes/` に1行足すか、その工程の成果物に注記 |
| 設計文書と実装が食い違う | 同上 |
| 要求と実装単位の対応が怪しい | 該当する要求の節へ「要確認」として残す |

### 3.2 記録に書くこと

- 気づいた内容（1〜2文）
- **確認する工程**（実装工程かテスト工程か）
- 気づいた時点（日付）

⚠️ **その場で確認しないと決めたことを書く。**
書かないと、後から見た人が検討漏れと誤解する。

## 4. なぜこの規律が要るのか

### 4.1 実測（2026年9月7日）

要件定義の途中で「ロードマップと実装のずれ」に気づき、**実機で確かめることを提案した。**
結果は次のとおりである。

| 項目 | 実測 |
|---|---|
| 費やした時間 | 13:55 から 16:04 までの約2時間 |
| その間のコミット | **0件** |
| 要件定義の前進 | **なし** |
| 得られた成果物 | 起動スクリプトの修正1件（`86ea643`） |

途中で遭遇したのは、`.ps1` の BOM 欠落、`try/catch` による Docker 判定の誤り、
`.venv` に埋め込まれた旧パス、`ruff.exe` によるファイル占有、
テーブルのスキーマ不一致である。**どれも要件定義の判断材料にならなかった。**

最終的に利用者が「実装状況の確認は止めます」と打ち切り、要件定義へ戻った。

### 4.2 動機そのものが誤っていた

ずれを直すために実機確認を勧めたが、**ずれの解消は要件定義に必要ではなかった。**
要件定義の途中で下流の状態を気にしたことが起点である。

⚠️ **上流の判断に、下流の現状は要らない。**
要らないものを調べると、調べた対象の問題（環境、依存、スキーマ）に時間を取られる。

### 4.3 同じ失敗が既に記録されている

[`arc-artifact-order.md`](../../../docs/arch-guide/arc-artifact-order.md) 第3章は
「⚠️ 実際にこの失敗をしている」という節を持つ。

`arc-behavior.md` v0.1 は「**実装が先行していて設計文書が無いから**」という理由で
状態遷移を最優先の成果物とした。v0.2 でそれが工程成果物でないと判明し、手戻りした
（[`reflection-arc-behavior-v02.md`](../../../docs/worknotes/reflection-arc-behavior-v02.md)）。

同節は結論をこう書いている。

> **この失敗は、順序を独自に決めたことから生じた。**

⚠️ **実装の存在に引きずられて上流の順序を変える**という点で、4.1の実測と同じ種類である。
**文書化済みの失敗を繰り返した。**

---

## 5. 提案しそうになったときの判定

上流工程の途中で「確かめよう」と言いそうになったら、次を問う。

1. **その確認の結果で、いま書いている文書の内容が変わるか。**
   変わらないなら確認しない
2. **変わるとして、それは上流で決めるべきことか。**
   実装を動かさないと決まらないなら、`paper-repro-requirement-deferral` に従って後工程へ送る
3. **利用者が求めたか。**
   求めていないなら提案しない

⚠️ **1で「変わるかもしれない」と思ったときが最も危ない。**
2026年9月7日の実測では、変わる見込みがあると考えて着手し、**何も変わらなかった。**

---

## 6. 禁止事項

- 上流工程の途中で開発環境の起動を提案する
- 上流工程の途中でテストを実行して結果を判断材料にする
- 「実装がこうなっているから」を理由に上流の順序や内容を変える
- ずれに気づいて、記録せずに調査へ移る
- ずれに気づいて、記録もせずに無視する
- 実装工程・テスト工程で本スキルを持ち出し、動作確認を省く
- 他プロジェクトへこのスキルを適用する
- 同じ本文を `.claude/skills` や `docs/skills` へ複製する
