## 1. 方針

**要求項目は2つに分ける。**

| 区分 | 扱い |
|---|---|
| 今の要件定義で決められるもの | **決める。** 保留にしない |
| 後工程を実施しないと決められないもの | **後工程へ送る。** その工程で決める |

**後工程**とは次を指す。

| 工程 | 成果物 |
|---|---|
| 画面編の設計 | `docs/arch-guide/arc-screen-*.md`、`screens/` |
| システム振る舞い編の設計 | `docs/arch-guide/arc-behavior-*.md`、`behaviors/` |
| データモデル編の設計 | `docs/arch-guide/arc-datamodel-*.md` |
| 外部インタフェース編の設計 | `docs/arch-guide/arc-interface-*.md`、`interfaces/` |
| 実装 | `backend/`、`frontend/` |
| テスト | `backend/tests/`、画面での確認 |

⚠️ **バッチ編と帳票編は対象外である**（[`arc-artifact-order.md`](../../../docs/arch-guide/arc-artifact-order.md) 5節）。

### 1.1 この方針が既存の規約と矛盾しない根拠

| 規約 | 記述 | 帰結 |
|---|---|---|
| [`requirements-update-workflow.md`](../../../docs/requirements-update-workflow.md) 11節 | 「すべての要求項目について、利用者の**選択または保留**が記録されている」 | 完了条件は全項目の決定ではない。**保留の記録で完了しうる** |
| 同 5.4節 | `DIF-06`・`DIF-13` を「保留」として記録済み | 同型の先送りが**既に実践されている** |
| [`requirements-usdm.md`](../../../docs/requirements-usdm.md) 第11章・第12章 | `REQ-C09-S02`・`S03`・`REQ-C11` は「段階2。仕様は第2フェーズで展開する」 | **仕様の展開を後工程へ送る運用が既にある** |
| [`arc-artifact-order.md`](../../../docs/arch-guide/arc-artifact-order.md) 5節 | 「論理設計17エンティティのうち物理仕様が確定しているのは `Project`／`Paper` だけであり、残る15件は利用フェーズ直前に確定する」 | **後工程での確定を前提にした運用が既にある** |

## 2. 判定手順

要求項目ごとに、次を順に見る。**先に一致したところで止める。**

### 判定1：根拠があるか

一次資料または決定台帳に根拠があるか。

⚠️ **根拠がなければ先送りしない。取り下げる。**
根拠のない候補を「後工程で決める」に分類すると、**根拠がないまま温存される。**

前例：`REQ-C09-S04` は一次資料の導入部が述べた困りごとから提案されたが、
配下の4小節をすべて分析しても根拠が得られず、取り下げた
（[`pending-req-c09-s04.md`](../../../docs/worknotes/pending-req-c09-s04.md) 第9章）。

### 判定2：何が足りなくて決められないのか

| 足りないもの | 分類 |
|---|---|
| 一次資料の追加分析 | **今の要件定義で決める。** 資料を読めば決まる |
| 既存要求との突き合わせ | **今の要件定義で決める。** 突合表を作れば決まる |
| 5択による方針の選択 | **今の要件定義で決める。** 選べば決まる |
| 画面に何をどう並べるか | 画面編へ送る |
| 状態遷移と処理の順序 | システム振る舞い編へ送る |
| エンティティの属性と関連 | データモデル編へ送る |
| 外部サービスの応答形式・制約 | 外部インタフェース編へ送る |
| 動かしてみないと分からない性能・コスト・運用 | 実装またはテストへ送る |

⚠️ **「決めるのが難しい」は先送りの理由にならない。**
先送りしてよいのは、**後工程の成果物が判断材料そのものになる**場合だけである。

### 判定3：どの工程へ送るか

送り先は1つに定める。複数の工程にまたがる場合は、**最も早い工程**へ送る。
そこで決まらなければ、その工程の記録に次の工程を書く。

## 3. 保留に必須の3項目

⚠️ **この3つを書かない保留を作らない。**

| 項目 | 内容 |
|---|---|
| **担当工程** | どの編・工程で決めるか。1節の表の名称を使う |
| **解除条件** | 何が分かれば決められるか。成果物の名前で書く |
| **再判断の期限** | いつ判断するか。工程の完了時点など、到来を確認できる形で書く |

### 3.1 なぜ3項目が要るのか

`DIF-06`・`DIF-13` は「保留」とだけ記録され、**いつ何をもって解除するかが書かれていない。**
2026年8月から残り続けている。

対して `REQ-C09-S04` は [`pending-req-c09-s04.md`](../../../docs/worknotes/pending-req-c09-s04.md) 第6章に
「判断すべき時期」を3条件で書いていた。**条件の到来を確認できたため、2026年9月7日に決着した。**

⚠️ **先送りしたこと自体を記録しなければ、後から見た人が検討漏れと誤解する。**

### 3.2 書き方

```markdown
- **保留**：<要求項目の名前>
  - 担当工程：データモデル編の設計
  - 解除条件：`arc-datamodel-definitions.md` に該当エンティティの属性が確定すること
  - 再判断の期限：データモデル編の一覧と定義が完成した時点
  - 保留の理由：<なぜ今決められないか。1〜2文>
```

## 4. 記録する場所

| 対象 | 記録先 |
|---|---|
| 要求項目の保留 | [`requirements.md`](../../../docs/requirements.md) 第10章 |
| 5択の中で保留と決めたもの | 該当する `requirements-decisions/batch-*.md` の選択結果 |
| 判断に材料が要るもの | `docs/worknotes/` に個別の検討資料を作る |
| 仕様の展開を送るもの | [`requirements-usdm.md`](../../../docs/requirements-usdm.md) の該当節に「状態」の行を置く |

⚠️ **`requirements.md` 第10章の既存5件も、この形式へ書き換える。**
認証・マルチユーザー、LLM プロバイダの固定と切替、実行基盤、
論文の figure キャプチャ、オフラインとセルフホストの要件は、いずれも担当工程と解除条件を持たない。

---

## 5. 要件定義の完了をどう判定するか

次をすべて満たしたとき、**要件定義は完了とする。**

1. すべての要求項目が、決定済みか、3節の3項目を備えた保留のいずれかである
2. 根拠のない候補が残っていない（取り下げ済み）
3. 決定済みの要求について、要求文・受入基準・仕様が文書間で一致している
4. 保留の一覧が [`requirements.md`](../../../docs/requirements.md) 第10章から辿れる

⚠️ **保留が残っていても完了と判定してよい。**
11節の完了条件が「選択または保留が記録されている」ことを求めているためである。
**保留をゼロにすることを完了の条件にすると、後工程の入力を待つ項目があるかぎり終わらない。**

---

## 6. 禁止事項

- 根拠のない候補を「後工程で決める」に分類する
- 担当工程・解除条件・再判断の期限のいずれかを欠いた保留を作る
- 「決めるのが難しい」を理由に先送りする
- 後工程で決めると記録した項目を、要件定義の側で先に決めてしまう
- 保留の一覧を更新せずに要件定義を完了と宣言する
- バッチ編・帳票編を送り先にする（本プロダクトの対象外）
- 他プロジェクトへこのスキルを適用する
- 同じ本文を `.claude/skills` や `docs/skills` へ複製する
