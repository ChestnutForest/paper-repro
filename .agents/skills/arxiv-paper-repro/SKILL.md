## 他スキルとの境界（english-parsing）

`english-parsing`（CCAF/TOEIC向けの英文解釈フォーマット）と発火条件が交差しうるため、次の基準で切り分ける。

**発火の必須条件は「実装・再現を目的としていること」。「英文を読むこと」ではない。**

| ユーザーの依頼 | 使うスキル |
|---|---|
| 論文のURL・PDFを提示して「実装したい」「再現したい」 | **このスキル** |
| 論文の数式・Method節をコードに落としたい | **このスキル** |
| 再現実装したがスコアが論文と合わない | **このスキル**（Phase 6から入る） |
| 英文（論文のAbstractを含む）を貼って「解釈して」「訳して」「構文を教えて」 | `english-parsing` |
| 論文を貼って「読み解いて」（実装の意図が示されていない） | `english-parsing` |

対象がarXiv論文の英文であっても、目的が英文解釈なら `english-parsing` に譲る。
**判断に迷ったら、ユーザーに「英文解釈が目的か、実装が目的か」を確認する。** 誤ったスキルで走り出すより、一言聞くほうが安い。

## このスキルの前提

再現実装の生産性を決めるのは「英語を速く読む力」ではない。次の2点でほぼ決まる。

- **(a) 論文の本質的な差分（Δ）を特定できるか**
- **(b) 検証ループを何秒で回せるか**

したがって、論文を頭から精読することも、ゼロからフルスクラッチで書くことも、どちらも負け筋である。
**論文は小説ではない。目的（自分の課題を解くパーツを探す）を持って、段階的に解像度を上げる**（スリーパス法）。
以下のPhase 0〜6を順に進める。**Phaseを飛ばさないこと。特にPhase 0とPhase 4を飛ばすと、後半で必ず原因不明のデバッグに沈む。**

## 論文タイプの判定（Phase 1で必ず行う。以降の全Phaseがこれで分岐する）

| | **タイプA：学習あり** | **タイプB：学習なし** |
|---|---|---|
| 例 | 新アーキテクチャ、新しい損失、事前学習・追加学習 | LLM応用、プロンプト手法、ベンチマーク、評価ハーネス、変換パイプライン |
| 中身 | モデル + 学習ループ | 既製LLM + プロンプト + 評価コード |
| 律速 | GPU時間 | **APIコスト・外部依存（レンダラ、実行環境）** |
| Phase 4 の検証 | shape→勾配→**1バッチ過学習**→ベースライン | 抽出→パース→**オラクル入力が満点**→少数サンプル照合 |
| Phase 6 で最後に疑うもの | モデル本体 | 外部依存（実行環境・パーサ・API） |

**タイプBに タイプA のサニティチェック（勾配・過学習）を当てるのは無意味。逆も同じ。**
判定を誤ると、存在しない不具合を探し続けることになる。

## 進め方の原則

- 各Phaseの終わりにユーザーへ中間成果（仕様メモ、Δリスト、仮定台帳）を提示し、認識をすり合わせてから次へ進む。勝手に全部実装しない。
- ユーザーの計算資源（GPU、API予算、時間、データ入手可否）を早期に確認する。フル再現が不可能なら**縮小版の設計に切り替える**。これは妥協ではなく正しい戦略である。
- 作業成果物（仕様メモ・仮定台帳・コード）はリポジトリ内の適切な場所へ保存し、利用中のAI開発環境が対応するファイルリンクで示す。会話に流すだけにしない。
- **推測で仮定台帳を埋めない。公式実装があるなら、コードを取得して読み、実測で確定させる。**「論文にこう書いてある」より「コードがこう動く」が常に強い。

## Phase 0 — 読む前（第1パス + 外堀）

### 0-A. 第1パス：鳥瞰と「読む価値」の判断（5〜10分）

**いきなり実装計画を立てない。まずこの論文を読む価値があるかを選別する。**

1. **タイトルと Abstract** — 何が課題で、どう解決し、どういう結果が出たか
2. **Introduction と Conclusion** — 著者のモチベーションと最終的な主張
3. **図表をパラパラ眺める** — アーキテクチャ図とパイプライン図、性能比較のグラフだけを流し見

**ここでのゴール:** 「この論文は、いま自分が抱えている課題に**直結しているか**」を判断する。
NO なら、ここで打ち切る。**読まないという判断も成果である。**

### 0-B. 外堀を埋める（ここで作業が消滅することすらある）

1. **公式実装の有無**を確認する。Abstract末尾の脚注、プロジェクトページ、GitHub、Papers with Code。
   - **存在するなら、タスクは「再現」ではなく「読解＋改造」に変わる。工数は1/5以下になる。** 見つけずに書き始めるのが最大の無駄。
   - **見つけたら必ずクローンして中を見る。** README の入出力スキーマと CLI は、論文の Method 節より情報量が多いことが珍しくない。
2. **OpenReview / 査読コメントを探す**（ICLR・NeurIPS系なら大抵ある）。査読者は論文が隠している弱点や欠落した実装詳細を的確に突いており、著者のrebuttalには**本文にないハイパーパラメータ**が書かれていることが頻繁にある。
3. **arXivのバージョン差分**（v1 → v2 → v3）。実装詳細は改訂で追記されがち。
4. **Related Work を「引用先の実装を探す」目的でだけ見る。**
   理解のために読むのではない。**ベースライン実装の在処を拾うためだけに見る。** これがPhase 2の土台になる。
5. **再現可能性の判定** — 必要GPU時間、API予算、データセットの入手性、ライセンス。

Web検索が使えるなら必ず検索する。論文タイトル + `github` / `official implementation` / `openreview`。

### Phase 0 の出力：方針を選んでユーザーと合意する

| 方針 | いつ選ぶか |
|---|---|
| **フル再現** | 公式実装なし、リソース十分、論文の主張そのものを検証したい |
| **縮小版** | リソースが足りない。**妥協ではなく正しい戦略** |
| **読解＋改造** | 公式実装あり。**最も多いケース** |
| **部分採用** | 論文全体は不要。**評価指標やプロンプトだけを自分のシステムに取り込みたい** |
| **見送り** | 第1パスで課題に直結しないと判断した |

**この5択を提示し、合意してから Phase 1 に進む。勝手に走り切らない。**

## Phase 1 — 仕様抽出リーディング（線形に読まない）

目的は「論文を理解すること」ではなく、**実装仕様書を書き出すこと**。

### 1-A. 第2パス：骨格とアプローチの把握（1時間程度）

1. **Method節の図解** — アーキテクチャ図と、その周辺のテキストを照らし合わせる。情報がどう流れ、どう整形されるか
2. **Experiments / Results の表** — ベースライン比でどれだけ上がったか。**どの指標で測っているか**
3. **図表はキャプチャして `spec.md` に貼る。** 後で実装方針を振り返るとき、最良のリファレンスになる

**ここで論文タイプ（A:学習あり / B:学習なし）を判定する。以降の全Phaseがこれで分岐する。**

**ゴール:** 「このアプローチは実装可能か」「この評価指標は自分のシステムでも使えるか」の目星をつける。

### 1-B. 第3パス：実装のための完全理解（実装すると決めた部分だけ）

**第2パスで「これを実装する / この指標を採用する」と決めた箇所に限って**詳細に読む。

1. **数式・アルゴリズムの詳細**
   - **タイプA:** 「理解」より先に **テンソルの shape を全部書き下す**。`x: [B, T, D]` レベルまで。**shapeが通れば実装の8割は決まる**
   - **タイプB:** **入出力のスキーマと、スコアの計算式**を書き下す。重み・丸め・部分点の有無まで
2. **前提条件と Limitations** — 自分の環境（データ、使えるモデル、API予算）で同じように動くか。
   **Limitations は「著者が認めた穴」であり、改造のΔはたいていここに落ちている**
3. **Appendix** — **AI論文では最も価値が高い宝庫。** 実際に使ったプロンプト、データセットのJSONサンプル、
   ハイパーパラメータが載っている。**本文より先に読んでもいいくらい重要**
4. **難解な条件分岐・数式の英文は、意味の塊ごとにスラッシュで区切って精読する。**
   （技法としてスラッシュリーディングを使うだけで、スキルの主導権はこちらにある。`english-parsing` には渡さない）

### LLM応用・ベンチマーク論文（タイプB）の特有チェックポイント

`references/llm-paper-checklist.md` を必ず読むこと。要点：

- **プロンプト構造** — Zero-shot か Few-shot か。Chain-of-Thought を使っているか。**出力の切り出し方（特殊トークン / コードフェンス）**
- **評価プロトコル** — 「正しい」をどう証明しているか。**単純な文字列一致か、スキーマ検証か、LLM-as-a-Judge か**。これで実装難度と再現コストが桁で変わる

### 英語読解のショートカット

実装者にとって意味を持つ定型表現がある。詳細は `references/english-cues.md` を読むこと。要点のみ：

- **"Following [Doe et al.]"** → 「その論文の実装をそのままコピーせよ」という指示。最強の手抜きポイント。
- **"We use the same architecture as X, except..."** → `except` 以降が唯一の差分。
- **"For simplicity" / "In practice, we find..."** → 論文の数式と実際のコードが乖離している箇所。バグの温床。
- **"omitted for brevity" / "see Appendix"** → 必ず追う。

### Phase 1の出力

`spec.md` を書き出してユーザーに提示する。**キャプチャした図表もここに貼る。**

**タイプA（学習あり）:**
```markdown
# 実装仕様メモ: <論文タイトル>
## 0. 論文タイプ: A（学習あり）
## 1. 入出力（型と shape）
## 2. アーキテクチャ（各モジュールの入出力 shape）
## 3. 損失関数（数式とその意味）
## 4. 学習設定（optimizer / lr / schedule / batch / epochs / 初期化）
## 5. データと前処理
## 6. 評価指標と評価プロトコル
```

**タイプB（学習なし。LLM応用・ベンチマーク）:**
```markdown
# 実装仕様メモ: <論文タイトル>
## 0. 論文タイプ: B（学習なし）
## 1. パイプラインの段構成（入力 → … → スコア）
## 2. データセットの実スキーマ（フィールド名まで。公式実装のREADMEが最良の情報源）
## 3. プロンプト（全文。Zero/Few-shot、CoT の有無、出力の切り出し方）
## 4. 評価指標（計算式・重み・丸め・部分点の有無）
## 5. 外部依存（実行環境、レンダラ、API、ライブラリの版）  ← ここが律速
## 6. 推論設定（temperature / max_tokens / 決定性）
## 7. 照合先の数値（論文の表から、再現の目標値を抜き出す）
```

## Phase 2 — 差分（Δ）の特定

**ほとんどのAI論文は「既存手法 + 小さなΔ」である。ゼロから書くのは負け筋。**

手順：

1. ベースライン実装を入手する（HuggingFace、公式リポジトリ、著者が比較対象にした手法のコード）。
2. **それが素の状態で動くことを先に確認する。** 論文のΔを入れる前に、ベースラインが動かない状態で先に進まない。
3. 論文のΔを **1〜3個の箇条書き**に圧縮する。

Δの例：
- 「損失関数に正則化項を1つ追加」
- 「attentionに新しいマスクを1種類追加」
- 「学習ループに2段階目（fine-tuning phase）を追加」

**Δが箇条書き5行に収まらないなら、まだ論文を理解できていないサイン。Phase 1に戻る。**

## Phase 3 — 仮定台帳（Assumption Ledger）

論文には必ず穴がある。**埋めた穴を記録しないと、後で数字が合わないときに切り分け不能になる。**

`assumptions.md` として次の表を作り、更新し続ける。テンプレートは `assets/assumption-ledger-template.md` にある。

| # | 曖昧な箇所 | 論文の記述 | 自分の選択 | 根拠 | 疑わしさ |
|---|---|---|---|---|---|
| 1 | LayerNormの位置 | 記述なし | Pre-LN | 引用元の実装に準拠 | 中 |
| 2 | 温度パラメータ τ | 「we set τ appropriately」 | 0.07 | SimCLRの慣例 | **高** |
| 3 | 負例のサンプリング | 曖昧 | バッチ内負例 | 計算量から推測 | 高 |

数字が合わないときは、**この表の「疑わしさ:高」から順に潰す。** これがあるかないかでデバッグ時間が桁で変わる。

## Phase 4 — 縦切り実装とサニティチェックの階段

横（機能ごと）ではなく、**縦（入力 → 出力 → スコアを最短で貫通）**に作る。おもちゃサイズで。

**必ず下から順にクリアする。段を飛ばさない。**
**そして、論文タイプに応じて正しい階段を使う。** タイプBに勾配チェックを当てても無意味である。

### タイプA（学習あり）の階段

| 段 | チェック | 落ちたときに疑うもの |
|---|---|---|
| 0 | **環境のピン留め** — seed固定、版固定、決定的動作 | — |
| 1 | **形が通る** — ランダム入力で出力shapeが期待どおり | Phase 1のshape書き下しが誤り |
| 2 | **勾配が流れる** — 全パラメータの `.grad` が None でなく NaN でもない | detach漏れ、in-place演算、初期化 |
| 3 | **1バッチに過学習できる** — サンプル8個で loss がほぼ0まで落ちる | **モデル本体か損失関数にバグ** |
| 4 | **ベースラインを再現** — Δを入れる前の素の状態で既知のスコアが出る | データ・前処理・評価 |
| 5 | **Δを1つずつ入れる** — 複数同時に入れない | 該当のΔ |

**段3（1バッチ過学習）を飛ばして大規模学習を回すのが、最大の時間浪費。**
8サンプルを暗記できないモデルは、100万サンプルでも絶対に学習しない。

### タイプB（学習なし。LLM応用・ベンチマーク）の階段

| 段 | チェック | 落ちたときに疑うもの |
|---|---|---|
| 0 | **環境のピン留め** — 版固定、temperature=0 等の決定性 | — |
| 1 | **データが読める** — 件数・タスク数・フィールドが論文の表と一致するか**実測**する | データセットの取り違え |
| 2 | **抽出・パースが通る** — LLMの生出力から目的の構造を切り出せる | 出力の切り出し方（特殊トークン / フェンス） |
| 3 | **オラクル入力が満点を取る** ← **最重要**。正解に相当する入力を人工的に作り、評価器に食わせて**満点が出るか** | **評価器そのもののバグ。ここが通らないなら、この先どんな数字が出ても意味がない** |
| 4 | **異常系が0点になる** — 壊れた入力・構文エラーを入れて、期待どおり落ちるか | 評価器が甘すぎる／厳しすぎる |
| 5 | **1件をE2Eで通す** — 実際のモデル出力1件で、入力→スコアまで貫通 | パイプラインの接続 |
| 6 | **識別力の高い少数サンプルで論文値と照合** | Phase 6 のデバッグ順序へ |
| 7 | **スケールする** — 全件へ。ここで新しい失敗モードは出ないはず | — |

**段3（オラクル満点）が、タイプBにおける「1バッチ過学習」に相当する。**
評価器が正解に満点を出せないなら、モデルの良し悪しなど測れない。
**ここを飛ばして全件を回し、採点バグに後から気づくのが最大の時間浪費**（GPUクォータやAPI予算ごと溶ける）。

段4（異常系が0点）も省かない。**評価器が何でも通してしまうバグは、スコアが「それっぽく」出るぶん発見が遅れる。**

詳細なチェックコード例は `references/sanity-checks.md` を参照。

## Phase 5 — フル再現ではなく「シグナル」を再現する

**論文のTable 1を丸ごと再現しようとしない。**

1. **安価に測れる代理指標**を1つ決める（例：全データの1%・小モデル・短エポックでの相対改善）。
2. 「ベースライン比で改善方向が出るか」だけを見る。**絶対値の一致は最後。**
3. 目標は「論文のSOTAスコア」ではなく、**「論文の主張（Δが効く）が自分の手元で成立するか」**。多くの目的にはこれで十分。

ユーザーに対しては、この段階で「何をもって再現成功とみなすか」の合意を取る。ここを曖昧にしたまま走ると、永遠に終わらない。

## Phase 6 — 数字が合わないときのデバッグ順序

**この順で疑う。** 実装したものから疑い始めるのが典型的な失敗。
自分が一番よく見ているぶん心理的に怪しく感じるが、実際の原因は圧倒的に手前にある。

### タイプA（学習あり）

1. **データ・前処理**（正規化、トークナイズ、train/val/testの切り方、ラベルのオフセット）— **圧倒的に多い**
2. **評価プロトコル**（指標の定義が論文と違う、testでチューニングしている、後処理の有無）
3. **最適化**（lr、warmup、weight decayの適用対象、勾配クリップ、AMPの数値精度）
4. **モデル本体** — **意外と最後**

### タイプB（学習なし）

1. **データ・前処理**（サブセットの取り違え、フィールドの読み違え、プロンプトの組み立て）
2. **評価プロトコル**（オラクルが満点か。平均の取り方。部分点の有無。丸め）
3. **推論設定**（temperature、max_tokens 切れ、chat template、thinking/reasoning モードの有無、量子化）
4. **外部依存** — **タイプBではここが「モデル本体」の位置に来る。**
   実行環境、レンダラ、**パーサのライブラリ差**（同じ形式でも実装により厳格さが違う）、APIの版。
   **環境依存で最も壊れやすく、しかも最後まで疑われない**

各項目の具体的な切り分け方は `references/debug-playbook.md` を参照。

## ツールの使い方（LLM含む）

- **LLMの使いどころは「数式 → コード」の下訳と、shape導出の検算。** ただし出力は必ずPhase 4のサニティチェックに通す。**生成コードをそのまま信じるのが再現失敗の典型。**
- **論文PDFを丸ごと投げて「実装して」は逆効果。** Method節の数式ブロックだけを切り出し、「この式のテンソル演算をshape付きで説明して」と聞くほうが精度が出る。
- 環境は最初にピン留めする（ライブラリのバージョン固定、seed固定、決定的動作の有効化）。**後からやると原因の切り分けができなくなる。**

## ユーザーへの接し方

- 論文が特定されていない場合は、まずURL・PDF・タイトルを尋ねる。
- **Phase 0 の第1パスで「読む価値」を判断し、方針（フル再現 / 縮小版 / 読解＋改造 / 部分採用 / 見送り）をユーザーと合意する。** 「見送り」も正当な結論である。
- **Phase 1 で論文タイプ（A:学習あり / B:学習なし）を判定し、明示的にユーザーへ伝える。** 以降のサニティチェックとデバッグ順序がこれで分岐するため、黙って進めない。
- 論文が特定できたら、**勝手に全Phaseを走り切らない。** Phase 0の結果（公式実装の有無、必要リソース）を報告し、方針（フル再現 / 縮小版 / 改造）を合意してから進む。
- ユーザーが「もう実装してある。数字が合わない」と言ってきた場合は、**Phase 6から入る**。ただし仮定台帳（Phase 3）が無ければ、先にそれを作らせる。切り分けの土台がないと何も進まない。
- 専門用語は相手の習熟度に合わせる。研究者相手なら略記でよいが、そうでなければ短く補足する。
