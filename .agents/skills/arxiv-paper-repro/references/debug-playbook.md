# 数字が合わないときのデバッグ手順（Phase 6 詳細）

> **本ファイルの1〜4は「タイプA（学習あり）」用。**
> **タイプB（学習なし）は末尾の「タイプBのデバッグ順序」を使うこと。**

**この順で疑う。** 経験上、原因の分布はこの順である。
モデル本体から疑い始めるのが典型的な失敗パターン。実装したモデルは自分が一番よく見ているぶん、
心理的に「怪しい」と感じやすいが、実際の原因は圧倒的に手前にある。

前提：**仮定台帳（Phase 3）があること。** 無ければ切り分けの土台がないので、先に作る。

---

## 1. データ・前処理 ← **圧倒的に多い**

まずここを疑う。ほとんどの再現失敗はここで終わる。

チェック項目：

- **正規化の統計量** — 論文はデータセット固有の mean/std を使っているか、`[0,1]` スケールか、`[-1,1]` か
- **train/val/test の分割** — 論文と同じ split を使っているか。**公式splitのファイルが配布されていることが多い**
- **testでチューニングしていないか** — 自分のvalが論文のtestと同じになっていないか
- **ラベルのオフセット** — 0始まりか1始まりか。`background` クラスの有無
- **トークナイズ** — 語彙、特殊トークン、最大長、truncationの方向（左/右）
- **画像のリサイズ順序** — resize → crop か crop → resize か。補間方法（bilinear/bicubic）
- **data augmentation** — 論文が使っているaugmentationを全部入れているか。**AugmentationはΔと同じくらい効く**
- **評価時のaugmentation** — test-time augmentationやcenter cropの有無

**切り分け方：** データローダから数サンプル取り出し、**目で見る**（画像なら表示、テキストならデコードして表示）。
統計量（mean/std/min/max、ラベル分布）を print する。ここで異常に気づくことが非常に多い。

---

## 2. 評価プロトコル

モデルは正しいのに、測り方が違うだけ、というケース。

- **指標の定義** — 同じ名前でも定義が違う。例：
  - F1 の micro / macro / weighted
  - mAP の計算方法（COCO式 / VOC式 / 11-point interpolation）
  - BLEU のトークナイザ依存性（`sacrebleu` を使っているか）
  - Accuracy が top-1 か top-5 か
- **公式の評価スクリプトがあるか** — あるならそれを使う。自作しない
- **後処理の有無** — NMS の閾値、beam search の幅、温度、閾値の最適化
- **どのcheckpointを評価しているか** — best-val か last か
- **論文の数字がアンサンブル/複数seedの最良値ではないか**

**切り分け方：** 公式の予測結果（配布されていることがある）を自分の評価コードに通し、論文の数字が再現するか見る。
再現しないなら**評価コードが原因**であり、モデルは無罪。

---

## 3. 最適化

- **learning rate** — 最も影響が大きい。まず10倍・1/10で振る
- **lrのスケーリング則** — 論文とバッチサイズが違うなら lr も変える必要がある（linear scaling rule 等）
- **warmup** — 有無とステップ数。Transformer系では必須のことが多い
- **weight decay の適用対象** — bias と LayerNorm のパラメータを除外しているか。**これは論文にはまず書かれていないが、標準的な実装では除外されている**
- **optimizer のハイパーパラメータ** — Adam の `betas`, `eps`。デフォルト値がフレームワークで違うことがある
- **勾配クリップ** — 有無と閾値
- **lr schedule** — cosine / step / linear。エポック単位かステップ単位か
- **AMP / 混合精度** — fp16 で不安定になっていないか。一度 fp32 で回して切り分ける
- **勾配累積** — 実効バッチサイズが論文と一致しているか

---

## 4. モデル本体 ← **意外と最後**

ここまで潰してから疑う。

- **正規化層の位置** — Pre-LN か Post-LN か（論文に書かれていないことが非常に多い。**仮定台帳の常連**）
- **初期化** — 論文が特別な初期化を指定しているか
- **活性化関数** — ReLU / GELU / SiLU。GELUには `tanh` 近似と exact の2種類があり、結果が変わる
- **residual接続の位置**
- **dropout の位置と率** — 適用箇所が違うと効きが変わる
- **重み共有（weight tying）** の有無
- **バイアス項** の有無

---

## 切り分けの技法

**二分探索する。** 「自分の実装」と「公式実装（あれば）」の中間状態を作る。

1. 公式実装のモデルに、自分のデータローダを繋ぐ → 数字が出れば**データが無罪**
2. 自分のモデルに、公式のデータローダを繋ぐ → 数字が出れば**モデルが無罪**
3. 中間テンソルを1層ずつ突き合わせる（同じ入力・同じ重みで、各層の出力の差分ノルムを見る）

```python
# 公式実装と自作実装に同じ重みをロードし、同じ入力を流して層ごとに比較する
diff = (mine_hidden - official_hidden).abs().max()
print(layer_name, diff.item())   # 最初に diff が跳ねた層が犯人
```

公式実装が無い場合は、**仮定台帳の「疑わしさ:高」の行を、1行ずつ変えて再実験する。**
これが台帳を作る最大の理由である。台帳が無いと、この探索が指数的に膨らむ。

---

## 撤退の判断

再現には往々にして、論文に書かれていない知見が必要になる。次のいずれかなら、深追いより先に手を打つ。

- 仮定台帳の「疑わしさ:高」を全部試しても、論文の数字に**5%以上**届かない
- 論文の主張の方向性（Δが効く）は再現できているが、絶対値だけが合わない

このとき取れる手：

1. **著者に連絡する。** メールやGitHubのIssueで質問する。返信率は思ったより高い。これは負けではなく、最も効率のよい手であることが多い
2. **Phase 5の「シグナル再現」で十分ではないか**を再考する。絶対値の一致が本当に目的か
3. その論文が**そもそも再現困難として知られていないか**を検索する（`<論文名> reproduce failed` / `not reproducible` / GitHub Issues）。既知なら、そこで消耗する意味はない

# タイプB（学習なし）のデバッグ順序

**「最適化」と「モデル本体」が存在しない。代わりに「推論設定」と「外部依存」が入る。**

## 1. データ・前処理 ← 最多

- **サブセットの取り違え**（論文の表と件数が合うか実測する）
- フィールドの読み違え
- **プロンプトの組み立て** — 論文の指示文（Appendix）を一字一句入れているか

## 2. 評価プロトコル

- **オラクルが満点か**（段3に戻る）。ここが通らないなら他を見ても無駄
- **平均の取り方** — タスク単純平均か、サンプル重み付きか。**論文の表から逆算して検算する**
- **部分点の有無** — 構文NGで全体が0点になる設計かどうか
- 丸め、判定不能（null）の扱い

## 3. 推論設定

- **temperature**（論文内で矛盾していることがある。設定表を優先し、両方試す）
- **max_tokens 切れ** — 長い構造化出力が途中で切られていないか
- **chat template** — 正しいテンプレートを適用しているか
- **reasoning / thinking モード** — 有効だと思考タグが混ざり、**パースが壊れる**
- **量子化** — 4bit にすると論文値との比較が無意味になる

## 4. 外部依存 ← **タイプBではここが「モデル本体」の位置**

**最も壊れやすく、しかも最後まで疑われない。**

- 実行環境・レンダラ（ブラウザ、TeX処理系）
- **パーサのライブラリ差** — 同じ形式でも実装により厳格さが違う
- 審査モデル（LLM-as-a-Judge）の版
- 文字コード・エスケープ処理

## 切り分けの技法

**中間ファイルを必ず残し、目で見る。**

- 生成の**生テキスト**を数件、そのまま読む。前置き、思考タグ、フェンスの有無を確認する
- レンダリングを伴うなら、**生成された画像を必ず開いて見る。**
  真っ白な画像でもパイプラインはエラーを出さず、構文点1を返しうる。
  その結果、採点だけが不可解に低くなり、原因究明に何時間も溶かすことになる
