## 段2: 勾配が流れる

**全パラメータ**の勾配が None でなく、NaN でもないことを確認する。
一部のパラメータだけ勾配が来ないのは、detach漏れ・分岐忘れ・in-place演算の典型的な兆候。

```python
loss = criterion(model(x), target)
loss.backward()

dead, nan = [], []
for name, p in model.named_parameters():
    if not p.requires_grad:
        continue
    if p.grad is None:
        dead.append(name)                       # 計算グラフから切れている
    elif torch.isnan(p.grad).any():
        nan.append(name)
    elif p.grad.abs().sum() == 0:
        dead.append(name + " (all-zero)")       # 勾配は来ているが常にゼロ

print("NO GRAD :", dead)
print("NaN GRAD:", nan)
assert not dead and not nan
```

疑うもの：`.detach()` の置き忘れ、`with torch.no_grad()` の範囲ミス、in-place演算（`x += y`）、
未使用のモジュール、初期化で全ゼロになっている重み。

## 段3: 1バッチに過学習できる ← **最重要**

**サンプル8個で loss がほぼ0まで落ちるか。**

```python
model.train()
xb, yb = next(iter(train_loader))
xb, yb = xb[:8], yb[:8]                  # たった8サンプル
opt = torch.optim.Adam(model.parameters(), lr=1e-3)

for step in range(300):
    opt.zero_grad()
    loss = criterion(model(xb), yb)
    loss.backward()
    opt.step()
    if step % 50 == 0:
        print(step, loss.item())

assert loss.item() < 1e-3, "8サンプルすら覚えられない → モデルか損失にバグがある"
```

**落ちないなら、モデル本体か損失関数にバグがある。**
8サンプルを暗記できないモデルが、100万サンプルで学習することは絶対にない。

**ここを飛ばして大規模学習を回すのが、最大の時間浪費。**
「とりあえず1エポック回してみる」の誘惑に負けないこと。数時間が無駄になる。

よくある原因：
- ラベルとロジットの対応がずれている（クラスのオフセット、one-hotと index の混同）
- 損失関数に `softmax` を二重にかけている（`CrossEntropyLoss` は内部でlog-softmaxする）
- lossの縮約軸が間違っている（`mean` すべき箇所で `sum`、あるいはその逆）
- 出力層が凍結されている

## 段の外：学習が「回り始めた」あとの監視

- lossが下がらない → lr が高すぎ or 低すぎ。まずlrを10倍・1/10で振る
- lossがNaNになる → 勾配爆発。grad clip、AMPのGradScaler、log(0)の混入を疑う
- train lossは下がるがval が下がらない → 正常な過学習。データ量・正則化の問題であってバグではない可能性が高い
- 学習が不安定 → warmupの有無を確認。論文のAppendixに書かれていることが多い

# タイプB（学習なし）の階段

LLM応用・ベンチマーク・評価ハーネス・変換パイプラインの論文用。
**勾配も損失もない。** 代わりに検証すべきは「**評価器が正しいか**」である。

## 段0: 決定性のピン留め

- `temperature=0`（greedy）を明示。**再実行で同じ数字が出る状態を先に作る**
- ライブラリの版を固定（`pip freeze > requirements.lock`）
- **パーサのライブラリを勝手に置き換えない。** 同じ形式でも実装により厳格さが違い、スコアが変わる

## 段1: データが読める

**論文の表と実測値を突き合わせる。** ここが合わないなら、サブセットを取り違えている。

```python
data = load(...)
print("件数:", len(data))                     # 論文の表と一致するか
print("タスク数:", len(set(d["task"] for d in data)))
assert len(data) == EXPECTED                  # 一致しないなら先に進まない
```

## 段2: 抽出・パースが通る

LLMの生出力から、目的の構造を切り出せるか。**特殊トークンかフェンスか**を確認する。

## 段3: **オラクル入力が満点を取る** ← 最重要

**正解に相当する入力を人工的に構築し、評価器に食わせる。満点が出るか。**

```python
oracle = build_oracle(item["expected_keys"])   # 期待仕様を全て満たす構造を機械的に生成
result = score(item, generation=wrap(oracle))
assert result["final_score"] == 1.00, "オラクルが満点にならない → 評価器が壊れている"
```

**これがタイプBにおける「1バッチ過学習」に相当する。**
評価器が正解に満点を出せないなら、モデルの良し悪しなど測れない。

**ここを飛ばして全件を回し、後から採点バグに気づくのが最大の時間浪費。**
GPUクォータやAPI予算ごと溶ける。

## 段4: 異常系が期待どおり0点になる

**評価器が甘すぎないか**を確認する。ここを省くと、スコアが「それっぽく」出るぶん発見が遅れる。

| 投入するもの | 期待 |
|---|---|
| 構文エラーの出力 | 0点 |
| 囲みタグが壊れた出力 | 論文の設計どおりの点（部分点なしなら0点） |
| 空出力 | 0点 |
| 指示違反（前置き付き、フェンス使用） | **論文の実装がどう扱うかを確認。** 意外と許容されていることがある |

**論文が報告している失敗モードを再現できれば、評価器が正しい強い証拠になる。**
（例: 特定モデルの特定タスクがちょうど0.00 → 構文エラーで部分点なしの設計と整合する）

## 段5: 1件をE2Eで通す

実際のモデル出力1件で、入力 → 生成 → 抽出 → 採点 まで貫通させる。

## 段6: 識別力の高い少数サンプルで論文値と照合

**全件を回さない。** 次の2種類を選ぶ。

- **サチュレーション側**（上位モデルがほぼ満点のタスク）→ **ここが低ければ確実に自分のバグ**
- **崩壊側**（モデル間でスコアが極端に割れるタスク）→ **識別力が最も高い。** 実装差がすぐ出る

## 段7: スケールする

段6が通れば、全件に広げる。**新しい失敗モードは出ないはず。**
出たなら、それは段1〜4のどこかを飛ばした証拠である。
