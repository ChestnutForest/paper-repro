# LLM応用・ベンチマーク論文（タイプB）のチェックリスト

学習のない論文（LLM応用、プロンプト手法、ベンチマーク、評価ハーネス、変換パイプライン）を
Phase 1（第3パス）で読むときに、**必ず埋めるべき項目**。

タイプAの論文と違い、ここでの律速は GPU ではなく **プロンプト・評価プロトコル・外部依存**である。

---

## 1. プロンプトエンジニアリングの構造

論文の Appendix にプロンプト全文が載っていることが多い。**最も価値の高い宝庫。**

| 項目 | 確認すること | なぜ効くか |
|---|---|---|
| **Zero-shot / Few-shot** | 例示を何件入れているか | few-shot を zero-shot で回すとスコアが大きく落ちる。逆も同じ |
| **Chain-of-Thought** | 「step by step」等の誘導があるか | CoT の有無で出力長もスコアも変わる |
| **出力の切り出し方** | 特殊トークン（`<\|BEGIN_CODE\|>` 等）か、コードフェンス（` ``` `）か、JSONモードか | **ここの実装が最大の急所。** モデルが囲みタグを壊すだけで、スコアが0点に落ちうる |
| **システムプロンプト** | 有無と全文 | 省略すると再現しない |
| **reasoning / thinking モード** | 対象モデルが思考モードを持つ場合、**有効か無効か** | 有効だと `<think>` 等が出力に混ざり、**パースが壊れ、トークン数も爆発する**。論文に明記されないことが多い |

**論文に書かれていなくても、公式実装のコードには痕跡が残る。**
例: 抽出関数に空の思考ブロックを除去する処理があれば、著者は思考モードを**無効**にして評価している。

## 2. 評価プロトコル — 「正しい」をどう証明しているか

**ここで実装難度と再現コストが桁で変わる。** 必ず分類する。

| 方式 | 実装コスト | 再現性 | 落とし穴 |
|---|---|---|---|
| **文字列一致 / 正規表現** | 低 | 高（決定的） | 大文字小文字、空白、正規化の差で数字が動く |
| **スキーマ検証・パース** | 低〜中 | 高 | **パーサのライブラリ差が効く。** 同じ形式でも実装により厳格さが違い、スコアが変わる |
| **構造照合（パス・キーの存在）** | 中 | 高 | ワイルドカードや添字のセマンティクスが曖昧。値まで見るのか、キーの存在だけかを確認 |
| **実行・レンダリング** | **高** | 中 | **外部依存の塊。** 環境構築の失敗が「モデルが悪い」に見える |
| **LLM-as-a-Judge / VLM採点** | 中 | **低** | **API課金が発生。** 審査モデルの版が変わると数字が動く。判定不能時の扱いが論文に書かれていないことが多い |

### 必ず確認する細部（論文に書かれないが、スコアを動かす）

- **部分点はあるか。** 構文エラー時に、内容点をゼロにするのか、独立に採点するのか
  → 「構文NGなら問答無用で0点」という設計は珍しくなく、**その場合スコアが極端に二極化する**
- **重み。** 複数指標の加重和なら、その重みは定数か、探索されたものか
- **丸め。** 小数第何位で丸めるか
- **平均の取り方。** タスク単純平均か、サンプル重み付き平均か。
  → **論文の表の数値から逆算して確定できることが多い。** 「表の各項の単純平均が総合値と一致するか」を電卓で検算する
- **判定不能（null / エラー）の扱い。** 不正解扱いか、分母から除外か

## 3. 外部依存（タイプBの「モデル本体」に相当する位置）

**最も壊れやすく、しかも最後まで疑われない。**

- 実行環境・レンダラ（ブラウザ、TeX処理系、可視化ライブラリ）
- **パーサのライブラリと版**（厳格さの違いがそのままスコア差になる）
- API（審査モデル、推論API）の**版とレート制限と課金**
- 文字コード・エスケープ処理（非ASCIIを壊す処理が紛れ込んでいることがある）

**サブセットに絞れば、外部依存が丸ごと消えることがある。**
例: レンダリングを伴わないサブセットだけを対象にすれば、レンダラもVLM採点も不要になり、
**API課金ゼロ・システム依存ゼロで完全再現できる**。Phase 0 の「縮小版」設計では、まずこれを検討する。

---

## 4. リソース見積もり（Phase 0 で必ず出す）

- **生成回数** = 例数 × モデル数
- **採点API回数** = LLM-as-a-Judge を使う例数 × モデル数 ← **課金の主因**
- **GPU** = オープンモデルをローカル推論する場合のみ。**API のみなら GPU 不要**
- 量子化の可否 — **量子化するとスコアが動き、論文値との比較が無意味になる。**
  比較したいなら、量子化せずに載るモデルサイズを選ぶ

## 5. 公式実装があるなら、コードで確定させる

タイプBの論文は、**仕様の細部が論文に書かれていない割合が特に高い**。
推測で仮定台帳を埋めず、**コードを取得して読む**。

読む優先順位：
1. **出力の抽出関数**（特殊トークン / フェンスのパース）
2. **スコアの最終計算**（重み・丸め・部分点の有無）
3. **各指標の実装**（パーサ、構造照合）
4. **データセットの実体**（件数・フィールドを実測し、論文の表と突き合わせる）
5. **推論設定**（temperature、chat template）

**「論文にこう書いてある」より「コードがこう動く」が常に強い。**
両者が矛盾している場合は、**コードを正とし、その矛盾自体を仮定台帳に記録する。**
